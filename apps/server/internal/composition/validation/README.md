# Проверка документов по окружению

`Load` выбирает активный manifest проекта/окружения. Для схемного Change Set используется только связанный неизменяемый кандидат: должны совпадать проект, окружение и исходный активный manifest, включая `NULL` при первой активации. Обычный Change Set не может использовать кандидат. Таблица `changeset_manifest_candidates` хранит эту привязку; кандидаты создаются командой `register-manifest` ([регистрация](../../../../../docs/manifest-registration.md)).

Вызывающий код передаёт `store.Queries` своей транзакции. Контекст блокирует окружение, затем команды блокируют CS и объекты. Workflow, проверяющий несколько окружений, сначала блокирует окружения проекта в порядке имени. Сам валидатор не активирует manifest. `RecordDiagnostics` сохраняет результаты по окружению в транзакции вызывающей команды.

Composed разрешается по точному объекту и версии:

- `live`: версия будущей публикации → рабочая версия того же незавершённого CS → опубликованная версия целевого окружения;
- числовая версия: только зафиксированная версия данного компонента в данном проекте, без подмены рабочей версией;
- анализ head: вместо published используется head; анализ рабочих версий учитывает их собственный CS.

Каждая транзитивная зависимость проходит L1–L6; L7 проверяет итоговое дерево страницы, включая Composed и заполненные слоты. Прямые и косвенные циклы обнаруживаются по ID компонента, даже если номера версий различаются (`COMPONENT_CYCLE`). Диагностика зависимости возвращается на ссылке исходного документа; `params` содержит ID компонента, ID разрешённой версии и вложенную диагностику с собственным указателем. Обход детерминирован. Защитные пределы: глубина 128 и 10000 раскрытий на документ (`LIMIT_EXCEEDED`).

`CheckPublication` проверяет будущие версии вместе с существующими опубликованными документами. Поэтому изменение live-компонента проверяет всех потребителей, включая транзитивных; исправления в том же пакете учитываются одновременно. `AnalyzeImpact` сохраняет отдельные стадии head/published/working и расширяет анализ использования через Composed перед проверкой предложенного manifest.

Workflow сохраняет целевые окружения и результаты `ir` по окружениям, включая проверенный хэш manifest. `submit-changeset` принимает необязательные `targets`; если они отсутствуют, используются ранее сохранённые цели либо все standard-окружения проекта. Для связанного схемного CS по умолчанию выбирается только его окружение. Кандидат, окружение и исходный manifest входят в хэш согласуемого содержимого; риск схемного CS — high.

Подача, согласование и rebase вызывают сервис; `publish` и `promote` повторяют проверку целевого контракта до любой записи публикации, сдвига указателей или outbox. Ошибка — `VALIDATION_FAILED` с диагностикой по объектам; транзакция откатывается целиком. Preview не допускает публикацию.

## Граница этого пакета

Реализованы контекст Composed, транзитивные зависимости/циклы и подключение L3–L7: manifest, привязки/действия, дизайн, политики и статическая A11Y. L4/L7 возвращают предупреждения черновика; ошибки L5/L6 отклоняют редактирование, ошибки L3–L7 блокируют публикацию. Предупреждения L7 не блокируют публикацию.

`ZoneRequirements` вычисляет requiredApprovalRole исходных/итоговых зон и затронутых live-потребителей. Workflow учитывает STRICT как high, связывает требования с хэшем согласования и возвращает requiredRoles/missingRequiredRoles. Публикация и продвижение повторно проверяют текущие роли активных независимых людей.

Регистрация и автоматическая активация подключены; отдельные диагностики по окружениям сохраняются с stale/needsAttention ([описание](../../../../../docs/manifest-registration.md)). Остаются остальные ссылки L2 (сущности/assets), динамический axe/preview, сущности и их миграции. Схемный lifecycle описан в [публикации схем](../../../../../docs/schema-publication.md). Данные кандидата можно проверять при первой активации, и опубликовать атомарно вместе с контрактом и исправленными документами. Подробности: [A11Y и согласование зон](../../../../../docs/a11y-zone-approvals.md).
