# Проверка документов по окружению

`Load` выбирает активный manifest проекта/окружения. Для схемного Change Set используется только связанный неизменяемый кандидат: должны совпадать проект, окружение и исходный активный manifest, включая `NULL` при первой активации. Обычный Change Set не может использовать кандидат. Таблица `changeset_manifest_candidates` хранит эту привязку; серверная регистрация и создание схемных CS появятся в следующем пакете.

Вызывающий код передаёт `store.Queries` своей транзакции. Контекст блокирует окружение, затем команды блокируют CS и объекты. Workflow, проверяющий несколько окружений, сначала блокирует окружения проекта в порядке имени. Проверки ничего не записывают и не активируют manifest.

Composed разрешается по точному объекту и версии:

- `live`: версия будущей публикации → рабочая версия того же незавершённого CS → опубликованная версия целевого окружения;
- числовая версия: только зафиксированная версия данного компонента в данном проекте, без подмены рабочей версией;
- анализ head: вместо published используется head; анализ рабочих версий учитывает их собственный CS.

Каждая транзитивная зависимость проходит L1/L3. Прямые и косвенные циклы обнаруживаются по ID компонента, даже если номера версий различаются (`COMPONENT_CYCLE`). Диагностика зависимости возвращается на ссылке исходного документа; `params` содержит ID компонента, ID разрешённой версии и вложенную диагностику с собственным указателем. Обход детерминирован. Защитные пределы: глубина 128 и 10000 раскрытий на документ (`LIMIT_EXCEEDED`).

`CheckPublication` проверяет будущие версии вместе с существующими опубликованными документами. Поэтому изменение live-компонента проверяет всех потребителей, включая транзитивных; исправления в том же пакете учитываются одновременно. `AnalyzeImpact` сохраняет отдельные стадии head/published/working и расширяет анализ использования через Composed перед проверкой предложенного manifest.

Workflow сохраняет целевые окружения и результаты `ir` по окружениям, включая проверенный хэш manifest. `submit-changeset` принимает необязательные `targets`; если они отсутствуют, используются ранее сохранённые цели либо все standard-окружения проекта. Для связанного схемного CS по умолчанию выбирается только его окружение. Кандидат, окружение и исходный manifest входят в хэш согласуемого содержимого; риск схемного CS — high.

Подача, согласование и rebase вызывают сервис; `publish` и `promote` повторяют проверку целевого контракта до любой записи публикации, сдвига указателей или outbox. Ошибка — `VALIDATION_FAILED` с диагностикой по объектам; транзакция откатывается целиком. Preview не допускает публикацию.

## Граница этого пакета

Реализованы контекст Composed (часть L2), транзитивные зависимости/циклы и подключение существующего L3. Привязки и действия (L4), остальные ссылки L2, design/policy/A11Y (L5–L7), отдельные сохранённые диагностики manifest с `stale`/`needsAttention`, регистрация/активация, схемные операции и совместный rollback ещё не реализованы. Данные кандидата можно проверять при первой активации, но схемная публикация пока явно блокируется `SCHEMA_PUBLICATION_NOT_READY`: содержимое нельзя опубликовать под кандидатом без его атомарной активации.
