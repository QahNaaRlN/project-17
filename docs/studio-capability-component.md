Продолжает [Missing Capability](studio-missing-capability.md),

## 1. Результат и границы

Дизайнер в CODE-зоне, не найдя в палитре подходящего компонента приложения,
описывает его: имя, назначение, критерии приёмки, свойства и слоты. После явной
отправки в выбранное место страницы вставляется **заглушка компонента** —
узел с типом запрошенного компонента и меткой `pending`, его свойства уже
заполнены и проверяются по предложенному контракту. Публикация страницы с
заглушкой блокируется. Разработчик получает context pack с контрактом,
похожими компонентами и их местом в коде, реализует компонент в приложении и
проходит обычный PR. Когда активный manifest стандартного окружения содержит
совместимый компонент из проверенного слияния, CMS снимает метку `pending`
во всех экземплярах группы (как в STU-338…347), и узел рендерится настоящим
компонентом. Проверка, согласование другим человеком и публикация остаются
обязательными.

В границах: вид запроса `component`, его контракт и правила имени; заглушка в IR
и её проверки; вставка заглушки при отправке и присоединение новых экземпляров
к группе; context pack для компонента; рендер заглушки в preview и подстановка
в preview/<ref>; совместимость и автоматическое/ручное выполнение через
существующие условия STU-339; агентский черновик; Studio RU/EN; миграция 00025;
локальная приёмка.

Вне границ: запросы `dataSource` и `token` (следующий пакет очереди, решение
§11.1), события и `provides` у заглушки (§11.3), генерация кода компонента,
автоматическое открытие PR, Composed-компоненты CMS (они создаются
`component.extract`, а не запросом), каталог и вставка компонентов из палитры
(отдельная задача M4), изменение уже опубликованных версий.

## 3. Требования

| ID | Требование |
|---|---|
| STU-355 | Запрос получает `kind: component`. Ключ — имя компонента `^[A-Z][A-Za-z0-9]{0,63}$`, не совпадает с builtin, `primitives` и `components` активного manifest исходного окружения и с открытым запросом того же вида (уникальность STU-258 по kind сохраняется). Заголовок, описание, acceptance — лимиты STU-256 |
| STU-356 | Предложенный контракт компонента: `props` в системе типов manifest §4 (до 32 свойств, глубина 8, без `content: true` и `reference` на неизвестные схемы), `container: bool`, `slots` (до 8, `allowedTypes` из builtin/manifest, `max` 1…50). События и `provides` в v1 не задаются (решение §11.3). Неизвестные поля отвергаются |
| STU-357 | Заглушка в IR — узел с `type` = ключ запроса и полем `pending` = id запроса (IR-053 расширяется, решение §11.2). Допустима только в черновике в эффективной CODE-зоне. Поля `props`, `bindings`, `design`, `when`, `children`, `slots` проверяются по предложенному контракту как по определению manifest; `on`, `ref`, `pending` у потомков заглушки — отклоняются |
| STU-358 | Публикация документа с заглушкой отклоняется (`COMPONENT_PENDING_CAPABILITY`, этап проверки IR) независимо от статуса запроса, как STU-269. Заглушка неизвестного, чужого, черновикового или терминального запроса — `CAPABILITY_PENDING_INVALID` при операции |
| STU-359 | Мастер в Structure и палитре: «Нужен другой компонент…» для выбранного места (родитель, слот, индекс) собственного открытого standard CS в CODE-зоне. Детерминированный поиск похожих: компоненты manifest по совпадению имени/категории/свойств и открытые запросы — до создания дубля; ручного JSON нет |
| STU-360 | Draft не меняет IR. Отправка (`submit-capability-request`) в одной транзакции проверяет revision/seq/manifest, место вставки и права, строит pack и записывает `node.insert` заглушки с начальными значениями свойств из формы. Повтор идемпотентен; ошибка откатывает всё |
| STU-361 | Права: создание — capability.request + design.read; отправка, присоединение и снятие — дополнительно design.compose, владение CS и CODE-зона, все locked/primary-content проверки. behavior.use не требуется (нет событий). code.propose не даёт правок IR |
| STU-362 | Привязка запроса вида `component` — узел (`anchor_kind=node`, событие пустое). Миграция 00025 расширяет CHECK вида запроса и привязки; существующие action-привязки не меняются. Лимиты STU-335 общие для видов |
| STU-363 | `attach-capability-request` для вида `component` вставляет ещё один экземпляр заглушки того же запроса в своё место собственного CS (parent, slot, index, свойства) — группа STU-336/337 с теми же правами видимости. Отсоединение удаляет свой экземпляр обычной `node.remove` |
| STU-364 | Операции над заглушкой: `node.setProps`/`setDesign`/`setBinding`/`setCondition`/`move`/`rename` — по предложенному контракту; `node.setBehavior` — отклоняется; `node.duplicate` и `component.extract` поддерева с заглушкой — `CAPABILITY_PENDING_INVALID` (новый экземпляр — только присоединением). Удаление узла оставляет привязку `anchor_changed` (STU-273) |
| STU-365 | Context pack вида `component`: контракт, начальные свойства и токены заглушки, родитель и слот (тип, без содержимого сущностей), до 5 похожих компонентов manifest с их `sourceRef` и записями индекса кода (definition, implementation, tests) по правилам STU-265 (≤ 40 файлов, стабильный порядок). Содержимое файлов и данные сущностей не включаются |
| STU-366 | Рендер: preview-режим runtime/React показывает заглушку нейтральным блоком с названием запроса и `data-cms-pending`, без вызова кода приложения; потомки в слотах рендерятся внутри. Published/Delivery API заглушек не содержат (STU-358). Старый adapter, не знающий `pending`, не рендерит узел (`null`) и не падает |
| STU-367 | preview/<ref>: если manifest PR содержит компонент ключа и он совместим (STU-368), ответ preview этого окружения рендерит узел настоящим компонентом, сняв `pending` только в ответе; иначе — заглушка с причиной. Хранимые версии не меняются (как STU-320) |
| STU-368 | Совместимость: каждое предложенное свойство есть в компоненте manifest с совместимым типом (правило STU-268); обязательные свойства компонента без default — среди предложенных; если у заглушки есть потомки, компонент принимает их (`container` или слоты с теми же именами и `allowedTypes`). Текущие значения свойств каждого экземпляра проходят L1–L4 по настоящему определению; иначе экземпляр — `invalid_props` |
| STU-369 | Выполнение — условия STU-339 с ключом в `components` активного manifest и совместимостью STU-368; происхождение версии, outbox, повторы и бюджеты — без изменений. Ручной resolve STU-268 для вида `component` — «Применить доступный компонент» владельцем |
| STU-370 | Снятие метки — операция `node.clearPending {nodeId}` (inverse восстанавливает метку только через журнал). Системный актор `cms-system` может выполнять её только для заглушки выполненного запроса вида `component` на живой привязке своего владельца; иные операции — `CAPABILITY_SYSTEM_OPERATION_FORBIDDEN` (STU-345). Замена по CS одной группой, undo → `reverted`, повтор, CS на проверке — как STU-342…347 |
| STU-371 | Агент: `report_missing_capability` создаёт draft вида `component` с местом вставки в разрешённом CS; `get_capability_request` читает проекцию. Агент не отправляет, не вставляет заглушку и не выполняет resolve (STU-271) |
| STU-372 | Studio: мастер компонента (свойства формой типов manifest, контейнер, слоты, начальные значения), бейдж «Ожидает компонент» на холсте и в Structure, панель свойств заглушки по контракту, карточка запроса с видом и разделами GitHub/Предпросмотр/Выполнение, «Вставить ещё экземпляр». RU/EN, клавиатура, 375 px, dirty guard, exact retry |
| STU-373 | Миграция/IR-схема Go и TS/команды/операции/pack/рендер/Query/Studio и отрицательные сценарии покрыты тестами с ID требований; conformance-фикстуры IR для заглушки; инъекция сбоя каждой новой записи. Покрытие Go ≥ 95% с запасом (цель ≥ 95.3% по итоговому CI); пороги не снижаются, исключения не добавляются |
| STU-374 | Локальная приёмка (§9): запрос компонента формами, заглушка на странице и в preview, блокировка публикации, второй экземпляр в другом CS, реализация компонента в витрине, preview/<ref>, автоматическое выполнение после `manifest push`, публикация с независимым согласованием и рендер настоящего компонента в новом публичном браузере |

## 4. IR и модель данных

Заглушка компонента (решение §11.2):

```json
"n_promo": {
  "id": "n_promo",
  "type": "PromoBanner",
  "pending": "0192f1c5-6a1e-7c3b-9d40-2f1e0c3b9a11",
  "props": { "title": { "lit": "Летняя распродажа" }, "tone": { "lit": "accent" } },
  "design": { "padding": { "token": "space.lg" } }
}
```

- `pending` — UUID запроса; допустим только у узла, чей `type` не определён в
  builtin/manifest. Определение для проверок берётся из `proposedContract`
  запроса по id через тот же механизм разрешения, что `Composed`
  (`ResolveComponent`), и только для запроса этого проекта.
- JSON Schema IR 1.0 получает необязательное поле `pending` узла; Go- и
  TS-валидаторы и conformance-фикстуры обновляются вместе. Документы без
  `pending` не меняются.
- Снятие метки — `node.clearPending`: после него узел проверяется по
  настоящему определению manifest; inverse восстанавливает метку только из
  журнала (как восстановление `pending:<id>` действия, STU-346).

Миграция 00025:

- `capability_requests.kind` — CHECK `IN ('action','component')`; уникальность
  открытого ключа по (project, environment, kind, key) сохраняется.
- `capability_request_anchors.anchor_kind` (`event`, `node`, по умолчанию
  `event`); для `node` событие — пустая строка; частичный уникальный индекс
  живой привязки включает `anchor_kind`.
- Состояние привязки `invalid_props` для вида `component`.

| Команда / операция | Изменение payload | Кто |
|---|---|---|
| create-capability-request | `kind`, для `component` — `placement {parentId, slot?, index}` вместо `nodeId/event`, `initialProps`; `proposedContract {props, container, slots}` | capability.request + design.read |
| submit-capability-request | Как сейчас; IR-жест — `node.insert` заглушки | + design.compose, владелец CS, CODE |
| attach-capability-request | Для `component` — `placement` и `initialProps` вместо `nodeId/event` | + design.compose |
| resolve-capability-request | Для `component` — без `handlers`; IR-жест — `node.clearPending` по всем своим экземплярам в CS | + design.compose |
| `node.clearPending` | `nodeId`; только заглушка выполненного запроса | design.compose; узкое право cms-system |

Аргументы выполнения (STU-344) для вида `component` не нужны: значения свойств
уже в узле; несовместимые значения дают `invalid_props`, владелец правит их
обычной панелью свойств и нажимает «Повторить замену».

## 5. Совместимость и происхождение

Совместимость STU-368 проверяется при preview/<ref>, автоматическом и ручном
выполнении одной функцией, по аналогии с `contractCompatible` для действий.
Происхождение версии (commit сборки равен слиянию PR или его потомок по GitHub
compare), CI слияния и свежесть наблюдения — без изменений STU-339/340.

Компонент в manifest может иметь `origin: native` или `generated`; оба
выполняют запрос, `origin` записывается в основание выполнения (решение §11.5,
уточнение AGT-062).

## 6. Выполнение и замена

Порядок STU-338…347 сохраняется: активация standard-manifest → оценка запроса →
привязки `queued` → замена по CS одной группой под блокировками окружения → CS →
объекты. Для привязки `node` под блокировкой повторяется: узел существует, его
`type` равен ключу, `pending` равен id запроса, текущие значения проходят
проверку по настоящему определению, потомки допустимы. Иначе — `anchor_changed`
или `invalid_props` без записи, остальные экземпляры CS откатываются вместе
с группой и обрабатываются заново (как `invalid_args`, STU-342).

## 7. Отказы и диагностики

| Код / состояние | Когда |
|---|---|
| `CAPABILITY_KEY_TAKEN` | Ключ есть в builtin/manifest или в открытом запросе вида `component` |
| `CAPABILITY_CONTRACT_INVALID` | Контракт нарушает STU-356 |
| `CAPABILITY_PLACEMENT_INVALID` | Родитель не принимает узел (контейнер, слот, `allowedTypes`, `max`), место вне CODE-зоны или locked |
| `CAPABILITY_PENDING_INVALID` | Заглушка чужого/неизвестного/терминального запроса, `duplicate`/`extract` заглушки, `on` у заглушки |
| `COMPONENT_PENDING_CAPABILITY` | Публикация документа с заглушкой |
| `waiting: key_missing`, `contract_incompatible` | Активный manifest не содержит совместимого компонента |
| `invalid_props` | Значения свойств экземпляра не проходят по настоящему определению |

## 8. Studio

Вход: в Structure и палитре для выбранного места — «Нужен другой компонент…»,
сначала список похожих компонентов и открытых запросов, затем мастер: имя и
описание, критерии приёмки, свойства (тип manifest, обязательность, default,
адаптивность), контейнер/слоты, начальные значения для этого места, предпросмотр
pack. Подтверждение «Отправить запрос и вставить заглушку».

Холст и Structure показывают заглушку бейджем «Ожидает компонент PromoBanner»;
панель свойств — по предложенному контракту; события недоступны с пояснением.
Карточка запроса показывает вид и контракт; разделы GitHub, Предпросмотр и
Выполнение — общие, с состоянием `invalid_props` и ссылкой на узел. На открытом
запросе — «Вставить ещё экземпляр» в выбранное место. RU/EN, клавиатура,
focus/Escape, 375 px, dirty guards и exact retry — как в предыдущих пакетах.

## 9. Проверки и локальная приёмка

| Область | Обязательные сценарии |
|---|---|
| IR | Заглушка валидна в CODE и отклоняется вне CODE; свойства/слоты по контракту; `on` отклоняется; Go/TS conformance одинаковы |
| Запросы | Имя занято builtin/manifest/открытым запросом; контракт за лимитами; гонка создания; draft не меняет IR |
| Отправка | Вставка в слот/контейнер; `allowedTypes`/`max`; locked; чужой CS; exact retry; конфликт seq |
| Операции | Правки заглушки по контракту; duplicate/extract/setBehavior отклоняются; удаление → `anchor_changed` |
| Pack | Состав и порядок; ≤ 40 файлов; без содержимого файлов и сущностей |
| Рендер | Заглушка в preview React и Studio; published не содержит; старый adapter не падает |
| preview/<ref> | Совместимый компонент рендерится только в ответе; несовместимый — заглушка с причиной |
| Выполнение | Каждое условие STU-339 для вида `component`; совместимость STU-368 по пунктам; `invalid_props` откатывает группу CS; undo/повтор; CS на проверке; системный актор не делает иных операций |
| Сбои | Инъекция сбоя новых колонок/состояний, команд, операции и pack |
| Регрессия | Action-запросы, привязки событий и выполнение STU-335…354 без изменений |

Локальная приёмка (изолированный стенд как в STU-354):

1. Базовая сборка витрины без `PromoBanner`; два человека, GitHub-каталог.
2. Alice в CODE-зоне CS-1 запрашивает `PromoBanner` (title, text, tone, слот
   `actions` для `Button`) формами, отправляет; на странице — заглушка с
   начальными значениями; preview показывает блок-заглушку.
3. Подача CS-1 отклоняется (`COMPONENT_PENDING_CAPABILITY`).
4. Во втором CS-2 Alice вставляет ещё экземпляр того же запроса.
5. Bob реализует `PromoBanner` в `examples/react-store`, PR #1; preview/<ref>
   показывает настоящий компонент; факты слияния — фикстура изолированной БД.
6. CLI `manifest push --env staging` с code index → запрос `fulfilled`, метки
   сняты в CS-1 и CS-2 системной группой; undo в CS-2 → `reverted`, повтор.
7. CS-1 подаётся, Bob согласует, Alice публикует; новый публичный браузер
   рендерит `PromoBanner` со значениями и кнопкой в слоте.
8. RU/EN, 375 px; отчёт `docs/studio-capability-component-acceptance.md`.

## 11. Вопросы к решению

1. **Состав пакета.** Рекомендация: только `component`; `dataSource` и `token`
   требуют своих заглушек в IR (`dataSources.*.source`, значения токенов),
   своих правил выполнения и рендера и идут следующим пакетом. Альтернатива —
   три вида сразу: один общий механизм, но примерно втрое больший объём и риск.
2. **Представление заглушки.** Рекомендация: узел с `type` = ключ и полем
   `pending` — свойства, слоты и потомки остаются на месте, выполнение лишь
   снимает метку, старый adapter не падает. Альтернатива — builtin-тип
   `Pending` с `ref.capability`: без нового поля, но выполнение меняет тип узла,
   а proposed-контракт нужно переносить в свойства.
3. **События у заглушки.** Рекомендация: в v1 нет — нельзя назначить действие
   событию компонента, которого ещё нет; события добавляются после выполнения.
   Альтернатива — предложенные события с `pending:` действий на них: вложенные
   запросы и сложное выполнение.
4. **Несовпадение свойств при выполнении.** Рекомендация: автоматически только
   при точных именах и валидных значениях, иначе `invalid_props` — владелец
   правит свойства и повторяет. Альтернатива — форма сопоставления
   переименованных свойств: больше UI и правил.
5. **Происхождение компонента.** Рекомендация: принимать `native` и
   `generated`, записывая `origin` в основание; AGT-062 трактуется как
   требование для компонентов, предложенных агентом. Альтернатива — только
   `generated`: разработчик обязан помечать компонент вручную.
6. **Удаление заглушки.** Рекомендация: обычное `node.remove` разрешено,
   привязка становится `anchor_changed` (как удалённый узел STU-273).
   Альтернатива — только явное отсоединение: строже, но мешает обычной правке.
7. **Новые экземпляры.** Рекомендация: только «Вставить ещё экземпляр» как
   присоединение к группе; `duplicate` заглушки отклоняется. Альтернатива —
   `duplicate` автоматически присоединяет копию: удобнее, но скрыто меняет группу.
