# Studio: сравнение изменений перед согласованием

Статус: **реализовано в рабочей ветке; локальная приёмка пройдена. Слияние в dev требует успешного CI**.
Дата: 2026-10-14. Основа: `dev`, commit `4a506ab` (после PR #51).

## 1. Цель и границы пакета

Согласующий открывает работу и видит, что именно изменено во всём Change Set
(CS): страницы, композиция, оформление, локальный текст, сущности и ассеты.
Он может сравнить результат с базой работы и с опубликованной версией выбранного
окружения, перейти к существующему узлу и принять решение по актуальному снимку.

Пакет расширяет [Работы и согласование](studio-work-approval.md),
[проверки и публикацию](studio-publishing.md) и [историю](studio-history.md).
Используются существующие графитовые/фиолетовые токены, Inter и компоненты Studio.
Figma не является зависимостью.

Начальная точка UI — CS, уже открытый из существующих «Работ» или редактора
страницы. Индекс сравнения включает все его объекты, а не только эту страницу.
Расширение очереди для работ без единой страницы (entity-only/asset-only CS)
не входит в пакет; backend сравнения не требует наличия страницы в CS.

В пакет входят backend Query API сравнения, защита команд от устаревшего
сравнения, Studio BFF, клиентский экран и приёмка на локальном OIDC-стенде.

В пакет не входят: редактирование через diff, разрешение конфликтов/rebase,
сравнение произвольных исторических версий, schema CS/миграции manifest,
визуальное сравнение скриншотов, diff бинарных файлов, откат публикаций,
подключение внешнего IdP, production-развёртывание и расширение Agent/MCP.

## 3. Два основания сравнения

**По умолчанию — «Изменения работы»: база CS → текущая рабочая версия.**
Это итог авторских изменений относительно `baseVersionId`, а не список всех
промежуточных действий. Операция и последующая отмена могут дать нулевой diff.
История таких действий остаётся доступной отдельно.

Второй режим — **«Изменения в окружении»: опубликовано в выбранном окружении →
текущая рабочая версия**. Он показывает результат предполагаемой публикации
для затронутых объектов. Выбранное окружение — настроенное окружение Studio,
которое должно входить в targets CS.

Пример: база работы — v19, в production опубликована v16, результат — рабочая
версия w20. Первый режим сравнивает v19 → w20, второй — v16 → w20. Интерфейс
обязательно называет основание; head не подставляется вместо published pointer.

Head показывается только как признак актуальности базы. Если он отличается от
baseVersionId, карточка объясняет необходимость rebase. Сравнение остаётся
доступно для чтения; согласование и публикация проходят существующие проверки.

Отсутствие версии и tombstone — разные состояния. Если раньше объекта не было,
показывается «Добавление в работу» или «Появится в окружении» по режиму.
Живая версия → tombstone означает удаление; tombstone → живая версия —
восстановление. Оба отсутствуют/оба tombstone дают отсутствие изменения
доставляемого содержимого; изменения метаданных tombstone видны отдельно.
Объект, созданный и удалённый внутри CS, нельзя представить как удаление
существовавшего объекта. Working-only объект другого CS не используется как база.
Для пары без живого объекта по обеим сторонам итог классифицируется как
`metadata-only`, если сведения отличаются, и `unchanged`, если записей diff нет.
Для живых объектов с изменёнными метаданными итог — `modified`.

## 5. Предлагаемый Query API

### 5.1. Полный индекс

`GET /api/v1/changesets/{id}/diff?environment=staging`

Чтение только standard CS в состояниях open/failed/changes_requested/in_review/
approved. Для merged/abandoned — `409 DIFF_STATE_UNSUPPORTED`: сравнение текущего
окружения с исторической публикацией относится к отдельному пакету.
Schema CS — `422 DIFF_KIND_UNSUPPORTED`, без выдачи частичного object diff.

Предлагаемые поля ответа:

```ts
interface DiffIndex {
  changesetId: string;
  seq: number;
  snapshot: string; // sha256:<64 hex>, детерминированный идентификатор снимка
  environment: string;
  targets: string[];
  complete: true;
  objects: {
    id: string;
    kind: "document" | "entity" | "asset";
    docKind?: "page" | "component";
    title: string;
    beforePath: string | null;
    afterPath: string | null;
    baseVersionId: string | null;
    workingVersionId: string;
    headVersionId: string | null;
    publishedVersionId: string | null; // выбранное окружение
    workingDeleted: boolean; // tombstone: переход к удалённому объекту отключён
    baseStale: boolean;
    summaries: {
      base: DiffSummary;
      published: DiffSummary;
    };
  }[];
}
interface DiffSummary {
  effect: "added" | "modified" | "deleted" | "restored" | "metadata-only" | "unchanged";
  changeCount: number; // число канонических записей детального diff
}
```

Индекс содержит все объекты CS, включая unchanged; сортировка — objectId.
`title` вычисляется детерминированно: имя корневого узла, поле названия схемы
при его наличии, название ассета, затем path/kind и короткий ID. Для удаления
используется before. Произвольное тело объекта в индекс не попадает.

Лимиты первой реализации: максимум 1000 объектов в CS для этого экрана,
максимум 4 MiB сериализованного ответа. Превышение —
`422 DIFF_LIMIT_EXCEEDED`, не успешный обрезанный индекс. Это лимит сравнения,
не новая квота записи CS и не изменение публикационной политики.

### 5.2. Детали объекта

`GET /api/v1/changesets/{id}/diff/{objectId}?environment=staging&baseline=base&snapshot=sha256:…&after=…&limit=100`

`baseline` — `base` или `published`; snapshot обязателен. `after` отсутствует
для первой страницы; limit по умолчанию 100, допустим 1–100.

```ts
interface DiffPage {
  changesetId: string;
  objectId: string;
  seq: number;
  snapshot: string;
  environment: string;
  baseline: "base" | "published";
  totalChanges: number;
  items: {
    key: string; // стабильный ключ в пределах снимка и baseline
    category:
      | "structure"
      | "property"
      | "design"
      | "binding"
      | "condition"
      | "behavior"
      | "localContent"
      | "metadata"
      | "content"
      | "file";
    kind: "add" | "remove" | "replace" | "move";
    pointer: string; // JSON Pointer, не URL
    nodeId?: string;
    locale?: string;
    before: DiffValue;
    after: DiffValue;
  }[];
  nextCursor: string | null;
}
type DiffValue =
  | { present: false }
  | { present: true; value: unknown }
  | { present: true; rawJson: string }
  | { present: true; redacted: true; reason: "service-field" };
```

`present: false` означает отсутствие, а не null. Для move значения описывают
место `{parentId, slot, index}`; изменения порядка используют реальный индекс,
не CSS-положение. Порядок записей фиксирован: категория, nodeId/ключ/locale,
JSON Pointer, вид изменения. Один и тот же снимок даёт одинаковые ключи,
счётчики и страницы. Перенос поддерева не создаёт move для каждого потомка,
чей собственный родитель/слот не изменился; сдвиги индексов соседей должны
показываться последовательно, без обещания математически минимального diff.

Числа сравниваются сервером без потери точности (включая целые больше 2^53);
эквивалентные JSON-числа 1 и 1.0 не дают замену. Если число внутри значения
исказится при разборе в JavaScript, сервер выдаёт `rawJson` вместо `value`.
UI показывает эту полную JSON-строку как текст, не преобразуя её через
JSON.parse/Number для отображения. Такой случай входит в общие fixtures.

Добавление/удаление узла даёт одну структурную запись с его собственными
данными; массивы children/slots показывают IDs, каждый изменённый потомок
имеет собственную запись. У целиком добавленного объекта детали перечисляют
его содержимое с отсутствующим before; удаление симметрично. Классификация
перемещений и изменение свойства одного узла могут существовать одновременно.

Курсор непрозрачен, защищён от подмены и привязан к project/CS/object,
снимку, окружению и baseline. Его использование в другом контексте —
`400 DIFF_CURSOR_INVALID`. Значения JSON выдаются полностью; UI сворачивает
большие значения. Сервер не обрезает строку/массив и не скрывает оставшиеся
изменения после первой страницы. Ответ ограничен 4 MiB: размер страницы
уменьшается при необходимости, сохранён nextCursor; если одна запись
не помещается — `422 DIFF_LIMIT_EXCEEDED` с безопасным кодом и objectId,
без фрагментов содержимого. UI сообщает невозможность полного сравнения.

Строки, HTML и RichText отображаются как текст/безопасные структурные данные,
без исполнения разметки, произвольных ссылок или команд. Для секретных
служебных полей ассетов — только признак изменения, не исходное значение.
Исключения перечисляются в типизированной серверной проекции; неизвестное
новое поле не пропускается молча: безопасное обычное поле отображается,
неподдерживаемая/служебная форма даёт явную диагностику и блокирует полное сравнение.
Redacted значение показывается как «Служебное значение скрыто» и сохраняет
признак изменения. Поля сущностей и RichText сравниваются в реально сохранённых
schemaVersion; upcast, разрешение ссылок через текущий head и автоматическое
применение нового manifest к старой версии при чтении запрещены. Метки полей
могут дополняться из доступного версионного контракта; при отсутствии метки
выводится исходное имя поля, а не придуманная схема.

### 5.3. Ошибки и BFF

| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Неверные UUID, baseline, limit, отсутствующий snapshot, неизвестный/повторный параметр | 400 PAYLOAD_INVALID; никаких частичных данных                                                 |
| Недействительная сессия / нет нужного права                                            | 401/403 по существующему контракту; очищение данных предыдущего пользователя                  |

| Окружение вне targets или настроенного окружения BFF                                   | 403 STUDIO_ENVIRONMENT_FORBIDDEN в BFF; backend 403 DIFF_ENVIRONMENT_FORBIDDEN                |
| Изменившийся снимок                                                                    | 409 DIFF_SNAPSHOT_STALE; индекс/детали считаются устаревшими                                  |
| Ненулевой ID базы/публикации не разрешается в допустимую версию                        | 409 DIFF_BASE_UNAVAILABLE; чтение завершается ошибкой, версия не подменяется отсутствием/head |
| Неподдерживаемый вид/состояние или превышение лимита                                   | Коды §§5.1–5.2; объяснение в UI, не пустой список                                             |
| Неподдерживаемая безопасная проекция данных                                            | 422 DIFF_PROJECTION_UNSUPPORTED; безопасные objectId/category, без сырых значений             |

BFF добавляет только эти read-only маршруты, фиксирует проект и своё окружение,
проверяет параметры и не проксирует произвольные versionId/from/to/URL.
Ответы `Cache-Control: no-store`; данные сравнения не попадают в localStorage,
логи, аналитику и сообщения Agent. Cache клиента разделён по пользователю,
проекту, CS, окружению, baseline и snapshot; logout/смена актора уничтожает его.

## 6. Идентичность и актуальность снимка

`snapshot` — SHA-256 канонического JSON следующего набора:

- projectId, changesetId, seq и отсортированные targets;
- полный отсортированный список объектов: ID/kind, baseVersionId, workingVersionId,
  хэш фактической рабочей проекции с телом, deleted, path и schemaVersion;
- текущие headVersionId этих объектов;
- publishedVersionId/отсутствие для каждого объекта в каждом target CS;
- идентичность активных manifest каждого target и действующий контекст
  публикационных требований (политика, настройки approvals и требования зон).

Для committed версий используются их неизменяемые ID и хэши. Отсутствие
представляется явно. Поля внутри JSON сортируются, массивы содержимого
сохраняют порядок; timestamp чтения, язык UI, развёрнутые секции и счётчик
уже полученных согласований не участвуют в идентичности снимка.

Baseline/выбранное окружение меняют представление деталей, но snapshot
покрывает весь CS и все targets и не зависит от выбранной вкладки. Добавление
согласования другим человеком само по себе не меняет этот fingerprint;
текущие state/actions и права всё равно перечитываются/проверяются отдельно.

Смена published pointer, head, содержимого, targets, manifest или требований
инвалидирует снимок даже при прежнем seq. Для проверки не нужны клиентские
тела before/after. Хэш не является секретом, bearer-токеном, доказательством
прочтения всех изменений или заменой существующего contentHash согласований.

## 7. Решение пользователя и серверная защита

Предлагается необязательное поле `expectedDiffSnapshot` в payload
`approve-changeset`, `request-changes`, `publish`. Существующие клиенты без
поля продолжают работать по прежним правилам. Новая Studio обязана передавать
поле вместе с expectedSeq; BFF для нового сценария проверяет его формат.
Расширение не вводит новое право и не делает чтение diff обязательным
публикационным правилом для всех API-клиентов.

Если поле передано, сервер проверяет актуальный fingerprint под существующим
порядком блокировок окружений/CS/объектов **до записи эффекта**. Чтение базы
для fingerprint и запись решения используют ту же транзакцию. Новый запрос
со старым снимком отклоняется `409 DIFF_SNAPSHOT_STALE` без решения/публикации.
Ошибки прав, самосогласования, expectedSeq, rebase, проверок, ролей и состояния
имеют прежнюю силу; diff не позволяет их обойти.

Реализация обязана проверить все пути записи источников fingerprint: CS/rebase,
publish/promote/rollback, manifest, политика и настройки approvals/зон.
Записи должны сериализоваться с этой проверкой по одному согласованному
порядку блокировок; простого перечитывания хэша до конкурентной записи
недостаточно. Если существующий writer не участвует в нужной блокировке,
его адаптация и тест гонки входят в этот пакет. Само чтение diff таких
блокировок записи не берёт. Изменение fingerprint из-за действий в другом
окружении targets требует перечитывания, а не автоматической смены цели.

UI разрешает решение только после загрузки полного индекса и успешного
первого ответа деталей выбранного объекта по текущему снимку. Пользователь
сам выбирает, какие объекты/страницы изменений открыть; отметки «прочитал всё»
не требуются. Ошибка выбранных деталей, незавершённое чтение, неподдерживаемое
сравнение и известный устаревший снимок временно выключают решения с объяснением.
Пустой CS не получает искусственную возможность согласования; нулевой diff
у непустого CS не отменяет существующие проверки и политику.

После согласования перечитываются review/actions; snapshot может остаться тем
же. Перед публикацией — явное перечитывание индекса и подтверждение всего CS
и окружения; чтение сбрасывает прежний выбор подтверждения, пользователь
подтверждает новый снимок самостоятельно. Снимок фиксируется при открытии
подтверждения, его смена закрывает подтверждение.

При потерянном ответе сохраняются прежние key/body/expectedSeq/snapshot;
повтор выполняется через существующую идемпотентность **до** повторной проверки
эффекта. Успешно завершённый запрос возвращает прежний receipt, даже если
состояние CS/published pointer уже изменилось вследствие этой публикации.
Неизвестный исход нельзя превратить в новую команду с новым снимком/ключом.
Известный отказ требует явного обновления и отдельного нового действия.

## 8. Представление Studio

В карточке работы блок «Изменения» располагается перед действиями согласования.
Он показывает число объектов, текущее основание и окружение. Индекс остаётся
доступен при выборе объекта; на узком экране элементы идут последовательно.

В строке объекта: название/маршрут до и после при смене, вид объекта, итоговый
эффект и число изменений. Детали группируются по понятным категориям:
«Структура», «Текст и свойства», «Оформление», «Привязки», «Поведение»,
«Контент», «Файл и сведения». Категории дополняются точным полем, локалью,
узлом и значениями до/после. Полные JSON и ID доступны в раскрываемых деталях.
Значения токенов показываются вместе с именами; разрешение токенов не заменяет
исходный diff и учитывает выбранный manifest окружения.

Для RichText/массивов первая версия использует безопасный структурный diff
с сохранением порядка. Выражения bindings/when/handlers не исполняются.
Ассеты показывают смену файла по хэшу и характеристикам, без загрузки оригинала.
Diff component показывает его собственный IR; экстраполяция изменений во все
инстансы и анализ влияния остаются отдельным пакетом.

Статусы: «Загружаем изменения», «Итоговых изменений нет», «Не удалось загрузить»,
«Работа или окружение изменились — перечитайте сравнение», «Сравнение превышает
лимит», «Этот вид работы пока не поддерживается». Ошибка следующей страницы
сохраняет загруженные строки с явной неполнотой и кнопкой повтора.
Кнопки решения получают текстовую причину недоступности, а не только disabled.

Открытие объекта/узла не меняет ничего в CMS. Существующий dirty/uncertain guard
действует до перехода. Возврат из редактора перечитывает изменённое сравнение,
сохраняя выбранный объект, если он ещё существует. Для entity/asset доступна
навигация к существующей карточке контента при наличии прав; создание нового
самостоятельного редактора этих объектов не требуется для этого пакета.

Go: контракт/изоляция запросов и команды с настоящим PostgreSQL, гонки чтения и

команд; отдельно реальный локальный OIDC-стенд без подмены CMS. Existing coverage
thresholds сохраняются; `go tool sqlc generate`, `go build ./...`, `pnpm check`
и CI обязательны для реализации. Спецификация сама по себе не подтверждает
наличие этих endpoints, реализацию race-защиты или прохождение новой приёмки.

## 10. Порядок реализации и завершение

1. Серверный согласованный read model, безопасные проекции и канонический diff;
   фиксированные fixtures для документов/контента/ассетов и обоих оснований.
2. Query API, курсоры/лимиты/права, fingerprint и атомарная защита команд;
   тесты PostgreSQL до подключения нового UI.
3. BFF/client validation, новый блок в карточке и переходы с существующими guards.
4. DOM/Chromium, реальная двухпользовательская приёмка и актуализация документации;
   PR в dev после обязательных проверок.

Пакет завершён, когда STU-149…161 выполнены, приёмка и CI подтверждены.
Полный M4/MVP, внешний IdP и production не объявляются завершёнными этим пакетом.

## 11. Реализация и проверка

Реализованы оба Query API, согласованное чтение PostgreSQL, каноническое сравнение
по ID узлов и точным JSON-числам, подписанные курсоры и пределы 1000 объектов /
100 изменений на страницу / 4 MiB. Index проверяет права на все виды объектов;
детали скрывают служебные поля ассетов. Защищённые команды проверяют снимок под
общими блокировками с изменениями manifest, policy и published pointers.

Studio показывает весь CS, обе базы сравнения, категории и значения до/после,
подгружает детали и открывает страницу/узел либо панель контента. Решения
блокируются при dirty/uncertain, ошибках и неактуальном сравнении; публикация
перечитывает индекс перед явным подтверждением. Повтор после потери ответа
сохраняет прежние тело команды, ключ и снимок.

Локальная приёмка 2026-10-14: настоящий PostgreSQL, CMS, signed OIDC Alice/Bob и
React-витрина. В CS `01a13acc-a122-760f-a131-fb0524c48010` вошли две страницы,
сущность Article и метаданные ассета. Ассет подготовлен как импортированный
committed fixture; бинарная загрузка в этой приёмке не проверялась. Alice
сохранила текст, Bob просмотрел все объекты и оба режима. Самосогласование
отклонено с 403; изменение approval policy при прежнем seq — с 409
`DIFF_SNAPSHOT_STALE`. Bob согласовал и явно опубликовал; committed документ,
сущность через Delivery API и заголовок в настоящем приложении подтверждены.
Снимки 1440px/390px проверены, горизонтального переполнения нет.

PostgreSQL-тесты проверяют mutable working body при неизменном UUID/seq,
REPEATABLE READ, base != published в разных окружениях, смену policy/pointers,
идемпотентность публикации, права и 1000/1001 объектов. DOM/BFF/Chromium
проверяют загрузку, курсоры, обе базы, переходы, guards и поздние ответы.
Полный `pnpm check` на Windows останавливается на POSIX-скрипте Go lint;
форматирование Go, генерация SQL, сборка, vet и проверки TS выполнены отдельно.
Окончательный полный набор с race/coverage выполняется в Linux CI.

Ограничения пакета сохранены: исторические версии и schema CS не сравниваются;
работы без страницы читаются backend, но их очередь в Studio пока не расширена.
