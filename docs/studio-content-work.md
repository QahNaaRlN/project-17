# Studio: создание работ с контентом без страницы

Статус: реализовано в рабочей ветке; локальная приёмка пройдена. Состояние CI — в PR.
Дата: 2026-10-15. Основа: `dev` на
`911dc8c4fda8ef0d82c257248da5afc5dbe447c1`, после слияния PR #55.
Пакет STU-190…202 продолжает [полную очередь работ](studio-work-queue.md),
[редактор контента](studio-content.md), [согласование](studio-work-approval.md),
[сравнение](studio-review-diff.md) и [историю публикаций](studio-publication-history.md).
Figma не требуется: используются существующие компоненты, Inter и фиолетовая палитра.

## 1. Результат и границы

Пользователь открывает «Работы», создаёт собственную работу, добавляет сущность
по схеме manifest или файл, сохраняет изменения, отправляет их на согласование
и получает опубликованный результат после решения другого человека.
Страница, её маршрут и document session для этого не нужны. Весь сценарий
доступен из Studio, без ручного ввода ID, команд API и подготовки CS извне.

В пакет входят создание пустого standard CS, действия добавления контента
в его карточке, возврат к сохранённой работе, обработка ошибок и проверка
существующего workflow для entity-only, asset-only и смешанной работы.
Формы, каталог ссылок, RichText, upload и публикация используют прежние контракты.

Не входят создание страниц/компонентов, изменение схем и локалей, новый файловый
менеджер, новый RichText, импорт HTML, автосохранение полей, архив очереди,
переименование и удаление работ, UI `abandon-changeset`, массовые операции,
конструкторы данных/поведения, Agent, Figma и production-развёртывание.
Отмена диалога до отправки ничего не создаёт. Уже созданная пустая работа
остаётся в очереди и может быть продолжена; скрытого удаления нет.

## 2. Проверенная исходная точка

- `create-changeset` в `apps/server/internal/changes/changes.go` уже создаёт
  собственный standard CS и принимает `title`, `description`, `targets`.
  Сервер проверяет наличие права записи и standard-окружения.
- `Api.createDraft` в `apps/studio/src/api.ts` уже вызывает эту команду,
  но вход в создание из `workspace.tsx` требует выбранную страницу.
  Клиентский reason сейчас описывает черновик страницы.
- После PR #55 есть `WorkContext`, открытие CS по `/editor#work=<id>`,
  самостоятельная карточка и формы контента без обязательного документа.
  Очередь показывает собственные пустые CS, но мастер создания самостоятельной
  работы был явно исключён из того пакета.
- `content-panel.tsx` уже содержит `entity.create`, схемные формы,
  локали и выбор ссылок. `asset-upload.tsx` реализует обработку файла
  и явное добавление в CS. Новые формы вместо них не нужны.
- `create-asset-upload` и `complete-asset-upload` требуют `asset.write`.
  Создание сущности требует `content.write`; чтение типов проверяется отдельно.
- Command Bus хранит результат идемпотентной команды 24 часа
  (`apps/server/db/queries/idempotency.sql`). Бесконечно безопасного повтора
  с тем же ключом этот контракт не гарантирует.

Уточнение модели доступа при реализации: отдельного `asset.read` в проекте нет.
Чтение сущностей и ассетов проверяется через `content.read`, запись ассетов —
через `asset.write`. Новое право и новая роль этим пакетом не вводятся.

## 4. Пользовательский сценарий

### 4.1. Создать работу

В заголовке очереди находится «Новая работа». Действие доступно человеку,
который может прочитать очередь и хотя бы один тип контента, а также имеет
соответствующее право записи: `content.read` + `content.write` либо
`content.read` + `asset.write`. Одного `content.publish` недостаточно.
Это условие входа данного UI; общие права `create-changeset` не сужаются.

Диалог содержит название и текущее окружение только для чтения.
Description и выбор другого окружения в этот пакет не входят.
Кнопка «Создать работу» создаёт пустой CS, без выбора обязательного типа:
работа может позднее содержать и сущности, и файлы.

При подтверждённом успехе открывается `/editor#work=<id>` и фокус переходит
на заголовок карточки. Ошибка последующего чтения не превращает успех создания
в новую попытку: ID сохраняется, повторяется открытие того же CS.
Список инвалидируется; текущие фильтры не сбрасываются скрыто. Если созданная
работа им не соответствует, карточка всё равно открывается, а при возврате
очередь может показать «Нет подходящих работ» с действием сброса фильтров.

### 4.2. Наполнить работу

Пустая карточка показывает «В работе пока нет изменений» и разрешённые действия.
Эти же действия остаются доступны после первого добавления. Список изменённых
объектов показывает состав CS, а существующий каталог — доступные объекты
проекта, которые можно изменить или выбрать в ссылочном поле. Эти списки
не подменяют друг друга: выбор объекта в каталоге сам по себе не добавляет
изменение в CS.

«Создать сущность» открывает выбор схемы из активного manifest окружения,
затем существующие поля. При отсутствии схем есть объяснение и повтор чтения,
без свободного ввода неизвестной схемы. Локали берутся из настроек проекта.
Missing required остаётся диагностикой черновика по текущему контракту;
окончательная готовность определяется серверными проверками публикации.
Singleton/уникальные поля и ссылочная целостность проверяются сервером;
конфликт не превращается в неявную замену существующей сущности.

«Загрузить файл» открывает существующий upload. Для недоступного storage или
неразрешённого MIME показывается конкретная причина; работа остаётся доступной.
После `ready` пользователь явно добавляет файл в работу. Метаданные редактируются
существующей формой. Добавление ссылки на новый ассет в сущность того же CS
доступно через существующий picker. Ни один шаг не публикует данные автоматически.

### 4.3. Согласовать и опубликовать

После первого подтверждённого изменения обновляются состав, seq, история,
диагностики и очередь. В ходе проверки/согласования формы работают только
на чтение; после возврата сохраняется прежний процесс возобновления правок.
Общий diff включает все типы объектов, даже если вход был через создание сущности.
После публикации активная карточка показывает подтверждённый результат и переход
в «Публикации» по существующему поведению. Отдельный publish одного файла не вводится.

## 5. Создание и неизвестный исход

Единица попытки — `{actor, project, environment, key, body, firstSentAt}`.
В body фиксируются команда, нормализованное название, `targets: [environment]`
и стабильный reason, описывающий работу с контентом. Повтор использует те же
значения, включая reason; повторное чтение config не меняет target попытки.
Общий адаптер создания можно переиспользовать, сохранив сценарий «Страниц».

До первого запроса минимальная запись попытки сохраняется в sessionStorage
текущей вкладки. Секреты, cookies, токены, signed URL, файл и содержимое форм
в эту запись не входят. При недоступном хранилище запрос создания не отправляется:
показывается восстанавливаемая ошибка, название остаётся в диалоге.

После сетевой ошибки, прерывания или некорректного успешного ответа исход считается
неизвестным. Нельзя разблокировать «новую» команду сменой названия, закрытием
диалога или reload. При восстановлении показывается незавершённая попытка
с явным «Проверить / повторить»; повтор не запускается при загрузке страницы.
Известный серверный отказ отделяется от неизвестного результата; следующий
исправленный запрос получает новый ключ только после определённого отказа.

Повтор разрешён лишь до 23 часов от первого отправления, с запасом относительно
24-часового серверного окна. При сомнительной/повреждённой временной записи,
переводе часов назад или истечении окна команда не переотправляется.
Показывается необходимость ручной сверки с очередью; отсутствие строки под
фильтром или на первой странице не доказывает отсутствие CS. Автоматическое
разрешение таких истёкших попыток и новый бессрочный recovery API вне пакета.
В этой ситуации возможность начать другую работу требует отдельного явного
подтверждения, что прежний результат не установлен и другая работа может
оказаться дубликатом; исходная запись не обозначается успешно отменённой.

После получения валидного ID он сохраняется до успешного открытия карточки.
При смене актора/проекта/окружения попытка не воспроизводится в новом контексте,
а её название не показывается другому человеку. Logout очищает чувствительные
данные попытки; после нового входа сверка выполняется через очередь вручную.
Гарантия восстановления неизвестной попытки ограничена той же вкладкой,
сохранённым sessionStorage и окном повтора. Закрытие вкладки, logout и очистка
хранилища не заявляются как гарантированное восстановление неподтверждённого CS.

## 6. Архитектурные ограничения

Используются существующие `POST /api/v1/commands/create-changeset`,
`apply-operations`, upload-команды, content/catalog Query API и work-queue API.
Новый backend CRUD и миграция для основной реализации не требуются.
Если проверка выявит необходимое расширение, оно фиксируется в контракте
и проверках PR, а не обходится прямой записью в БД.

Формы принимают `WorkContext`, не обязательный `DocumentRecord`.
Не создаются фиктивные page ID, session, маршрут, preview или presence.
После подтверждённой записи перечитывается серверное состояние; seq не
увеличивается оптимистически до результата. Query/cache keys учитывают актор,
проект, окружение, CS и параметры каталога. Смена контекста отменяет старые
запросы; поздний ответ не меняет текущую карточку.

`entity.create`/`asset.create` не имеют inverse по прежнему контракту.
История объясняет `UNDO_NOT_SUPPORTED`; закрытие формы не удаляет объект.
Правки полей, metadata и замена файла сохраняют прежнюю поддержку undo/redo.
Для остальных content-команд неизвестные исходы, exact retry и dirty guard
сохраняются по [контракту контента](studio-content.md); данная спецификация
не обещает долговременное хранение всех несохранённых форм или файлов.

Права проверяются при каждом серверном чтении и изменении. Потеря доступа
к любому затронутому типу закрывает весь CS по правилам полной очереди,
очищает недоступные данные и не оставляет editable-формы в кеше.
Право создания не даёт права согласования. Сервисный тестовый вход может
проверять создание, но не заменяет двух людей в приёмке workflow.

## 7. Проверки и приёмка

Каждое требование STU-190…202 покрывается тестом или фикстурой с ID согласно
[правилам тестирования](testing.md). Для документации этого PR требуются
проверка ссылок, уникальности ID, форматирования и `git diff --check`;
поведенческие проверки ниже обязательны при реализации.

| Уровень             | Проверки                                                                                                                                                                                                                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Адаптер / состояние | Trim и границы Unicode 0/1/200/201; точные targets/reason/key; двойной клик; commit с потерей ответа; reload и явный повтор; ID получен, но карточка не загрузилась; неизвестное/истёкшее окно; storage unavailable; смена identity/config.                                                                                 |
| UI / браузер        | Создание из пустой и отфильтрованной очереди без страницы; отмена до отправки; empty/no-schema/нет storage; сущность, файл и смешанная работа; формы на конфликте и после потери доступа; deep link/reload; фокус, клавиатура, RU/EN, 375 px.                                                                               |
| CMS / PostgreSQL    | Один CS при повторе точного запроса; запрет несовпадающего тела с тем же ключом; project/environment isolation; content-only и asset-only права без design.read; open/owner/seq/version/schema checks; пустая подача запрещена. Существующие гарантии покрываются действующими тестами, изменения — отдельными регрессиями. |
| Upload              | Реальное object storage; ready без asset.create не меняет CS; повтор complete/add без дубликатов; отклонённые MIME/размер, processing/error/expired и невозможность публикации незавершённого файла.                                                                                                                        |
| Workflow / Delivery | Alice создаёт и наполняет CS только через UI; Bob видит весь diff и согласует; самосогласование запрещено; отдельное явное действие публикует; Delivery читает точные сохранённые поля/файл. Проверяется также запрет решения по устаревшему снимку.                                                                        |

Для STU-202 стенд содержит настоящий CMS/PostgreSQL, локальный подписанный OIDC
с двумя учётными записями, storage и React-витрину. Подготовка manifest, ролей
и окружения допустима API; сами CS, сущность и ассет создаются через Studio.
Доказательство включает идентификаторы CS/объектов и опубликованного результата,
сравнение полей и SHA-256 скачанного файла, а также проверку, что в этих CS
нет затронутых page-документов. Entity-only, asset-only и смешанный сценарии
проходят отдельно; фикстура готового CS не заменяет создание через UI.

Перед PR реализации: целевые проверки Studio, браузерные сценарии, затронутые
Go/интеграционные тесты и `pnpm check`, без снижения порогов. Если меняются SQL,
выполняются `go tool sqlc generate` и `go build ./...`. Ограничения среды,
прерванные тесты и отсутствие реального storage отмечаются как непроверенные,
а не как успешная приёмка. CI проверяется на конечном SHA.

## 8. Готовность и порядок реализации

1. Независимое создание CS, валидация, durable attempt и переход в WorkContext.
2. Действия добавления и переиспользование content/upload в пустой карточке.
3. Reload/dirty/conflict/access состояния и обновление очереди после изменения.
4. Приёмка двух людей, Delivery, responsive/accessibility и обновление статусов.

Этап завершён, когда STU-190…202 подтверждены, проверки конечного PR зелёные,
нет зависимости от страницы, а документация содержит фактические результаты
приёмки и оставшиеся ограничения. Полные M4/M5/M6, Figma, внешний IdP
и production не считаются завершёнными этим пакетом.

## 9. Реализация и доказательства

Реализованы STU-190…202: «Новая работа» в очереди, независимое создание standard CS,
сохранённая в sessionStorage попытка с точным повтором, вход в существующие формы
сущностей/файлов из пустой и непустой карточки. Перезагрузка незавершённой попытки
остаётся на экране «Работы». Повторное действие добавления сбрасывает выбранную
форму после dirty guard; переключение сущность → файл не оставляет старую форму.
Права записи ограничивают действия карточки и редактора контента.

Локальная приёмка `scripts/studio-live-content-work.mjs` на настоящем стенде
CMS/PostgreSQL/OIDC/MinIO завершена: Alice создаёт entity-only, asset-only
и смешанный CS через UI; Bob согласует и явно публикует; Delivery возвращает
сохранённые данные. У entity-only запроса реальный сервер сначала выполняет
создание, после чего ответ намеренно отбрасывается на транспортной границе.
Reload и явный повтор возвращают тот же ID, поиск подтверждает одну работу.
API-фикстура готового CS или объекта в этом сценарии не используется.

Отдельная read-only проверка `scripts/fixtures/work-queue-verify.go` подтвердила
committed/head/published версии всех объектов, отсутствие документов в этих CS
и скачивание готового файла из локального S3 с точным SHA-256. Смешанная работа
проверяется с фактическим ожидаемым числом объектов, legacy-проверка одного объекта
сохранена. Проверены пустая подача, запрет самосогласования, reload, прямое
открытие и отсутствие горизонтального переполнения диалога на 375 px.
Отчёт `content-work-acceptance.json` и снимки `content-work-mobile.png` /
`content-work-desktop.png` хранятся в локальном каталоге доказательств.

Для повторения нужны `STUDIO_REVIEW_ADMIN_FILE`, `STUDIO_REVIEW_OUTPUT`,
затем `node scripts/studio-live-content-work.mjs`. Используется изолированный
loopback-стенд предыдущего пакета; в Studio дополнительно настраивается
`assetUploadOrigin` на origin локального storage с разрешённым CORS.
Независимая проверка запускается из `apps/server`:
`go run ../../scripts/fixtures/work-queue-verify.go <report-path>` при
`STUDIO_REVIEW_DATABASE_URL` на собственную loopback-БД `studio_work_queue_*`.
Секреты остаются в private-файлах и переменных окружения.

TypeScript-пакеты: типы, тесты и сборки пройдены; Studio — 271 тест,
покрытие statements 91,98%, branches 86,93%, functions 91,43%, lines 93,44%.
Браузерные регрессии — 60 сценариев. Отдельно проверены двойная отправка,
смена человека и отзыв прав при восстановлении неизвестного исхода:
ошибка нового preflight/повтора не доказывает отсутствие прежнего коммита.
`go build ./...` и `go vet ./...` пройдены. Локальный `pnpm check` проходит
форматирование и ESLint, но серверный POSIX lint не исполняется через Windows cmd.
Полный Linux check с Go race/coverage и Docker проверяется в CI конечного SHA;
локальные частичные проверки не подменяют его результат. Production, внешний
IdP, CDN, полный M4 и измерения NFR остаются за границами пакета.
