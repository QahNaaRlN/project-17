# Схемные операции, публикация и совместный откат

## Критерии приёмки

Подготовленный manifest остаётся кандидатом до согласования. Публикация применяет
схемы, активирует manifest и фиксирует исправленные документы одной транзакцией.
Отказ сохраняет прежние схемы окружения, active manifest, head/published,
Change Set и outbox. Откат возвращает предыдущий контракт вместе с контентом,
не создавая и не удаляя версии.

## Реализовано

- Регистрация standard-кандидата создаёт упорядоченные `schema.apply` для всех
  изменённых схем. Цель — `{kind: "schema", schemaName}`, без objectId и без
  фиктивного документа. Payload содержит `schema` и `version`; удаление — `null`.
  `before`/`after` вычисляются по исходному manifest и неизменяемому кандидату.
- Автоматические операции с `source: import` декларируют подготовленный план;
  они требуют права регистратора `manifest.register` при повторной проверке.
  Эта подготовка не записывает общий реестр и не активирует окружение.
- `claim-schema-changeset {changesetId, expectedSeq}` позволяет человеку с
  `schema.apply` принять открытый кандидат от сервиса. Владение другого человека
  забрать нельзя. Передача имеет неизменяемую запись аудита. Кандидаты предыдущего
  пакета без журнала получают план при принятии человеком.
- `apply-operations` принимает `schema.apply` с указанной схемной целью; для
  операций документов UUID-цели остаются совместимыми. Нельзя подменить версию,
  тело, имя схемы или использовать несвязанный кандидат. Запись в журнале входит
  в транзакцию пакета операций. Индивидуальный undo неизменяемого схемного плана
  не поддерживается: для другого плана нужен новый кандидат.
- Схемный CS без документов можно подать на согласование: его непустое содержимое
  составляет проверенный план. Риск high. Право владельца `schema.apply`
  проверяется по текущим ролям; авторы исправлений проверяются обычным policy stage.
  Кандидат и база входят в хэш согласуемого содержимого.
- Изменения схем, ломающие опубликованные привязки, могут остаться неактивным
  кандидатом (CNT-022). Pipeline блокирует его до исправления этих документов
  в том же CS. Несовместимые изменения остальных контрактов приложения продолжают
  отклоняться при регистрации по MF-022. Для автоматической preview-активации
  сохраняется запрет нарушения опубликованного контракта.
- `publish` повторно проверяет базу под блокировкой окружения, полный pipeline,
  хэш и действующие согласования людей. Публикующий и владелец должны сохранять
  `schema.apply`. Смена базы — `MANIFEST_BASE_CHANGED`; конфликт глобальной версии
  схемы — `SCHEMA_VERSION_CONFLICT`. Состояние CS и данные остаются прежними.
- После проверки атомарно сохраняются новые immutable версии схем, переключается
  active manifest и публикуются исправленные документы. Другие standard-окружения
  сохраняют свои active manifest. Известные одинаковые версии схем переиспользуются.
- История публикаций содержит `manifestChanged`, `previousManifestId` и
  `currentManifestId`, включая первую активацию с прежним `NULL` и rollback.
- `rollback` одновременно восстанавливает manifest и указатели контента.
  Superseded manifest или объект — `ROLLBACK_SUPERSEDED`. Возвращаемый контракт
  проверяется по оставшимся опубликованным документам: откат не оставляет их
  несовместимыми. Первая активация откатывается в `MANIFEST_NOT_READY`.
  Registry versions не удаляются; новых object versions при откате нет.
- Активация и откат обновляют диагностики незавершённых CS; смена базы инвалидирует
  кандидаты. Outbox в той же транзакции содержит ключи объектов, routes и manifest.
- `promote` схемной публикации явно отклоняется `PROMOTE_SCHEMA_NOT_SUPPORTED`:
  в целевом окружении требуется отдельная регистрация и согласование кандидата.

## Граница реализации

Работает lifecycle контракта, схем и документов IR. CRUD сущностей/ассетов,
проверки их ссылок L2, чтение/upcast и фоновая материализация CNT-023/024 ещё не
реализованы. Существующие версии схем сохраняются при откате без даункаста;
поддержка сущностей будет использовать эту модель. CLI/SDK, code index upload,
preview TTL и динамический runtime/axe pipeline остаются отдельными пакетами.

## Проверка

Интеграционные тесты с PostgreSQL покрывают первую активацию, публикацию только
схем, совместное исправление привязок, удаление схемы и обратный rollback,
права/согласования, неподходящую базу, конкурирующие версии между окружениями,
legacy-кандидаты и атомарность сбоев хранения, указателей и outbox.
