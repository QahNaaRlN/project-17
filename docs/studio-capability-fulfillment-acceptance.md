# Автоматическое выполнение запроса: реализация и проверка

Дата: 2026-10-20. Ветка: `feature/capability-fulfillment` от `dev` `291dc30`.
[Спецификация STU-335…354](studio-capability-fulfillment.md) одобрена пользователем
2026-10-20 вместе с решениями §11. Пакет не слит; полный M5 не завершён.

## Реализовано

- Миграция 00024: системный актор `cms-system` на проект (без токенов и входа;
  создаётся и для новых проектов в bootstrap), таблица привязок запроса с переносом
  исходной привязки 1:1, основание выполнения в запросе, outbox оценки и аудит.
- Команды `attach-capability-request`, `detach-capability-request`,
  `set-capability-fulfillment-args`, `retry-capability-fulfillment`,
  `check-capability-fulfillment`; поиск открытого запроса по ключу.
- Проверка заглушки в конвейере операций по таблице привязок. Узкое правило
  системного актора: только `node.setBehavior`, только замена `pending:<id>`
  выполненного запроса на вызов его ключа на месте живой привязки, только в CS
  владельца, от имени которого он действует. Стадия проверки прав CS признаёт эту
  операцию.
- Outbox: активация standard-manifest (регистрация и публикация схемного CS),
  проверенное наблюдение «PR слит» и явная проверка ставят оценку. River-задача
  каждые 10 секунд оценивает условия STU-339, при необходимости вызывает GitHub
  compare и запрашивает свежие факты в бюджетах STU-305; решение фиксируется
  короткой транзакцией.
- Замена по CS одной группой операций через общий конвейер (inverse, история,
  undo, rebase); неверные аргументы откатывают группу и отклоняют только свою
  привязку; ручной resolve выполняет запрос и ставит в очередь остальные привязки.
- Query `GET /capability-requests/{id}/fulfillment`, `GET /capability-requests/open`,
  краткая сводка в карточке запроса и у агента; маршруты BFF.
- Studio: раздел «Выполнение» (состояние и причина, основание, свои привязки,
  аргументы выполнения, повтор замены, отсоединение, явная проверка, exact retry),
  «Присоединить к существующему запросу» в мастере запроса.

## Отступления и уточнения при реализации

| Тема | Решение | Основание |
|---|---|---|
| `changes_requested` и `failed` CS | Не меняются системой, ждут возврата в `open` (как `in_review`/`approved`) | Конвейер операций принимает правки только в `open`; подача с заглушкой переводит CS в `failed` |
| Префилл из preview-аргументов | Не реализован: форма аргументов выполнения заполняется вручную | Query preview отдаёт только статус аргументов, не значения; решение §11.2 соблюдено — без подтверждения замены нет |
| Предпросмотр PR для присоединённых привязок | Подстановка в preview/<ref> работает только для исходной привязки | Подстановка STU-320 опирается на привязку запроса; расширение — отдельной задачей |
| Повтор после временной ошибки | Задача оценки возвращается в очередь до 3 попыток с шагом 1 минута | Ограниченный повтор STU-340 без бесконечных задач |
| Отображение «отменено» | `reverted` вычисляется при чтении: замена была, а заглушка снова на месте | Undo не требует отдельного хука, состояние всегда соответствует черновику |

## Автоматические проверки

- Go: тесты с ID требований — группа и присоединение, все условия STU-339
  (слит/не слит, потомок/расхождение/недоступно сравнение, без индекса,
  несовместимый контракт, CI слияния, устаревшее наблюдение, без связи), замена
  и неверные аргументы, CS на проверке/`failed`/закрытый/изменённый узел, undo и
  повтор, ручной resolve группы, кросс-владельцы и видимость, узкое правило
  системного актора, прохождение проверок после замены, инъекция сбоев каждой
  новой таблицы и шага; юнит-тест GitHub compare.
- CI-эквивалент в Linux-контейнере: `go test -race` с PostgreSQL и порогом покрытия
  (`assets`/`imagedelivery` в контейнере без S3/imgproxy не запускаются; в CI запускаются).
- Studio: тесты раздела «Выполнение», API-клиента и BFF; ESLint и typecheck.

## Не проверено

- Реальный GitHub (слияние PR и compare на настоящем репозитории).
- Продакшн-хостинг приложения; почтовые уведомления — вне пакета (решение §11.6).
