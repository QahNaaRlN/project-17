# Регистрация и активация manifest

## Цель и критерии приёмки

Контракт приложения регистрируется через Command API, выбирается по окружению и
проверяется до активации. Ошибка откатывает всю транзакцию: active manifest,
документы, указатели публикаций и диагностики остаются прежними.

## Реализовано

- `register-manifest`: только сервисный актор с `manifest.register` (MF-004).
  Payload: `manifest`, `environment`. Полная проверка формата и семантики manifest.
- Канонический SHA-256 и неизменяемое хранение (MF-002). Повтор hash сохраняет
  исходные тело, автора и время. Повтор Idempotency-Key возвращает сохранённый ответ.
- Diff и анализ L1–L7 для head, опубликованных версий целевого окружения и рабочих
  версий незавершённых Change Set, включая точные транзитивные версии Composed (MF-020).
- Несовместимые используемые опубликованные контракты отклоняются с
  `MANIFEST_BREAKING_IN_USE` и отчётом. Блокирующая диагностика опубликованного
  документа также отклоняет активацию, включая изменения класса `visual` (MF-022).
- Standard без изменений схем активируется автоматически. Любое изменение схем
  сохраняет кандидат и отдельный `kind: schema` Change Set с неизменяемой привязкой
  project/environment/base manifest (MF-021/025/026). Повтор кандидата с той же
  базой возвращает существующий незавершённый Change Set; его состояние сохраняется.
- Preview активируется сразу и хранит отдельные снимки схем по manifest, не меняя
  общий реестр standard (MF-033). Регистрация preview-manifest в standard снова
  проверяет глобальный реестр версий: одинаковая версия имеет одинаковое тело;
  новая версия выше последней; известная старая версия может повторно использоваться
  в отстающем окружении. Конфликт — `SCHEMA_VERSION_CONFLICT` (CNT-002).
- Активация повторно проверяет незавершённые обычные Change Set по этому окружению.
  Сохраняются diagnostics, проверенный manifest и seq без смены состояния CS.
  Проверки остальных окружений сохраняются (MF-023, CHG-034).
- `GET /api/v1/changesets/{id}` показывает `needsAttention`, `manifestDiagnostics`,
  kind и привязку кандидата. Ошибка или устаревшая проверка требует внимания;
  свежесть учитывает seq, manifest и базу кандидата. Согласование/recheck обновляет
  проверенное окружение; перед публикацией проверка повторяется в её транзакции.
- `GET /api/v1/manifest?environment=...` (`design.read`) и
  `GET /api/v1/schemas?environment=...` (`schema.read`) читают только активный
  неизменяемый контракт. При отсутствии активного manifest — `MANIFEST_NOT_READY`.

Ответ регистрации: `manifestHash`, `activation` (`active` или `pending`), diff
`changes`, `impact`; при `pending` также `changesetId`. Все изменения выполняются
в транзакции Command Bus. Порядок блокировок: окружения по имени, CS, объекты.

## Следующий пакет

Связанный схемный CS пока принадлежит зарегистрировавшему сервису и не содержит
операций `schema.apply`. CNT-021 реализован частично: создание кандидата и привязка
готовы; операции, передача владения человеку, миграция сущностей, согласуемая
схемная публикация, сравнение исходного manifest при активации и совместный откат
manifest/контента ещё впереди. Публикация кандидата продолжает блокироваться
`SCHEMA_PUBLICATION_NOT_READY`; пустой схемный CS нельзя подать на согласование.

Code index upload не реализован: `codeIndexUploadId` и заявление `uploaded: true`
отклоняются с `CODE_INDEX_UPLOAD_NOT_READY`. CLI/SDK с ожиданием deployment,
TTL/удаление preview, динамические axe-проверки и runtime — отдельные этапы.

## Проверка

Интеграционные тесты проверяют команды и Query API с PostgreSQL: авторизацию,
идемпотентность, конкурирующие регистрации, кандидаты со сменой базы, изоляцию
preview, версии схем, независимые диагностики окружений и блокировку публикации.
Сбои записи manifest, active pointer, кандидата, снимка схем и диагностик проверяют
полный откат транзакции. Общие проверки и покрытие запускаются по docs/testing.md.
