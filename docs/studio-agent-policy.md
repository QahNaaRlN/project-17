## 1. Результат и границы

Администратор проекта задаёт для агентов не только общий список прав, но и
**условные правила**: где агенту разрешено, где запрещено и где его изменения
требуют согласования — в зависимости от окружения, пути страницы, зоны и её
режима, вида операции и схемы контента. По тем же правилам проект повышает
риск и число согласований для изменений, сделанных агентом. Каждое решение
объяснимо: отказ называет право, правило и условие, а Studio показывает
администратору «проверку политики» для заданной ситуации до сохранения.

Политика по-прежнему только **сужает** права агента: эффективные права сессии —
пересечение прав делегирующего человека, снимка прав сессии, неизменного
потолка агента и правил политики (AGT-022). Условное правило не может выдать
агенту публикацию, согласование, управление зонами или иное право вне потолка.

В границах: документ политики версии 1 (правила для агентов, правила риска и
согласований), команда `set-agent-policy` с версиями и аудитом, вычисление при
каждой операции агента и повторно на этапе проверки прав CS, объяснимые
отказы и записи `security_events`, перенос текущей allow/deny-политики,
проверка политики (dry-run), редактор в Studio RU/EN, миграция 00027,
локальная приёмка.

Вне границ: правила для ролей людей (решение §11.1), выдача агентам прав вне
потолка, в том числе публикации (§11.2), YAML-формат (§11.3), секционирование
`security_events`, внешние policy-движки, условия по времени и по содержимому
значений, изменение уже опубликованных версий.

## 3. Требования

| ID | Требование |
|---|---|
| STU-420 | Документ политики v1 (JSON): `rules` — список `{id, subject, allow?, deny?, requireApproval?, when?}`, где `subject` — `{agent: "*"}` или `{agent: <имя зарегистрированного агента>}`; `risk` — список `{id, when, min}`; `approvals` — список `{id, when, require: {count, roles?}}`. До 100 правил каждого вида, `id` уникален (`^[a-z][a-z0-9-]{0,63}$`), неизвестные поля отвергаются |
| STU-421 | Условия `when`: `environment`, `pathPrefix`, `zoneMode`, `zoneId`, `operationType`, `schema`, `risk`, `source`. Внутри условия — ИЛИ значений, между условиями — И. Значения проверяются при сохранении: известные окружения, режимы, типы операций, схемы активного manifest; `pathPrefix` начинается с `/` |
| STU-422 | Вычисление для операции с правом R (AGT-010/011): подходящий `deny` с R — отказ; иначе R в потолке агента, делегата и сессии и (в подходящем `allow` или нет правил `allow` для этого агента) — разрешено; иначе R в подходящем `requireApproval` — разрешено с обязательным согласованием CS; иначе — отказ. `deny` всегда сильнее `allow` |
| STU-423 | Контекст операции: окружения — цели CS; путь — путь документа (для сущностей — отсутствует); зона и режим — эффективные у затронутого узла; тип операции и схема — из операции. Правило с `environment` подходит, если условие выполнено для **любой** цели CS при `deny` и для **всех** целей при `allow`/`requireApproval` (решение §11.4) |
| STU-424 | Условия `risk` известны только при подаче: правила с `risk` применяются на этапе проверки прав CS (этап 5) и при публикации, а не в момент операции. Остальные условия применяются и в операции, и на этапе 5 |
| STU-425 | Каждая операция агента (`apply-operations`, `create-changeset`, `submit-changeset`, `create-capability-request`) проверяется политикой в транзакции команды до записи. Пакет операций отклоняется целиком при отказе любой операции, ответ называет индекс операции |
| STU-426 | Отказ: `403 POLICY_DENIED` c `params {right, ruleId?, condition?, operationIndex?, reason}`, где `reason` — `no_rule`, `denied_by_rule`, `outside_ceiling`, `delegate_lacks_right`. В `security_events` пишутся те же поля без данных страницы; тексты не раскрывают содержимое других CS |
| STU-427 | `requireApproval`: операция записывается, CS агента получает метку `policyApproval: [ruleId]`; подача требует ≥ 1 согласования человеком, не являющимся делегатом, даже при низком риске (дополняет PUB-001…004) |
| STU-428 | Правила риска: при подаче CS риск поднимается до максимального `min` из подходящих правил (`source`, `pathPrefix`, `environment`, `zoneMode`); риск агентского CS не ниже `medium` (как сейчас) |
| STU-429 | Правила согласований: при подаче требуемое число и роли согласующих — максимум из `set-approval-policy`, зон и подходящих правил `approvals` (`risk`, `environment`, `source`). Недостающие роли — `APPROVAL_ROLES_MISSING`, как у зон |
| STU-430 | Этап 5 и публикация повторно вычисляют политику для всех операций агента CS по **текущей** версии политики (AGT-013): новая запрещающая версия делает CS `failed` с причиной; разрешающая — не снимает требований согласования, уже записанных в CS |
| STU-431 | `set-agent-policy` (project.admin, reason, idempotency) принимает документ v1 и `expectedVersion`; сохраняет неизменяемую версию с автором, временем и хэшем; конфликт версии — `POLICY_VERSION_CONFLICT`. Query: `GET /agent-policy` (текущая версия) и `GET /agent-policy/versions` (список с авторами) |
| STU-432 | Перенос: миграция 00027 превращает `settings.agentPolicy {allow, deny}` в версию 1 с правилом `{id: "legacy", subject: {agent: "*"}, allow, deny}`; при отсутствии настройки — пустая политика (действует только потолок). Поведение существующих проектов не меняется |
| STU-433 | Проверка политики (dry-run): `POST /agent-policy/explain` с черновиком документа и ситуацией (`agent`, `right`, `environment`, `path`, `zoneMode`, `zoneId`, `operationType`, `schema`, `risk`) возвращает решение, применённые правила и причину; ничего не записывает. Доступна project.admin |
| STU-434 | Агентская сессия и встроенный Agent получают отказ с причиной и показывают её в шаге задачи; модель получает безопасный текст отказа без деталей других правил. Квота за отклонённую операцию не списывается |
| STU-435 | Studio, «Политика агентов» (project.admin): список правил формами (субъект, эффект, права из потолка, условия выбором значений), правила риска и согласований, проверка политики, история версий с автором и diff, сохранение с `expectedVersion` и reason. RU/EN, клавиатура, 375 px, dirty guard, exact retry |
| STU-436 | Права сессии в Query (`/agent-sessions/{id}`) показывают потолок и безусловную часть; условная часть объясняется через проверку политики, без раскрытия правил пользователю без project.admin |
| STU-437 | Агент, человек и система используют одни команды (AGT-001): правила с `subject: agent` не влияют на людей и на `cms-system`; правила риска/согласований с `source: agent` затрагивают только CS с операциями агентов |
| STU-438 | Миграция/команды/вычисление/этап 5/публикация/Query/Studio и отрицательные сценарии покрыты тестами с ID требований; таблица решений AGT-010 проверяется табличным тестом; инъекция сбоя новых таблиц. Покрытие Go ≥ 95% с запасом; пороги не снижаются, исключения не добавляются |
| STU-439 | Локальная приёмка (§9): администратор формами задаёт правила (запрет зоны `checkout`, согласование для production, повышение риска), проверка политики объясняет решения, агент через MCP получает объяснимый отказ и разрешённую правку, подача CS агента требует согласования, смена политики переводит CS в `failed`, история версий видна |

## 4. Модель данных и команды

```json
{
  "version": 1,
  "rules": [
    { "id": "no-checkout", "subject": { "agent": "*" }, "deny": ["design.compose", "content.write"],
      "when": { "pathPrefix": ["/checkout"] } },
    { "id": "prod-review", "subject": { "agent": "*" }, "requireApproval": ["content.write"],
      "when": { "environment": ["production"] } },
    { "id": "copy", "subject": { "agent": "copy-assistant" }, "allow": ["content.read", "content.write", "design.read"] }
  ],
  "risk": [ { "id": "checkout-risk", "when": { "pathPrefix": ["/checkout"] }, "min": "high" } ],
  "approvals": [ { "id": "agent-prod", "when": { "environment": ["production"], "source": ["agent"] }, "require": { "count": 1 } } ]
}
```

Миграция 00027:

- `agent_policy_versions`: project, version (возрастает), body jsonb, hash, author,
  reason, created_at; уникальна по (project, version). Текущая — максимальная.
- Перенос `settings.agentPolicy` в версию 1 (STU-432); настройка остаётся для
  отката миграции, но не читается.
- `changesets.policy_approval` text[] — правила `requireApproval`, сработавшие
  при операциях (STU-427).

| Команда / Query | Payload | Кто |
|---|---|---|
| set-agent-policy | `policy` (v1), `expectedVersion` | project.admin, reason |
| `GET /agent-policy`, `GET /agent-policy/versions` | — | project.admin |
| `POST /agent-policy/explain` | `policy?` (черновик), `situation` | project.admin |

Старый payload `set-agent-policy {allow, deny}` принимается и сохраняется как
правило `legacy` новой версии (совместимость CLI и тестов).

## 5. Вычисление

1. Потолок: `AgentRights` ∩ права делегата ∩ снимок сессии. Право вне потолка —
   `outside_ceiling` / `delegate_lacks_right`, правила не рассматриваются.
2. Подходящие правила: субъект совпадает (`*` или имя агента), условия `when`
   без `risk` выполнены для контекста операции (STU-423).
3. AGT-010: `deny` → отказ; `allow` (или отсутствие правил `allow` у агента) →
   разрешено; `requireApproval` → разрешено с меткой CS; иначе — отказ.
4. На этапе 5 и при публикации шаги 1–3 повторяются по текущей версии политики
   для всех операций агентов CS, затем добавляются правила с `risk`.

Вычисление чистое (без сети и записи), детерминированное: правила
просматриваются по порядку, отказ называет первое подходящее `deny`.

## 6. Отказы и диагностики

| Код | Когда |
|---|---|
| `POLICY_DENIED` | Отказ политики (STU-426) |
| `POLICY_INVALID` | Документ нарушает STU-420/421 (поле и причина в `params`) |
| `POLICY_VERSION_CONFLICT` | `expectedVersion` устарела |
| `APPROVAL_ROLES_MISSING`, `APPROVAL_REQUIRED` | Подача/публикация без нужных согласований (STU-427/429) |
| Этап 5 `failed` | Текущая политика запрещает операцию агента CS (STU-430) |

## 7. Studio

Раздел «Администрирование → Политика агентов»: таблица правил с эффектом,
субъектом, правами и условиями; форма правила с выбором прав из потолка и
значений условий из проекта (окружения, зоны, схемы, типы операций); правила
риска и согласований; «Проверить политику» — форма ситуации и ответ с
решением и правилами; история версий с автором, причиной и diff.

Панель агента показывает отказ в шаге задачи: «Запрещено политикой: правило
no-checkout, путь /checkout» — без текста других правил. Карточка CS
показывает требование согласования по политике.

## 9. Проверки и локальная приёмка

| Область | Обязательные сценарии |
|---|---|
| Документ | Лимиты, уникальность id, неизвестные поля, значения условий, перенос legacy |
| Вычисление | Таблица AGT-010 (deny/allow/requireApproval/нет правил), каждое условие отдельно, И/ИЛИ, `environment` для нескольких целей, потолок |
| Операции | Отказ пакета с индексом, причина, событие безопасности, квота не списана, люди не затронуты |
| Этап 5 | Смена политики после правки → `failed`; разрешающая версия не снимает согласование; risk-правила |
| Согласования | `requireApproval` требует человека-не-делегата; правила approvals по окружению/источнику; роли |
| Версии | Конфликт `expectedVersion`, история, idempotent retry |
| Studio | Формы, проверка политики, история, RU/EN/375 px, dirty guard |
| Сбои | Инъекция сбоя таблицы версий, чтения политики при операции и на этапе 5 |
| Регрессия | Сессии, Missing Capability, выполнение `cms-system`, существующая allow/deny-политика |

Локальная приёмка: администратор Bob создаёт правила формами (запрет
`design.compose` для `/checkout`, `requireApproval` для production, риск high
для `/checkout`), проверяет их «проверкой политики»; Alice запускает внешнюю
MCP-сессию: правка `/checkout` отклонена с причиной, правка `/store`
разрешена; подача CS агента требует согласования Bob; новая версия политики
переводит CS в `failed`; история версий показывает обе версии. RU/EN, 375 px;
отчёт `docs/studio-agent-policy-acceptance.md`.

## 10. Связь с другими частями

Правила не меняют потолок агента и существующие проверки зон, IR и manifest;
они добавляются к ним. Правила для людей (`subject: role`) из архитектурного
§2.3 остаются следующим пакетом укрепления M6 вместе с секционированием
`security_events`.

## 11. Принятые решения — 2026-10-21

Пользователь одобрил спецификацию и принял рекомендации по всем вопросам.

1. **Субъекты.** Только агенты (`agent: "*"` и по имени); правила для ролей
   людей — отдельный пакет M6 (STU-420, STU-437).
2. **Расширение прав.** Политика только сужает права в пределах потолка;
   публикация, согласование и управление зонами агенту недоступны (§1, STU-422).
3. **Формат.** JSON документа и редактор формами в Studio (STU-420, STU-435).
4. **Несколько целей CS.** `deny` — если условие окружения выполнено для любой
   цели; `allow`/`requireApproval` — только для всех (STU-423).
5. **Смена политики.** Этап 5 и публикация используют текущую версию; CS
   получает `failed`, записанные операции не откатываются (STU-430).
6. **Нет `allow`.** Без подходящего `allow` у агента действуют права потолка (STU-422).
