# Кэш Delivery API на origin и лимиты запросов

Статус: **одобрена пользователем 2026-10-27; решения §11 приняты; реализована в ветке `feature/delivery-cache-limits`, см. [приёмку](delivery-cache-limits-acceptance.md)**.
Дата: 2026-10-27. Требования: STU-520…539 (STU-500…519 заняты пакетом
[безопасности MVP](security-hardening.md)).
Основа: `origin/dev` на `0abf615` (после [PR #91](https://github.com/QahNaaRlN/project-17/pull/91)).
Второй пакет M6 в утверждённом порядке: безопасность → **кэш Delivery** →
нагрузка → этапы 10–11 → наблюдаемость → ADR → набор для эксперимента.
Пакет — предпосылка нагрузочных тестов: NFR-002 (p95 < 80 мс на тёплом кэше
Redis) нельзя измерить, пока кэша нет.

## 1. Проблема и границы

Сверка 2026-10-27 показала:

| Требование | Состояние |
|---|---|
| Кэш ответов на origin, 07 §4 (`dlv:…`, `tag:…`) | Нет: каждый published-запрос читает PostgreSQL; Redis в коде, compose и CI отсутствует |
| API-033 `ETag`, `Cache-Control`, `Surrogate-Key` | Выполнено (`httpapi/delivery.go`), `304` на `If-None-Match` |
| Инвалидация после публикации и отката, PUB-021 | Только CDN: задача `cdn_purge` в outbox публикации (`publishing.enqueuePurge`) |
| Лимиты 08 §7 | Нет ни одного; есть только квота операций агентской сессии и месячный лимит токенов агента |
| `429 RATE_LIMITED` с `Retry-After` (08 §6) | Код описан, нигде не выдаётся |
| ST-001: потеря Redis не ломает корректность | Не к чему применять |

Границы пакета:

- кэшируются только published-ответы Delivery API: `/page`, `/document/{id}`,
  `/routes`, `/entity/{id}`, `/asset/{id}`. Черновые ответы (preview-токен) и
  `/asset/{id}/image` остаются `no-store` и в кэш не попадают;
- лимиты — все строки 08 §7: Studio, сервисные токены, агентские сессии, ключи доставки;
- presence остаётся на PostgreSQL ([решение](studio-realtime.md)), идемпотентность — тоже (07 §4);
- измерение NFR-001…003 — следующий пакет (нагрузочные тесты); здесь — корректность,
  отказоустойчивость и микробенчмарк попадания.

Вне пакета: CDN как продукт, лимиты на уровне балансировщика, WAF,
настройка лимитов по проектам в Studio.

## 2. Требования

### Redis и конфигурация

| ID | Требование |
|---|---|
| STU-520 | Сервер подключается к Redis 7 по `CMS_REDIS_URL` (решение §11.1). Пустое значение — режим без Redis: кэша нет, лимиты считаются в памяти процесса (решение §11.4). Неверный URL — ошибка конфигурации при старте |
| STU-521 | `deploy/compose/docker-compose.yml` получает сервис `redis:7` без персистентности (12 §5.2), стенд сценария §2 в CI — Redis как `services`; тесты Go — контейнер Redis через testcontainers |
| STU-522 | Готовность: `/readyz` не зависит от Redis (ST-001): недоступный Redis ухудшает задержку, но не доступность. Состояние Redis пишется в журнал при смене (доступен ↔ недоступен), не на каждый запрос |

### Кэш ответов

| ID | Требование |
|---|---|
| STU-523 | Ключ записи — `dlv:{project}:{env}:{kind}:{key}:{locale}` (07 §4): `kind` — `page`, `document`, `routes`, `entity`, `asset`; `key` — нормализованный путь (как в сопоставлении маршрутов) или ID. Значение — тело ответа, `ETag`, `Surrogate-Key` и версии тегов (STU-525). TTL — 1 ч |
| STU-524 | Попадание отдаёт те же байты, `ETag`, `Cache-Control` и `Surrogate-Key`, что и ответ из PostgreSQL; совпавший `If-None-Match` — `304` без тела. Ошибки (`4xx`, `5xx`) не кэшируются. Заголовок `X-CMS-Cache: hit|miss|bypass` — для тестов и нагрузки |
| STU-525 | Корректность при гонке с публикацией: каждый `Surrogate-Key` ответа — тег с версией `tagv:{project}:{env}:{object}` (решение §11.2). Промах читает версии тегов **до** чтения БД и сохраняет их в записи; попадание сверяет сохранённые версии с текущими одним `MGET` и при расхождении считается промахом. Так ответ, прочитанный до публикации и записанный после инвалидации, не будет отдан |
| STU-526 | Инвалидация: публикация, откат и `promote` увеличивают версии тех же тегов, что идут в `cdn_purge` (объекты, `routes`, `manifest`). Увеличение — в задаче outbox `delivery_cache_invalidate`, поставленной в транзакции публикации рядом с `cdn_purge`; задача выполняется раньше purge CDN, чтобы CDN не перезапросил старый ответ из Redis (решение §11.3) |
| STU-527 | Ключи записей и тегов включают проект и окружение: инвалидация одного окружения не задевает другие, `promote` инвалидирует только целевое окружение. Новых тегов сверх ключей `cdn_purge` (объекты, `routes`, `manifest`) не вводится |
| STU-528 | Ошибка Redis при чтении — промах с чтением из PostgreSQL; при записи — ответ отдаётся без записи; при инвалидации — задача повторяется River. Ни одна ошибка Redis не превращается в `5xx` клиента |
| STU-529 | Размер записи ограничен 1 МиБ: больший ответ отдаётся без кэша (`X-CMS-Cache: bypass`). Повторное заполнение одного ключа параллельными промахами допускается (без распределённых блокировок) |

### Лимиты запросов

| ID | Требование |
|---|---|
| STU-530 | Счётчик — фиксированное окно 1 с, ключ `rl:{subject}:{class}:{window}` (07 §4, решение §11.5), `INCR` + `EXPIRE` одним конвейером. `subject` — ID ключа доставки, токена, сессии агента или актора-человека |
| STU-531 | Лимиты по умолчанию (08 §7): человек — 50 команд/с и 200 запросов/с ко всему `/api/v1`; сервисный токен — 20 команд/с; агентская сессия — 5 команд/с; ключ доставки — 500 запросов/с; preview-токен — 200 запросов/с на субъект токена. Значения задаются переменными `CMS_RATE_*` на установку (решение §11.6) |
| STU-532 | Превышение — `429 RATE_LIMITED` (problem+json) с `Retry-After` в секундах до конца окна и `Cache-Control: no-store`; отказ агенту и сервису попадает в журнал безопасности как `access.denied` (как отказы `429` агентам сейчас), отказ ключу доставки — не пишется (объём) |
| STU-533 | Недоступный Redis — лимит не применяется (fail open) и это пишется в журнал по STU-522; квоты агентов в PostgreSQL продолжают действовать (решение §11.4) |
| STU-534 | Лимит проверяется после аутентификации и до чтения БД и Command Bus; `Access` ключа доставки получает ID ключа; `304` и попадания кэша тоже считаются |
| STU-535 | `/healthz`, `/readyz` и `/auth/*` лимитами пакета не покрываются (вход защищён IdP) |

### Проверки и документация

| ID | Требование |
|---|---|
| STU-536 | Go: попадание и промах для каждого `kind`; байтовое совпадение с ответом без кэша; `304` из кэша; публикация, откат и `promote` делают ответ свежим; гонка «чтение до публикации — запись после инвалидации» не отдаёт старое; черновой режим не пишет в кэш; отказ Redis на чтении, записи и инвалидации; изоляция проектов и окружений в ключах |
| STU-537 | Go: лимиты каждого класса, `Retry-After`, сброс окна, отдельные счётчики разных субъектов, fail open без Redis, режим без `CMS_REDIS_URL` (лимиты в памяти) |
| STU-538 | Микробенчмарк `BenchmarkDeliveryPageCacheHit` (httptest + Redis контейнер) в отчёте приёмки — ориентир для NFR-002 до нагрузочного пакета; порог не применяется |
| STU-539 | Документация: эта спецификация, 07 §4 (реализация), 08 §5.2.1 и §7 (кэш, лимиты, `X-CMS-Cache`), 12 §5 (Redis в compose), `docs/testing.md`, строка плана MVP, отчёт приёмки |

## 3. Порядок реализации после одобрения

1. Конфигурация и клиент Redis, compose, CI, режим без Redis (STU-520…522).
2. Кэш published-ответов с версиями тегов и инвалидация в outbox (STU-523…529).
3. Лимиты и `429` (STU-530…535).
4. Тесты, микробенчмарк, документация, приёмка (STU-536…539).

## 4. Критерии приёмки пакета

- Повторный published-запрос отдаётся из Redis с тем же телом и `ETag`;
  после публикации или отката следующий запрос видит новую версию.
- Остановка Redis на работающем стенде не даёт ни одного `5xx` и не меняет ответы.
- Превышение лимита даёт `429` с `Retry-After`; лимиты разных ключей независимы.
- Сценарий §2 проходит со включённым Redis; пороги покрытия и проверки CI не ослаблены.

## 11. Принятые решения — 2026-10-27

1. **Клиент Redis.** `github.com/redis/go-redis/v9` (STU-520).
2. **Защита от гонки с публикацией.** Версии тегов: промах читает версии до
   чтения БД, попадание сверяет их одним `MGET` (STU-525).
3. **Где инвалидировать.** Задача outbox `delivery_cache_invalidate`, выполняется
   раньше `cdn_purge` (STU-526).
4. **Поведение без Redis.** Кэш выключен; лимиты при сбое Redis не применяются
   (fail open), без `CMS_REDIS_URL` — считаются в памяти процесса; квоты агентов в
   PostgreSQL действуют всегда (STU-520, 528, 533).
5. **Алгоритм лимита.** Фиксированное окно 1 с, `INCR` + `EXPIRE` (STU-530).
6. **Где настраиваются лимиты.** Переменные `CMS_RATE_*` на установку с
   умолчаниями 08 §7; по проектам — после MVP (STU-531).
