## 1. Проблема и границы

Pipeline публикации ([06 §5.1](spec/06-changes-publishing.md#51-этапы)) требует:

- этап 10 — скриншоты 375 / 768 / 1440 px в сравнении с опубликованной версией; не блокирует, результат прикладывается к ревью; риск ≥ medium;
- этап 11 — Lighthouse (performance, accessibility) по порогам проекта; риск `high`.

PUB-005: согласующий видит скриншоты. Сейчас этапы 8–9 ([STU-480…499](pipeline-render-checks.md))
рендерят страницы черновика в `apps/check-runner`, но ничего не сохраняют:
исполнитель не пишет HTML и скриншоты (STU-498), а у проверок нет хранилища
бинарных артефактов, хотя колонка `checks.artifacts` и раскладка
`projects/{projectId}/checks/{changesetId}/{checkId}/{artifact}`
([07 §5](spec/07-storage.md#5-объектное-хранилище)) предусмотрены.

Пакет добавляет:

- хранилище артефактов проверок в объектном хранилище и выдачу их Studio;
- этап 10 `visual` на том же исполнителе: черновик против опубликованной версии, три ширины, разница по пикселям;
- этап 11 `lighthouse` на том же исполнителе с порогами в настройках проекта;
- результаты обоих этапов в ревью Studio;
- срок хранения артефактов.

Вне пакета: этап 12 (внешние проверки приложения); сравнение с эталонами,
утверждёнными вручную (Percy/Chromatic-подобный поток); Lighthouse на
production-окружении по расписанию; масштабирование исполнителей.

## 3. Требования

| ID | Требование |
|---|---|
| STU-570 | `submit-changeset` для CS с риском ≥ medium вместе с `preview`/`axe` ставит в очередь `visual` (этап 10) по каждому окружению с `appUrl`, `blocking=false`; для риска `high` — ещё `lighthouse` (этап 11) с `blocking` по порогам проекта (STU-581). Риск ниже порога этапа — `skipped`, причина `RISK_LOW` |
| STU-571 | Неблокирующие проверки не держат CS в `checking`: переход `checking → in_review/approved` ждёт только блокирующие (STU-483); `visual` может завершиться позже, Studio показывает его статус. Согласование и публикация `visual` не ждут |
| STU-572 | Хранилище артефактов: ключи `projects/{projectId}/checks/{changesetId}/{checkId}/{name}`, `name` — `[a-z0-9._-]{1,128}`. Без настроенного объектного хранилища `visual` — `skipped`, причина `CHECK_ARTIFACTS_UNAVAILABLE`; `lighthouse` выполняется, но без HTML-отчёта |

| STU-575 | Чтение: `GET /api/v1/changesets/{id}/checks/{checkId}/artifacts/{name}` с правом чтения CS (как Review API); ответ — поток из хранилища с `Content-Type`, `Cache-Control: private, max-age=3600`, `X-Content-Type-Options: nosniff`; HTML-отчёт — с `Content-Security-Policy: sandbox`. | STU-576 | Исполнитель, этап 10: для каждой затронутой страницы (тот же список и лимит 50, что этап 8) и ширины 375, 768, 1440 px снимает два скриншота всей страницы — опубликованная версия `{appUrl}{path}` и черновик через preview-токен — с отключёнными анимациями, после загрузки шрифтов и `networkidle`, высота не больше 10 000 px |
| STU-577 | Сравнение: попиксельно (pixelmatch, порог цвета 0,1, без сглаживания) в пределах общей высоты; разная высота считается изменением полосы разницы. Изображения без изменений (`changedRatio = 0`) не загружаются, кроме `after` |
| STU-578 | Страница без опубликованной версии в окружении (новая или опубликованная маршрут которой ещё не отдаёт 200) — `baseline: "none"`, только `after`. ## 4. Поток

```
submit ─▶ ir, policy ─▶ checking
            queued: preview, axe (блокирующие), visual (неблокирующий),
                    lighthouse (risk = high; блокирует по порогам)
            │
 check-runner: claim-check
   visual:     published {appUrl}{path} ┐
               draft /api/cms/preview   ┴─▶ pixelmatch ─▶ PUT artifacts ─▶ complete-check
   lighthouse: draft /api/cms/preview ─▶ Lighthouse ─▶ PUT report ─▶ complete-check
            │
 блокирующие пройдены ─▶ in_review | approved   (visual может ещё идти)
```

## 5. Схемы `details`

`visual`:

```json
{ "pages": [{ "objectId": "…", "path": "/store", "widths": [
  { "width": 375, "baseline": "published", "changedRatio": 0.042,
    "heights": { "before": 2210, "after": 2390 },
    "artifacts": { "before": "store-375-before.png", "after": "store-375-after.png",
                   "diff": "store-375-diff.png" } },
  { "width": 1440, "baseline": "none", "artifacts": { "after": "store-1440-after.png" } }
] }], "truncated": false }
```

`lighthouse`:

```json
{ "pages": [{ "objectId": "…", "path": "/store",
  "scores": { "performance": 0.71, "accessibility": 0.96 },
  "report": "store-lighthouse.html" }],
  "thresholds": { "performance": { "min": 0.5, "blocking": false },
                  "accessibility": { "min": 0.9, "blocking": true } },
  "truncated": false }
```

Новые причины: `CHECK_ARTIFACTS_UNAVAILABLE`, `CHECK_ARTIFACT_MISSING`,
`CHECK_ARTIFACT_EXPIRED`.

## 6. Исполнитель

- Тот же процесс и образ `apps/check-runner`; новые зависимости — `pixelmatch`, `pngjs`, `lighthouse`. Lighthouse подключается к Chromium исполнителя по порту отладки; отдельный браузер не запускается.
- Опубликованная версия снимается без токена и cookie, в отдельном контексте браузера.
- Стабильность снимков: `reducedMotion: "reduce"`, `animations: "disabled"`, ожидание `document.fonts.ready`, фиксированный `deviceScaleFactor: 1`, часовой пояс и локаль стенда.
- Файлы пишутся в CMS по мере съёмки; локально исполнитель их не хранит.

## 7. Отступления и связи

- 06 §5.1 «в сравнении с опубликованной версией»: опубликованная версия снимается
  в момент проверки с работающего приложения, эталоны не хранятся (решение §11.2).
  Изменение кода приложения между публикацией и проверкой попадёт в разницу; это
  видно по страницам, которых нет в CS.
- 06 §5.1 «по порогам проекта»: пороги задаются `set-check-policy`; без настройки
  действуют умолчания STU-581.
- STU-498 этапов 8–9 («исполнитель не сохраняет скриншоты») сохраняется для этапов
  8–9; скриншоты сохраняет только этап 10.

### Реализация (отступления)

- **Lighthouse запускает свой Chromium** на каждую проверку (по порту отладки), а не
  подключается к браузеру исполнителя (§6): при параллельности 2–4 замеры
  производительности не делят один браузер.
- **HTML-отчёт Lighthouse только скачивается** (`Content-Disposition: attachment`,
  `CSP: sandbox`): отчёт рисует себя скриптами, а показывать его в песочнице без
  скриптов бессмысленно. Баллы и пороги видны в ревью Studio (STU-575, 584).
- **Стенд §2 хранит артефакты в каталоге**, а не в MinIO: опубликованных образов MinIO
  нет, сборка из исходников заметно удлиняет job. Хранилище-каталог есть только в
  e2e-сборке CMS (`CMS_E2E_ARTIFACTS_DIR`); продукт хранит артефакты только в S3.
- **В ревью у проверки есть `id`**: по нему Studio строит адрес артефакта.
- **Отказ от CS** (`abandon`) возможен только из `open`, где открытых проверок уже нет,
  поэтому отдельно пропускать проверки при отказе не нужно; при публикации
  незавершённый `visual` получает `skipped` с причиной `CHANGESET_MERGED`.

## 8. Порядок реализации после одобрения

1. Сервер: этапы `visual`/`lighthouse`, неблокирующий асинхронный этап, артефакты (загрузка, сверка, чтение), продление аренды, пороги и `set-check-policy`, срок хранения (STU-570…575, 581…583, 585, 586).
2. Исполнитель: этап 10 и этап 11 с тестами против фикстурного приложения (STU-576…580).
3. Studio: ревью сравнения и баллов (STU-584).
4. Стенд с MinIO, сценарий §2 и тест риска `high` (STU-587, 588).
5. Документация и отчёт (STU-589).

## 9. Критерии приёмки пакета

- В сценарии §2 согласующий видит для изменённой страницы «до / после / разница» на трёх ширинах.
- CS с риском `high` и баллом accessibility ниже порога — `failed`; ниже порога performance по умолчанию — `warning`, согласование доступно.
- Незавершённый `visual` не задерживает согласование и публикацию.
- Артефакт недоступен без права чтения CS; после срока хранения — `410`.
- Существующие проверки CI, пороги покрытия и E2E не ослаблены; job сценария остаётся обязательным и укладывается в прежний таймаут.

## 11. Принятые решения — 2026-10-28

Пользователь принял рекомендации 1–6:
- хранилище — S3/MinIO (1а);
- опубликованная версия снимается в момент проверки (2а);
- `visual` предупреждает только при ошибке съёмки (3а);
- пороги Lighthouse по умолчанию — как в п. 4;
- срок хранения — 90 дней;
- Lighthouse — до 10 страниц.

Варианты и обоснования:

1. **Где хранить скриншоты и отчёты.**
   - (а) Объектное хранилище S3/MinIO по раскладке 07 §5, файлы идут через CMS; стенды поднимают MinIO.
   - (б) PostgreSQL (`bytea`): без новой зависимости, но десятки мегабайт на проверку раздувают базу и резервные копии.
   - (в) Не хранить файлы, только доли изменённых пикселей: согласующий не видит скриншотов, PUB-005 не выполняется.

   Рекомендация — (а): раскладка уже заложена в 07 §5, хранилище уже используется
   для файлов контента (STU-572, 573, 575).
2. **С чем сравнивать.**
   - (а) Снимать опубликованную версию с приложения в момент проверки.
   - (б) Хранить эталоны, снятые при каждой публикации.

   Рекомендация — (а): эталоны не устаревают и не требуют съёмки при публикации,
   отката и переноса. Цена — вдвое больше снимков на проверку (STU-576, §7).
3. **Когда `visual` предупреждает.**
   - (а) `warning` только при ошибке съёмки; изменения показываются, но не считаются проблемой.
   - (б) `warning` при любом изменении.

   Рекомендация — (а): правка в CS почти всегда меняет пиксели, предупреждение на
   каждую подачу перестанут читать (STU-578).
4. **Пороги Lighthouse по умолчанию.**
   - Accessibility ≥ 0,9 — блокирует.
   - Performance ≥ 0,5 — только предупреждает.

   Балл performance на общих машинах заметно плавает (это видно по нагрузочным
   прогонам), поэтому блокировать по нему без настройки проекта рискованно. Проект
   может сделать его блокирующим (STU-581, 582).
5. **Срок хранения.** 90 дней после финального состояния CS или замены проверки
   новым содержимым; записи проверок остаются (STU-583).
6. **Объём Lighthouse.** До 10 страниц на проверку, остальные — `skipped` со
   списком; только риск `high` по 06 §5.1 (STU-579).
