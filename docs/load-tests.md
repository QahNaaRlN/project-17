# Нагрузочные тесты NFR-001…007

Статус: **одобрена пользователем 2026-10-27; решения §11 приняты; реализована и слита в dev в PR #96 (2026-10-28), см. [отчёт](load-test-report.md)**.
Дата: 2026-10-27. Требования: STU-540…559 (STU-520…539 заняты пакетом
[кэша Delivery и лимитов](delivery-cache-limits.md)).
Основа: `origin/dev` на `5d42462` (после [PR #94](https://github.com/QahNaaRlN/project-17/pull/94)).
Третий пакет M6 в утверждённом порядке: безопасность → кэш Delivery → **нагрузка** →
этапы 10–11 → наблюдаемость → ADR → набор для эксперимента.
Цель — критерий готовности MVP 2 ([план §3](spec/14-mvp-plan.md#3-критерии-готовности-mvp)):
нагрузочные тесты подтверждают NFR-001…007 при профиле [01 §5](spec/01-requirements.md#5-профиль-нагрузки-mvp).

## 1. Проблема и границы

Сверка 2026-10-27:

| NFR | Цель | Что есть сейчас |
|---|---|---|
| NFR-001 Delivery, попадание в CDN | p95 < 50 мс | CDN в MVP нет; `Cache-Control` и `Surrogate-Key` отдаются, purge — вебхуком |
| NFR-002 Delivery, тёплый кэш Redis | p95 < 80 мс | Кэш реализован (PR #93); микробенчмарк 6,4 мс без нагрузки |
| NFR-003 Delivery, промах кэша | p95 < 250 мс | Не измерялось |
| NFR-004 `apply-operations` ≤ 20 операций | p95 < 300 мс | Не измерялось |
| NFR-005 правка в Studio → перерисовка preview | p95 < 400 мс | Сценарий §2 измеряет `document.patch` без нагрузки: p95 133–234 мс, гейт 800 мс |
| NFR-006 публикация CS до 50 объектов | < 30 с | Не измерялось |
| NFR-007 rollback | < 5 с | Сценарий §2: откат production 25–27 мс на одном объекте, без нагрузки |

Каталога `perf/`, генератора данных и инструмента нагрузки нет; `docs/testing.md`
называет k6 и запуск «перед релизом».

Профиль 01 §5: до 20 проектов; до 100 000 сущностей и 10 000 документов IR на
проект; до 50 одновременных пользователей Studio на проект; до 200 RPS к Delivery
API на origin; до 500 публикаций в день на проект.

Вне пакета: доступность NFR-008/009 (месячные показатели эксплуатации),
RPO/RTO NFR-010, выбор CDN-провайдера, нагрузка на Studio-BFF как на отдельный
сервис, измерения в production.

## 2. Требования

| STU-542 | Генератор данных (`apps/server/cmd/loadseed`, решение §11.4): детерминированный по зерну, загрузка через `COPY`. Проекты, окружения, активный manifest со схемами, сущности, документы IR (размеры 20–300 узлов по распределению, предел NFR-012 не превышается), маршруты, опубликованные указатели, ключи доставки и токены виртуальных пользователей (решение §11.6). ### Реализация (отступления)

- Стенд — `perf/run.mjs` (`pnpm load`): PostgreSQL, Redis, nginx и k6 в контейнерах,
  `cms serve` — бинарник с тегом `e2e` вместо образа `apps/server/Dockerfile`: его же
  запускает стенд сценария §2 для NFR-005 (STU-541).
- NFR-005 измеряется полным сценарием §2 на той же базе под фоновым профилем k6
  (`LOAD_MODE=background`); порог задаёт `E2E_NFR005_MAX_MS=400` (STU-549).
- Workflow `Load` дополнительно запускается меткой `load` на PR — чтобы проверить
  ветку до слияния (STU-552).
- Найденные причины в коде исправлены в пакете (STU-554), см. [отчёт](load-test-report.md).

## 11. Принятые решения — 2026-10-27

1. **Инструмент нагрузки.** k6, образ `grafana/k6` с фиксированной версией (STU-540).
2. **Где и когда запускать.** Отдельный workflow `Load`: вручную и еженедельно на
   GitHub-hosted runner; не обязательная проверка PR (STU-552).
3. **NFR-001 без CDN.** Эталонный кэширующий прокси nginx `proxy_cache` перед origin
   на стенде (STU-541, 545).
4. **Объём данных.** Полный профиль: 20 проектов × 100 000 сущностей × 10 000
   документов, загрузка через `COPY` (STU-542).
5. **NFR-005.** Измерение сценария §2 под фоновой нагрузкой, строгий порог 400 мс (STU-549).
6. **Пользователи Studio в нагрузке.** Сервисные токены с правами редактора, по одному
   на виртуального пользователя (STU-542, 546).
7. **Когда критерий 2 выполнен.** После трёх зелёных прогонов `Load` подряд на `dev` (STU-553).
