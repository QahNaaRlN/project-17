# Тестирование

Обязательные правила тестирования проекта. Отступление от правила оформляется в описании PR с обоснованием и согласуется с ревьюером.

## 1. Принципы

1. **Тест — часть изменения.** PR без тестов на новое или изменённое поведение не принимается. Исключения: документация, конфигурация без логики.
2. **Требование → тест.** Каждое требование спецификации (`IR-012`, `PUB-020` …), которое реализует PR, покрыто хотя бы одним тестом или фикстурой; ID требования указан в названии теста, в `description` фикстуры или в комментарии рядом с тестом.
3. **Сначала падающий тест для бага.** Исправление ошибки начинается с теста, который воспроизводит её и падает; затем исправление.
4. **Проверяется контракт, а не реализация.** Для диагностик проверяются `code`, `pointer`, `nodeId`, `params` — их используют Studio, агент и сервер. Текст сообщения проверяется только там, где он сам является контрактом (например, перевод сообщений схемы).
5. **Детерминированность.** Тест даёт одинаковый результат при каждом запуске: без реального времени, сети, порядка обхода словарей и неуправляемой случайности. Случайные данные — только через fast-check: при падении он печатает `seed` и минимальный контрпример, по которым падение воспроизводится.
6. **Тесты не отключаются.** Запрещено пропускать, удалять или ослаблять тест, чтобы получить зелёный CI. `.only` в CI приводит к ошибке (поведение Vitest при `CI=true`).

## 2. Уровни тестов

| Уровень | Что проверяет | Инструменты | Где | Когда запускается |
|---|---|---|---|---|
| Модульные | Функции и модули изолированно | Vitest; `go test` | `packages/*/test`, `*_test.go` | каждый PR |
| Conformance | Одинаковое поведение реализаций на TS и Go на общих данных | Фикстуры JSON | `packages/ir/fixtures` | каждый PR |
| На случайных данных (property-based) | Свойства, верные для любых входов | fast-check; `go test -fuzz`, `testing/quick` | рядом с модульными | каждый PR |
| Интеграционные | Сервер с настоящими PostgreSQL, Redis, MinIO | testcontainers | `apps/server/...` | каждый PR (после появления сервера) |
| Контрактные | OpenAPI ↔ обработчики; MCP-инструменты ↔ команды | генерация клиентов, схемы | `apps/server`, `packages/mcp` | каждый PR (после появления API) |
| Сквозные (E2E) | Сценарий MVP ([14-mvp-plan.md §2](spec/14-mvp-plan.md#2-сквозной-сценарий-приёмки)) | Playwright | `e2e/` | каждый PR в `dev`, `main` |
| Нагрузочные | NFR-001…007 | k6 | `perf/` | перед релизом |
| Мутационные | Качество самих тестов | Stryker; `go-mutesting` | пакеты | раз в неделю, перед релизом, вручную |

## 3. Правила по видам тестов

### 3.1. Модульные

- Название теста — что проверяется, на русском: `"удаление любой ссылки на ребёнка делает его сиротой"`.
- Один тест — одно поведение; структура «подготовка → действие → проверка».
- Табличные тесты (`it.each`, table-driven в Go) — для однотипных случаев.
- Граничные значения проверяются с обеих сторон границы: допустимое `N` и недопустимое `N + 1`.

### 3.2. Conformance-фикстуры

Формат и правила — [packages/ir/fixtures/README.md](../packages/ir/fixtures/README.md). Каждое новое структурное правило IR добавляется вместе с фикстурами в `valid/` и `invalid/`. Фикстуры — данные, а не код: одни и те же файлы читают тесты на TypeScript и Go.

### 3.3. На случайных данных

Обязательны для чистых функций с широким пространством входов:

- валидаторы и парсеры — **не бросают исключений** на любом входе;
- взаимно обратные преобразования — **возвращают исходное значение** (`normalize(toNested(doc)) == doc`);
- операции над документом — **операция и обратная операция дают исходный документ**;
- rebase — **независимые операции коммутируют**;
- инварианты — **намеренное нарушение обнаруживается** (удалённая ссылка → сирота).

Генераторы данных размещаются в тесте или в общем модуле `test/arbitraries.ts` пакета, если используются несколькими тестами.

### 3.4. Интеграционные

- Каждый тест работает в собственной схеме или транзакции БД и не зависит от порядка запуска.
- Внешние сервисы, которые нельзя поднять в контейнере, подменяются на границе модуля (интерфейс в Go, адаптер в TS), а не внутри бизнес-логики.

### 3.5. Сквозные

- Только через публичные интерфейсы: Studio, Delivery API, MCP.
- Ожидание — по событию или состоянию (`expect(...).toBeVisible()`), не `sleep`.

## 4. Метрики и пороги

| Пакет | Покрытие: инструкции / ветвления / функции / строки | Мутационная оценка: минимум |
|---|---|---|
| `packages/ir` | 95 / 85 / 95 / 95 % | 80 % |
| Новые пакеты по умолчанию | 90 / 80 / 90 / 90 % | 70 % |

- Пороги покрытия проверяются в CI при каждом `pnpm test`; падение ниже порога — красный CI.
- Пороги задаются в `vitest.config.ts` пакета (`coverage.thresholds`) и в `stryker.config.json` (`thresholds.break`).
- Порог можно повысить в любом PR. Понизить — только с обоснованием в описании PR.
- Сгенерированный код (`src/generated/**`) и реэкспорты (`src/index.ts`) не учитываются.

Покрытие показывает, какой код выполнялся, но не то, что результат проверялся. Поэтому решающая метрика качества тестов — мутационная оценка: Stryker вносит в код мелкие ошибки (меняет условия, операторы, константы) и проверяет, что тесты их замечают.

### 4.1. Разбор выживших мутантов

Отчёт: `packages/<пакет>/reports/mutation/index.html` (локально) или артефакт workflow `Mutation` (в CI). Для каждого выжившего мутанта решается одно из трёх:

1. **Пробел в тестах** — добавить тест.
2. **Эквивалентный мутант** (поведение не меняется, например защитная проверка, дублирующая схему) — оставить; при необходимости пометить комментарием `// Stryker disable next-line <мутатор>: <причина>`.
3. **Лишний код** — удалить.

Изменение текста сообщения (мутатор `StringLiteral`) пробелом не считается, если текст не является контрактом (§1, п. 4).

## 5. Запуск

```bash
pnpm test                                   # все пакеты, с покрытием
pnpm --filter @cms/ir test                  # один пакет
pnpm --filter @cms/ir exec vitest           # режим наблюдения
pnpm --filter @cms/ir test:mutation         # мутационное тестирование (несколько минут)
```

## 6. CI

| Workflow | Триггер | Что делает |
|---|---|---|
| `CI` | каждый PR, пуш в `main` и `dev` | формат, линтер, типы, тесты с порогами покрытия, сборка, актуальность сгенерированных файлов |
| `Mutation` | еженедельно (понедельник), вручную | Stryker во всех пакетах со скриптом `test:mutation`; HTML-отчёт — артефакт запуска; падение при оценке ниже порога |

## 7. Чек-лист ревьюера

- [ ] Новое и изменённое поведение покрыто тестами; ID требований спецификации указаны.
- [ ] Для бага есть тест, падающий без исправления.
- [ ] Для изменения формата IR добавлены фикстуры.
- [ ] Тесты проверяют контракт (коды, указатели, параметры), а не внутреннее устройство.
- [ ] Нет пропущенных, ослабленных или недетерминированных тестов.
- [ ] Пороги покрытия не понижены без обоснования.
