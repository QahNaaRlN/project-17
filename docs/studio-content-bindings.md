Пакет STU-203…218 продолжает [создание работ с контентом](studio-content-work.md),

## 1. Результат и границы

Редактор выбирает основную сущность страницы, связывает её поля со свойствами
блоков, видит реальные значения на холсте, сохраняет и публикует результат
через существующее согласование. Приёмочный путь: создать Article и обложку
→ подключить Article к странице → связать Heading.text, Image.src и Image.alt
→ проверить RU/EN preview → согласовать другим человеком → опубликовать.
Ручной ввод ID, JSON страницы и выражений для этого пути не требуется.

В пакет входят источник `content.resolve.by = entity`, выбор прямых полей
и полей вложенных объектов из схемы, минимальное разрешение `$content`
в Delivery/SDK/React и обновление preview. Выбор сущности работает в уже
открытом собственном standard CS страницы; допускаются сущность/ассет из
этого же CS или доступный head, с отдельной проверкой публикации в окружение.
Новый мастер создания сущности не вводится: используется пакет PR #56.

Не входят конструкторы `$data`, Repeat, `$item`/`$props`, события и действия,
форматтеры/шаблоны выражений, fallback-конструктор, разыменование entity-reference,
индексация списков, динамические маршруты `routeParam`, конструктор схем,
locale fallback/upcast, component.extract, Figma и production-развёртывание.
Существующие сложные привязки и routeParam-декларации сохраняются и отображаются
только для чтения в новых контролах, без принудительного преобразования.
Это первый законченный пакет привязок, а не закрытие всего M4 или IR-044.

## 2. Проверенная исходная точка до реализации

- IR уже содержит `content: {schema, resolve: {by: "entity", entityId}}`
  и `by: "routeParam"` ([02-ir.md](spec/02-ir.md), IR-015).
  Новая форма IR и миграция хранения не требуются.
- В каталоге `ops` есть `node.setBinding` с `design.compose`, атомарным
  применением, inverse и взаимоисключением `props`/`bindings`. Операции
  изменения `document.content` пока нет. Structure умеет node binding,
  но не заменяет отсутствующую серверную операцию декларации.
- В `fields.ts` обычная привязка показывается как read-only; существующий
  scalar/localContent ввод сохраняется. Серверный bindingdoc валидирует
  пути по схеме и совместимость типов.
- `$content` есть в `BindingScope`; `readPath` читает только собственные
  свойства. Автоматической загрузки основной сущности и её локализации
  в текущем React loader нет. `page.data` сегодня не доказывает разрешение
  primary content: loader передаёт его как `$data`.
- Общая спецификация Delivery уже предусматривает `data.content`
  ([08-api.md §5](spec/08-api.md#5-delivery-api)); этот пакет реализует
  ограниченную часть данного контракта, а не весь описанный API.
- `Image.src` имеет тип `asset`, `assetKind: image`; значение — `{assetId}`,
  а не строка URL. `Image.alt` — текст. Runtime использует предоставленные
  приложением image models; загрузка и подпись изображения не происходят
  внутри binding evaluator.
- Content Query API использует working текущего CS поверх head; Delivery
  опубликованного окружения читает published pointers. Эти источники нельзя
  взаимозаменять. Чтение сущностей и файлов требует `content.read`, запись
  ассета — `asset.write`; права `asset.read` в проекте нет.

## 4. Интерфейс и сценарий

### 4.1. Основной контент страницы

Панель «Данные» показывает «Не выбран» либо имя/схему текущей сущности.
Для недоступной сущности показывается причина, без запроса её имени в обход прав.
«Выбрать сущность» открывает каталог по схемам активного manifest окружения.
Переключение страницы/CS не переносит выбор и незавершённый диалог.
Текущий источник считается сохранённым только после подтверждённой команды.
Связь хранит ID объекта, а не закрепляет его версию: последующая публикация
правок сущности должна обновлять значения страницы. Наблюдаемая версия нужна
для диагностики/перечитывания, не переносится в IR как скрытый pin.

Если источник использует routeParam, контрол показывает этот режим для чтения.
Его замена на конкретную сущность — отдельное явное действие с сохранением
прежней декларации в inverse; автоматической миграции маршрута нет.
Неизвестная схема/версия блокирует запись, а не заменяется первой доступной.

### 4.2. Привязка свойства

У совместимого свойства есть «Связать с контентом». Picker показывает дерево
полей схемы, тип и доступный пример в выбранной локали. Отсутствие значения
не делает корректный путь несуществующим: контракт определяется схемой.
Дерево ограничено глубиной 8 и 200 выбираемыми листьями; при превышении
показывается понятное ограничение, без обрезания уже сохранённой привязки.
Сегменты пути проверяются общей грамматикой и запретом prototype-ключей.

Для первого пакета доступны scalar/enum/text/asset-поля и вложенные object-поля.
Reference/list/richText/object целиком остаются недоступны как новый выбор.
Строка и text совместимы только по действующим правилам manifest; enum и
ограничения принимающего свойства проверяются ими же. Нельзя вводить свой URL
вместо asset reference, интерполировать JS или автоматически вызвать formatter.

Выбор показывает итоговую связь, например `Heading.text ← $content.title`.
Значение отображается отдельно как предпросмотр. После сохранения IR содержит
путь; изменение title сущности не переписывает bindings страницы.
Существующие object binding/default/format/template и другие scopes показываются
целиком только для чтения. Их замена или удаление требуют явного действия;
открытие picker и отмена сохраняют точное исходное значение.

### 4.3. Смена источника и история

Смена entityId в той же совместимой схеме сохраняет пути. Для смены схемы
проверяются все зависимости `$content`, включая when/dataSources/сложные
выражения, даже если их редакторы не входят в пакет. UI предлагает явно снять
только поддержанные простые node bindings; остальные зависимости требуют
изменения через существующий Structure либо отмены смены источника.
Не допускаются скрытое удаление when/обработчиков/полей и частичное применение.

Одна подтверждённая смена с согласованным снятием привязок — одна атомарная
группа истории и один undo. Inverse восстанавливает точные декларации,
props/bindings и присутствие optional-полей. Если поддержанным удалением binding
свойство остаётся без required-значения, сервер возвращает диагностику;
UI не выдумывает значение для прохождения проверки.

## 5. Команды и согласованность

Добавляется `document.setContent` в существующий `apply-operations`:

```json
{
  "type": "document.setContent",
  "target": "<page-object-id>",
  "payload": {
    "content": {
      "schema": "Article",
      "resolve": { "by": "entity", "entityId": "<entity-id>" }
    }
  }
}
```

`content: null` в payload снимает декларацию: поле удаляется из IR, а не
записывается как null. Операция принимает существующую ContentDeclaration,
включая routeParam для точного undo старых документов; UI создаёт только
by:entity. Page-only, схема, права, тип/доступность/версия ссылки и совместимость
проверяются на сервере. Операция не изменяет саму сущность или маршрут страницы.

Право операции — `design.compose`; дополнительно проверяется `content.read`,
включая снятие декларации, без новой роли. Запись разрешена только владельцу
open CS. Для выбора и человеческого чтения источника нужны `design.read`
и `content.read`; одного права дизайна недостаточно для выдачи private content.
Серверное сравнение и публикация повторно применяют текущие права и общие
правила whole-CS доступа. Агентский каталог этим пакетом не расширяется.

Существующий `node.setBinding` используется для установки/снятия привязки.
Добавление операции требует согласованного изменения Go/TS apply, типов,
inverse/rebase и JSON diff декларации, а не обхода Command Bus через PUT IR.
Новая операция включается в журнал и существующий publication diff;
expectedSeq, idempotency и неопределённые исходы сохраняют прежние гарантии.

## 6. Разрешение данных, preview и кеш

Для by:entity опубликованный `GET /delivery/v1/{project}/{env}/page`
разрешает primary entity из published pointers того же окружения. Draft preview
разрешает working того же CS поверх его доступной head-базы; права и область
preview-токена проверяются до выдачи данных. Нельзя взять source из другого
неопубликованного CS или заменить недоступный draft публичной версией без отметки.
Валидация публикации использует будущее состояние: источник и обложка должны
быть опубликованы в target либо публиковаться атомарно тем же CS.

Реализуется только статически используемая проекция primary content:
простые `$content` пути, поддержанные этим пакетом, включая необходимые
параметры существующих привязок/условий. Неиспользуемые поля/ссылки и полный
entity.data не сериализуются в страницу «на всякий случай».
Новая проекция ограничена 200 уникальными путями и 1 MiB JSON; превышение
даёт явную диагностику/ошибку, а не успешный обрезанный набор данных.
Неподдержанный reference traversal или routeParam выдаёт явную диагностику этого ограниченного
resolver; нельзя заявлять полную поддержку IR-044 или показывать подложные данные.

В `data.content` выдаются выбранные значения в выбранной локали; метаданные
зависимостей с версиями остаются серверными либо отдельным типизированным
служебным полем, не смешиваются с именами полей сущности. SDK ReadOptions
дополняются `locale?: string`; getPage передаёт её в query, decoder проверяет
новую часть ответа. При отсутствии locale используется defaultLocale проекта;
неизвестная локаль — ошибка запроса. Это не locale fallback отдельных полей.

React loader устанавливает `scope.content` из разрешённого `data.content`
до data-source evaluation и подготовки плана. Витрина и preview используют
одну реализацию, сохраняя прежние `$data`/`$context` страницы. Image.src сохраняет
asset reference; сервер приложения получает image model через действующий
`getImage` и передаёт renderer отдельно. Повреждённый/неготовый/недоступный
файл даёт безопасное пустое состояние/alt и диагностику, без прямого S3 URL
и без превращения asset reference в произвольный HTML.

ETag страницы учитывает документ и разрешённые content/asset версии, локаль
и значимые входы ответа. Ключ кеша SDK включает locale; preview обходит кеш.
После публикации одной сущности новый Delivery-запрос со старым ETag получает
200 с новым значением, даже если IR и версия страницы не изменились.
Используются действующие границы TTL/инвалидации; мгновенное обновление всех
внешних клиентов и завершение CDN/NFR этим пакетом не обещаются.

Preview после подтверждённой правки получает новый разрешённый контекст.
Один document.patch с прежним scope недостаточен: допустим полный безопасный
reload через существующий bridge. Секреты/preview-токены остаются в серверной
cookie/прокси-связке, не отправляются через postMessage или поля Studio.

## 7. Состояния и диагностики

В UI различаются: нет источника, загрузка каталога/значений, пустой каталог,
нет совместимых полей, источник удалён/недоступен, схема устарела, значение
отсутствует в этой локали, файл не готов, неподдержанный режим, конфликт
и неизвестный исход сохранения. Ошибка чтения не очищает сохранённую привязку.
Автоперепривязка на другую сущность, копирование разрешённых значений в IR,
авто-upcast и скрытый сброс несохранённых форм запрещены.

Используются действующие `BINDING_*` и content-диагностики. Новый код
`BINDING_VALUE_MISSING` означает: путь существует в схеме, но значение отсутствует
в выбранной локали. Go-константа находится в `internal/delivery/primary.go`,
TS-контракт `ContentValueDiagnostic` — в `packages/sdk-core/src/types.ts`.
Ответ содержит `pointer` исходной привязки, `nodeId` и `params.path`; Studio
показывает RU/EN сообщение. `null`, пустая строка, `false` и `0` сохраняются
значениями и не превращаются в эту диагностику. Неверный путь даёт
`BINDING_PATH_UNRESOLVED`, ошибка подписанной картинки — `CMS_IMAGE_UNAVAILABLE`.
Недостаток прав не раскрывает title, данные или версии недоступных объектов.
Удаление и публикация связанных объектов проверяются сервером повторно,
даже если picker загрузил доступный вариант раньше.

## 8. Проверки и критерии готовности

Каждое STU-203…218 покрывается тестом/фикстурой с ID по [правилам](testing.md).
При реализации обязательны следующие проверки:

| Уровень               | Сценарии                                                                                                                                                                                                                                                       |

Для STU-218 используется настоящий CMS/PostgreSQL, локальный подписанный OIDC
двух людей, React-витрина и готовое object storage/image delivery. Настройка
схем/ролей/окружения допустима API. Article, cover, выбор источника и привязки
создаются через Studio; нельзя подменять сценарий заранее заполненным IR
или заглушкой `$content` в приложении. После согласования и явной публикации
проверяются содержимое Delivery, SSR и браузерная картинка, версии и хеш файла.
Если реальный image delivery недоступен, приёмка обложки отмечается непроверенной.

Дополнительная проверка: изменить только title выбранной сущности, опубликовать
без правки страницы и подтвердить новый текст/ETag при прежней page version.
Отдельно пройти отмену смены источника, конфликт seq, отсутствующую локаль
и отказ чтения чужого draft. Скриншот без данных и проверка одного binding JSON
не заменяют сквозную приёмку.

Порядок: серверная операция и контракты → resolver/locale/cache → UI выбора
источника и полей → React/preview/images → двухпользовательская приёмка.
Перед PR реализации нужны целевые проверки, генерация затронутых контрактов,
`go tool sqlc generate` при изменении SQL, `go build ./...`, `pnpm check`
и зелёный CI конечного SHA без снижения порогов. Ограничения локальной среды
фиксируются отдельно. Текущее состояние реализации и доказательства приведены ниже.

## 9. Реализация и доказательства

Реализованы STU-203…218: операция `document.setContent`, атомарные группы,
inverse/undo/redo/rebase, повторная проверка источника и прав; панель «Данные»
с каталогом и типизированными полями; ограниченная проекция Delivery; локаль,
ETag зависимостей, SDK/React scope и подписанные модели Image отдельно от IR.
JSON diff поддерживает декларацию. Сложные зависимости блокируют несовместимую
смену источника, а точный повтор сохраняет исходные seq, key и операции.

Приёмка `scripts/studio-live-content-bindings.mjs` пройдена на изолированном
loopback-стенде с PostgreSQL, подписанным OIDC двух людей, MinIO/imgproxy и React.
Article, файл, выбор сущности и три привязки созданы через Studio. Только исходная
статическая раскладка страницы настроена через API; IR с привязками не подставлялся.
Проверены RU/EN заголовок и реальная картинка (`naturalWidth > 0`), точный retry
после потерянного ответа уже выполненного запроса, undo/redo, ширина 375 px,
согласование Bob и явная публикация. SHA-256 опубликованного файла совпал
с загруженным PNG. Вторая работа меняет только title сущности: до публикации
старый ETag даёт 304, после публикации — 200 с новым ETag/текстом при прежней
page version. Новая публичная сессия браузера подтверждает опубликованный результат.

Отчёт `content-bindings-acceptance.json` и снимки `bindings-mobile.png` /
`bindings-published.png` сохранены в локальном каталоге доказательств. Проверенные
работы: `01a14177-018a-796a-adf2-75de572c91fd` (страница/сущность/файл) и
`01a14177-2d9c-770b-b8ed-7ef1cc4220ad` (только сущность). Для повторения нужен
свежий loopback-стенд с RU/EN, `CMS_REVIEW_BINDINGS=true` при подготовке схемы,
`assetUploadOrigin` и разрешённый CORS storage; затем
`STUDIO_REVIEW_ADMIN_FILE`, `STUDIO_REVIEW_OUTPUT` и
`node scripts/studio-live-content-bindings.mjs`. Секреты остаются в private-файлах.

Локально пройдены форматирование, ESLint/gofmt, типы/Go vet, генерация sqlc/Go,
сборки затронутых приложений, все TypeScript-тесты с действующими порогами,
весь обычный набор Go-тестов с настоящим PostgreSQL и целевые проверки rebase.
Linux race для семи библиотек композиции пройден отдельно. Браузерные регрессии:
60 сценариев. Studio: 281 тест, statements 91,95%, branches 86,27%,
functions 91,51%, lines 93,49%.

При ревью PR проверены отсутствующая/`null` обложка и срок действия подписанных
картинок. Отсутствие значения сохраняет заголовок, страницу и preview; Image
показывает безопасную заглушку с `CMS_IMAGE_UNAVAILABLE`. Непустая некорректная
ссылка по-прежнему отклоняется. Привязанные картинки участвуют в существующем
обновлении витрины за 30 секунд до истечения URL; обновление сохраняет выбранную
локаль, в том числе при повторе после ошибки. Добавлены регрессионные тесты;
число тестов витрины после этих исправлений — 115.

Полный локальный `pnpm check` ограничен отсутствием C-компилятора для Go race
в Windows; локальный Go 1.26.0 также не содержит `covdata` для полного профиля
`-coverpkg`. Полные race/coverage, сборки и браузерные регрессии проверяются CI.
Пороги не снижены. Production, внешний IdP, CDN, locale fallback, полный M4
и IR-044 остаются вне этого пакета.
