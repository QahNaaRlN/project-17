# Техническая спецификация CMS — обзор

Версия 1.0-draft • 9 октября 2026 • основана на архитектурной спецификации v0.1 от 25 сентября 2026

## 1. Назначение

Документ превращает архитектурную спецификацию v0.1 в реализуемую техническую спецификацию: фиксирует форматы данных, контракты API, модель хранения, семантику версий и публикации, протоколы взаимодействия и критерии приёмки MVP.

Архитектурные принципы v0.1 сохраняются без изменений. Там, где v0.1 оставляла решение открытым, этот документ принимает решение и помечает его как **[Решение]** с кратким обоснованием. Решения можно пересмотреть через ADR (см. [13-decisions.md](13-decisions.md)).

## 3. Соглашения

### 3.1. Уровни требований

| Термин | Значение |
|---|---|
| **ДОЛЖЕН / ОБЯЗАН** | Обязательное требование. Реализация без него не соответствует спецификации. |
| **НЕ ДОЛЖЕН** | Абсолютный запрет. |
| **СЛЕДУЕТ** | Рекомендуется; отступление допустимо с обоснованием в ADR. |
| **МОЖЕТ** | Необязательная возможность. |

### 3.2. Идентификаторы требований

Требования имеют идентификатор `<ОБЛАСТЬ>-<НОМЕР>`, например `IR-012`, `PUB-004`. Идентификаторы не переиспользуются. Тесты приёмки ссылаются на них.

| Префикс | Область |
|---|---|
| `FR` | Общие функциональные требования |
| `NFR` | Нефункциональные требования |
| `IR` | Формат IR |
| `DS` | Дизайн-система и Design Runtime |
| `MF` | Manifest и реестры |
| `CNT` | Контент и схемы |
| `CHG` | Операции и Change Set |
| `PUB` | Публикация, rollback, окружения |
| `API` | Внешние интерфейсы |
| `AGT` | Агент и Missing Capability |
| `SDK` | Runtime, SDK, preview |
| `STU` | Studio |
| `ST` | Хранилище данных |
| `SEC` | Безопасность |
| `OPS` | Эксплуатация |

### 3.3. Форматы

- Идентификаторы хранимых объектов: UUID v7 (строка в каноническом виде).
- Идентификаторы узлов IR: короткие строки (см. [02-ir.md §3](02-ir.md#3-узел)).
- Время: RFC 3339 в UTC, точность до миллисекунд.
- JSON: UTF-8, ключи в `camelCase`; в SQL — `snake_case`.
- Версии форматов: `MAJOR.MINOR`. Изменение MINOR обратно совместимо для читателей; изменение MAJOR — нет.

## 4. Глоссарий

| Термин | Определение |
|---|---|
| **IR** | Типизированное промежуточное представление UI; источник истины для декларативной части интерфейса. |
| **Документ IR** | Единица хранения IR: страница (`page`) или компонент (`component`). |
| **Узел** | Элемент дерева IR с типом, свойствами и слоями. |
| **Примитив** | Тип узла, реализованный Design Runtime (`Box`, `Stack`, `Text` …). |
| **Компонент** | Повторно используемый тип узла. Происхождение: `native`, `composed`, `generated`. |
| **Manifest** | Машиночитаемое описание возможностей приложения: компоненты, токены, действия, источники данных, capabilities. |
| **Capability** | (1) Именованная программная возможность приложения (`commerce.addToCart`); (2) право актора в модели доступа (`content.write`). Различаются по контексту; в тексте используются термины «capability приложения» и «право». |
| **Объект** | Версионируемая сущность хранения: контент-сущность, документ IR, схема. |
| **Версия** | Неизменяемый снимок тела объекта. |
| **Операция** | Неизменяемая запись об одном семантическом изменении. |
| **Change Set (CS)** | Набор операций; единица проверки, согласования и публикации. |
| **Head** | Указатель на последнюю принятую версию объекта. |
| **Published** | Указатель на опубликованную версию объекта в окружении. |
| **Окружение** | Именованная цель публикации (`staging`, `production`). |
| **Актор** | Субъект, выполняющий команду: `human`, `agent`, `service`, `migration`. |
| **Зона** | Поддерево IR с собственной политикой (режимом свободы, ограничениями). |
| **Missing Capability** | Формализованный запрос на программную возможность, отсутствующую в manifest. |
| **Studio** | Административный интерфейс CMS. |
| **Delivery API** | Публичный read-only API, из которого приложение получает опубликованный или черновой IR и контент. |

## 5. Отличия от архитектурной спецификации v0.1

Сводка решений, уточняющих или меняющих v0.1. Подробности — в соответствующих разделах и в [13-decisions.md](13-decisions.md).

1. IR хранится в **нормализованном виде** (плоская карта узлов со стабильными ID), а не вложенным деревом. Вложенная форма допустима только как формат импорта.
2. Шесть «моделей IR» из v0.1 §4.1 реализуются как **слои одного документа** (Composition, Design, Binding, Behavior, Policy). Content IR хранится отдельно — в сущностях контента.
3. Добавлены **структурные примитивы** `Repeat`, `Show`, `Slot`, без которых невозможны коллекции и условный показ.
4. Таблицы `entities`, `compositions`, `components` из v0.1 §10 объединены в общий реестр **`objects` / `object_versions`** с полем `kind`. Это упрощает указатели, Change Set и ссылочную целостность.
5. **GraphQL исключён из MVP.** Для чтения используется Delivery API (REST); GraphQL — после MVP.
6. Модуль `proto/` удалён из структуры monorepo. Единый источник типов IR — **JSON Schema** с генерацией кода для Go и TypeScript.
7. Go-код сервера живёт в `apps/server/`, включая `apps/server/internal/...`.
8. Svelte- и Vue-адаптеры исключены из MVP; протокол остаётся независимым от фреймворка.
9. Фоновые задачи — очередь на PostgreSQL (библиотека River); Redis — кэш, rate limiting, presence.
