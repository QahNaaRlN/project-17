# 02. Типизированное промежуточное представление UI (IR)

IR — источник истины для декларативной части интерфейса. Его одинаково читают и пишут Studio, CMS Core, агент и runtime приложения. Формальная схема — [packages/ir/schema/ir-1.0.schema.json](../../packages/ir/schema/ir-1.0.schema.json); примеры и conformance-фикстуры — [packages/ir/fixtures/](../../packages/ir/fixtures/).

## 1. Принципы

| ID | Требование |
|---|---|
| IR-001 | Документ IR ДОЛЖЕН быть единственным представлением страницы или Composed-компонента. JSX, HTML и состояние редактора — производные. |
| IR-002 | Двусторонняя генерация JSX ↔ IR НЕ ДОЛЖНА использоваться как основной механизм редактирования. |
| IR-003 | Все клиенты ДОЛЖНЫ изменять IR через операции ([06-changes-publishing.md](06-changes-publishing.md)); прямая перезапись тела документа доступна только команде импорта. |
| IR-004 | IR НЕ ДОЛЖЕН содержать исполняемый код, CSS-строки, селекторы или HTML. |
| IR-005 | Единственный источник типов IR — JSON Schema в `packages/ir/schema/`. Типы Go и TypeScript генерируются из неё. Валидаторы на Go и TS ДОЛЖНЫ проходить общий набор conformance-фикстур `packages/ir/fixtures/`. |

## 2. Документ

**[Решение]** Документ хранится в нормализованном виде: плоская карта узлов по ID, порядок детей задаётся массивами ID. Нормализованная форма даёт стабильную адресацию для операций, diff, выбора в preview и будущего CRDT; вложенная форма такие операции усложняет.

```json
{
  "irVersion": "1.0",
  "kind": "page",
  "root": "n_root",
  "content": { "schema": "Article", "resolve": { "by": "routeParam", "field": "slug", "param": "slug" } },
  "policy": { "mode": "SYSTEM", "maxMode": "FREE" },
  "dataSources": {},
  "localContent": {},
  "nodes": {
    "n_root": { "id": "n_root", "type": "Container", "children": ["n_grid"] }
  },
  "meta": { "title": "Шаблон статьи" }
}
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `irVersion` | `"1.0"` | да | Версия формата. |
| `kind` | `"page"` \| `"component"` | да | Страница или Composed-компонент. |
| `root` | NodeId | да | ID корневого узла. |
| `nodes` | map NodeId → Node | да | Все узлы документа. |
| `policy` | DocumentPolicy | нет | Политика уровня документа (§9). |
| `content` | ContentDeclaration | нет | Только `page`. Основная сущность страницы — источник `$content`. |
| `inputs` | map → InputDef | нет | Только `component`. Типизированные входы (§8). |
| `slotDefs` | map → SlotDef | нет | Только `component`. Объявления слотов (§8). |
| `dataSources` | map → DataSourceUse | нет | Подключённые источники данных (§6.6). |
| `localContent` | map → LocalContentItem | нет | Контент, введённый прямо на холсте (§6.5). |
| `meta` | object | нет | `title`, `description`, `thumbnailAssetId`. Не влияет на рендеринг. |

Маршрут страницы (`path`) — свойство объекта, а не IR, потому что уникальность маршрутов обеспечивается хранилищем ([07-storage.md](07-storage.md)).

### 2.1. Объявление основного контента

```json
{ "schema": "Article", "resolve": { "by": "routeParam", "field": "slug", "param": "slug" } }
{ "schema": "LandingPage", "resolve": { "by": "entity", "entityId": "0192f1c4-..." } }
```

- `by: "routeParam"` — шаблонная страница; сущность ищется по уникальному полю `field`, равному параметру маршрута `param`.
- `by: "entity"` — страница привязана к конкретной сущности.

### 2.2. Инварианты документа

| ID | Инвариант |
|---|---|
| IR-010 | `root` ДОЛЖЕН существовать в `nodes`. |
| IR-011 | Ключ в `nodes` ДОЛЖЕН совпадать с `id` узла. |
| IR-012 | Каждый узел, кроме корня, ДОЛЖЕН упоминаться ровно один раз во всех `children` и `slots` документа. Сирот и множественных родителей быть не должно. |
| IR-013 | Граф узлов ДОЛЖЕН быть деревом без циклов. |
| IR-014 | Число узлов ≤ 5 000, глубина ≤ 32, размер тела ≤ 2 МиБ (NFR-011…013). |
| IR-015 | `content` допустим только при `kind = "page"`; `inputs`, `slotDefs` — только при `kind = "component"`. |

### 2.3. Канонический порядок обхода

Чтобы все реализации валидатора (TypeScript, Go) выдавали одинаковые диагностики, порядок обхода дерева фиксирован:

1. Ссылки узла на детей перебираются так: `children` по порядку, затем слоты в лексикографическом порядке имён, внутри слота — по порядку.
2. Обход начинается с `root` в прямом порядке (узел, затем его дети в порядке п. 1). Узел закрепляется за первым родителем, через которого он достигнут; каждая следующая ссылка на него — `NODE_MULTIPLE_PARENTS` в месте этой ссылки.
3. Затем узлы, не достигнутые от корня, обходятся по тому же правилу, начиная с каждого ещё не посещённого узла в лексикографическом порядке ID.
4. Цикл сообщается один раз, на узле цикла с наименьшим ID; «сирота» — на вершине недостижимого поддерева.

Порядок ключей JSON-объектов не влияет на результат: реализации НЕ ДОЛЖНЫ на него опираться.

## 3. Узел

```json
{
  "id": "n_k3j9x2ab",
  "type": "Heading",
  "name": "Заголовок героя",
  "props": { "level": 1 },
  "bindings": { "text": "$content.title" },
  "design": { "typography": "display", "color": "text" },
  "when": { "op": "exists", "arg": "$content.title" },
  "on": {},
  "children": [],
  "slots": {},
  "zone": null,
  "locked": false
}
```

| Поле | Слой | Описание |
|---|---|---|
| `id` | — | Стабильный ID. Формат `^[A-Za-z0-9_-]{4,32}$`. Генерация: `n_` + 8 случайных символов `[a-z0-9]`. Уникален в документе; никогда не переиспользуется в нём. |
| `type` | Composition | Примитив (`Stack`), структурный примитив (`Repeat`, `Slot`), компонент из manifest (`ProductCard`) или `Composed`. |
| `ref` | Composition | Только для `Composed`: `{ "component": "<objectId>", "version": "live" \| <int> }` (§8.3). |
| `name` | — | Человекочитаемое имя для дерева слоёв. |
| `props` | Composition | Статические значения свойств. |
| `bindings` | Binding | Свойства, получаемые из данных (§6). |
| `design` | Design | Визуальные свойства (§5, [03-design-system.md](03-design-system.md)). |
| `when` | Binding | Условие показа (§6.4). |
| `on` | Behavior | Обработчики событий (§7). |
| `children` | Composition | Упорядоченный список дочерних ID для контейнеров. |
| `slots` | Composition | Слоты компонента: имя → упорядоченный список ID. |
| `zone` | Policy | Объявление зоны политики (§9). |
| `locked` | Policy | Запрет структурных изменений узла и поддерева в Studio без права `design.zones.manage`. |

| ID | Требование |
|---|---|
| IR-020 | Ключ свойства НЕ ДОЛЖЕН одновременно присутствовать в `props` и `bindings`. |
| IR-021 | `children` допустим только для типов, объявленных в manifest как контейнеры. `slots` — только с именами слотов, объявленными для типа. |
| IR-022 | При копировании поддерева все узлы ДОЛЖНЫ получить новые ID; ссылки внутри поддерева (например, цели `openModal`) ДОЛЖНЫ быть переназначены. |
| IR-023 | Неизвестные поля узла в пределах той же MAJOR-версии читатель ДОЛЖЕН игнорировать, а сервер — сохранять при записи. |

## 4. Слои IR

Шесть моделей из архитектуры v0.1 §4.1 реализуются так:

| Модель v0.1 | Реализация | Где хранится |
|---|---|---|
| Content IR | Сущности контента; `localContent` документа | `object_versions` (kind `entity`); раздел документа |
| Composition IR | `type`, `ref`, `props`, `children`, `slots` | Документ IR |
| Design IR | `design` | Документ IR |
| Binding IR | `bindings`, `when`, `dataSources`, `content` | Документ IR |
| Behavior IR | `on` | Документ IR |
| Policy IR | `policy` документа, `zone`, `locked` + политики проекта | Документ IR + `policies` |

**[Решение]** Слои хранятся в одном документе, а не в шести. Это сохраняет атомарность операций (перемещение узла не рассинхронизирует его дизайн) и простоту версионирования. Разделение слоёв обеспечивается на уровне операций (у каждого слоя свои типы операций и права) и валидаторов, а не на уровне хранения.

## 5. Адаптивные значения и значения дизайна

### 5.1. Адаптивные значения

Breakpoint'ы объявляются в manifest ([04-manifest.md](04-manifest.md)). Модель mobile-first: значение breakpoint'а применяется при ширине viewport ≥ его `minWidth`. По умолчанию:

| Имя | minWidth |
|---|---|
| `base` | 0 |
| `sm` | 640 |
| `md` | 768 |
| `lg` | 1024 |
| `xl` | 1280 |

Адаптивное значение — объект, ключи которого — имена breakpoint'ов; `base` обязателен:

```json
{ "columns": { "base": ["1fr"], "md": ["3fr", "2fr"] }, "gap": { "base": "md", "lg": "xl" } }
```

| ID | Требование |
|---|---|
| IR-030 | Любое свойство в `design` МОЖЕТ быть адаптивным. |
| IR-031 | Свойство в `props` МОЖЕТ быть адаптивным, только если в manifest оно объявлено с `responsive: true`. |
| IR-032 | Адаптивное значение ДОЛЖНО содержать `base`; остальные ключи ДОЛЖНЫ быть объявленными breakpoint'ами. |
| IR-033 | Имена `raw`, `token`, `expr` зарезервированы и НЕ ДОЛЖНЫ использоваться как имена breakpoint'ов. |

### 5.2. Токены и сырые значения

- Значение-токен — строка-идентификатор: `"gap": "md"`, `"background": "surfaceAccent"`.
- Сырое значение — объект `{"raw": "<значение>"}`: `"padding": {"raw": "24px"}`. Допустимо только там, где режим и политика это разрешают ([03-design-system.md §4](03-design-system.md#4-режимы-свободы)).

Явная обёртка `raw` делает каждое отступление от дизайн-системы видимым при валидации и подсчёте метрики «число overrides» (эксперимент, [14-mvp-plan.md](14-mvp-plan.md)).

### 5.3. Состояния взаимодействия

```json
"design": {
  "background": "primary",
  "states": { "hover": { "background": "primaryHover" }, "focusVisible": { "outline": "focus" } }
}
```

Допустимые состояния: `hover`, `active`, `focusVisible`, `disabled`. Внутри состояний допустим ограниченный набор свойств ([03-design-system.md §3.3](03-design-system.md#33-свойства-состояний)).

## 6. Привязки (Binding IR)

### 6.1. Выражения пути

Привязка — строка-выражение пути без вычислений:

```
binding   = "$" scope *( "." segment )
scope     = "content" | "local" | "props" | "item" | "index" | "each" | "data" | "context"
segment   = identifier | 1*DIGIT
identifier = ALPHA *( ALPHA / DIGIT / "_" )
```

| Область | Где доступна | Значение |
|---|---|---|
| `$content` | Страница с `content` | Основная сущность страницы. Поля-ссылки разыменовываются: `$content.author.name`. |
| `$local` | Любой документ | `localContent` текущего документа: `$local.t_hero_title`. |
| `$props` | Документ-компонент | Входы Composed-компонента: `$props.title`. |
| `$item` | Внутри `Repeat` | Текущий элемент ближайшего `Repeat`. |
| `$index` | Внутри `Repeat` | Индекс текущего элемента ближайшего `Repeat` (с 0). |
| `$each.<alias>` | Внутри `Repeat` | Элемент `Repeat` с `props.as = alias`; доступ к внешним циклам. |
| `$data.<key>` | Любой документ | Результат источника данных из `dataSources`. |
| `$context` | Любой документ | Контекст выполнения (§6.7) и контекст, предоставленный native-компонентами. |

### 6.2. Объектная форма привязки

```json
{ "expr": "$content.publishedAt", "format": { "fn": "date", "args": { "style": "long" } }, "default": "" }
```

```json
{ "template": "от {price} за {unit}", "vars": { "price": { "expr": "$item.price", "format": { "fn": "currency", "args": { "code": "RUB" } } }, "unit": "$item.unit" } }
```

| Поле | Описание |
|---|---|
| `expr` | Выражение пути. |
| `format` | Форматтер из реестра: встроенный или объявленный в manifest. |
| `default` | Литерал, если значение отсутствует (`null` или нет поля). |
| `template` + `vars` | Строковый шаблон с подстановками `{name}`. Текст шаблона — контент и ДОЛЖЕН храниться через `$local` при `content: true` (IR-041). |

Встроенные форматтеры: `date {style: short|medium|long|iso}`, `number {style: decimal|percent, minFraction, maxFraction}`, `currency {code}`, `truncate {length}`, `uppercase`, `lowercase`. Локаль берётся из `$context.locale`.

### 6.3. Правила привязок

| ID | Требование |
|---|---|
| IR-040 | Выражения НЕ ДОЛЖНЫ содержать операторов, вызовов функций и индексации вычисляемыми ключами. |
| IR-041 | Свойство, объявленное в manifest как контентное (`content: true`, например `Heading.text`, `Image.src`), НЕ ДОЛЖНО иметь литерал в `props`; его значение задаётся только привязкой. Текст, введённый на холсте, Studio сохраняет в `localContent` и создаёт привязку `$local.<key>`. |
| IR-042 | Тип значения по пути ДОЛЖЕН быть совместим с типом свойства (таблица совместимости — [04-manifest.md §4](04-manifest.md#4-система-типов)). Проверка выполняется статически по схемам контента, входам компонента, схемам результата источников данных и `provides` компонентов. |
| IR-043 | Глубина разыменования ссылок в одном выражении ≤ 3. |
| IR-044 | Delivery API ДОЛЖЕН вычислять множество используемых путей статически и разыменовывать только их (без избыточной выборки). |
| IR-045 | Значения типа `url`, полученные через привязку, ДОЛЖНЫ проходить проверку схемы URL в runtime (`http`, `https`, `mailto`, `tel`, относительные пути). |

### 6.4. Условия показа (`when`)

Узел с `when` рендерится, только если условие истинно. Условие — дерево предикатов:

```json
{ "op": "and", "args": [
  { "op": "exists", "arg": "$content.image" },
  { "op": "neq", "args": ["$context.locale", { "lit": "en" }] }
] }
```

| Оператор | Аргументы |
|---|---|
| `exists`, `empty` | `arg`: выражение |
| `eq`, `neq`, `gt`, `gte`, `lt`, `lte` | `args`: [операнд, операнд] |
| `in` | `args`: [операнд, массив литералов] |
| `and`, `or` | `args`: предикаты (1–16) |
| `not` | `arg`: предикат |

Операнд — выражение (строка, начинающаяся с `$`) или литерал `{"lit": <значение>}`. Глубина дерева предиката ≤ 8.

### 6.5. Локальный контент

```json
"localContent": {
  "t_hero_title": { "type": "text", "value": { "ru": "Летняя коллекция" } },
  "t_hero_img":   { "type": "asset", "value": { "ru": { "assetId": "0192f1c4-...", "alt": "Модель в льняном костюме" } } }
}
```

Ключ: `^t_[a-z0-9_]{2,40}$`. `value` — карта локаль → значение (локализация на уровне значения, [05-content.md §5](05-content.md#5-локализация)). Изменения `localContent` классифицируются как контентные операции (права `content.write`), несмотря на хранение в документе IR.

### 6.6. Источники данных

```json
"dataSources": {
  "featured": {
    "source": "commerce.products.list",
    "params": { "collection": "$content.collection.handle", "limit": { "lit": 4 } }
  }
}
```

- `source` — имя источника из manifest; схема параметров и схема результата объявлены там.
- Параметры — выражения или литералы `{"lit": ...}`; допустимы области `$content`, `$local`, `$props`, `$context`.
- Источники исполняет приложение (SDK вызывает зарегистрированный загрузчик). CMS знает только контракт.
- Источник, объявленный с `paginated: true`, предоставляет `$data.<key>.items`, `$data.<key>.hasMore` и допускает действие `data.loadMore`.

### 6.7. Контекст выполнения

| Путь | Значение |
|---|---|
| `$context.locale` | Текущая локаль |
| `$context.route.path` | Путь страницы |
| `$context.route.params.<name>` | Параметр маршрута |
| `$context.viewer.authenticated` | Признак аутентифицированного пользователя приложения |
| `$context.<key>` | Значения, предоставленные native-компонентом-предком (`provides` в manifest), например `$context.product` внутри слотов `ProductCard` |

## 7. Поведение (Behavior IR)

```json
"on": {
  "click": [
    { "action": "commerce.addToCart", "args": { "product": "$context.product", "quantity": { "lit": 1 } } },
    { "action": "track", "args": { "event": { "lit": "add_to_cart" } } }
  ]
}
```

| ID | Требование |
|---|---|
| IR-050 | Значение события — одно действие или массив действий (≤ 8), исполняемых последовательно; при ошибке действия цепочка прерывается. |
| IR-051 | Узел МОЖЕТ объявлять обработчики только событий, которые его тип объявляет в manifest (`Button.click`, `Link.click`, `Form.submit`…). |
| IR-052 | `action` ДОЛЖЕН быть встроенным действием или действием из manifest; аргументы ДОЛЖНЫ соответствовать его схеме. |
| IR-053 | В черновике в зоне режима CODE `action` МОЖЕТ иметь вид `pending:<capabilityRequestId>` (заглушка Missing Capability, [09-agent.md §5](09-agent.md#5-missing-capability)). Публикация документа с заглушками запрещена. |

Встроенные действия runtime:

| Действие | Аргументы |
|---|---|
| `navigate` | `to`: Link |
| `openModal` / `closeModal` | `target`: NodeId узла типа `Modal` |
| `scrollTo` | `target`: NodeId |
| `track` | `event`: string, `props`: map |
| `data.loadMore` | `source`: ключ `dataSources` |

Тип `Link`:

```json
{ "kind": "page", "page": "<objectId>", "params": { "slug": "$item.slug" } }
{ "kind": "url", "url": "https://example.com" }
{ "kind": "anchor", "node": "n_faq" }
```

## 8. Composed-компоненты

### 8.1. Документ компонента

```json
{
  "irVersion": "1.0",
  "kind": "component",
  "root": "n_root",
  "inputs": {
    "title":   { "type": "text", "required": true, "content": true },
    "image":   { "type": "asset", "assetKind": "image", "content": true },
    "variant": { "type": "enum", "values": ["light", "dark"], "default": "light" },
    "product": { "type": "reference", "schema": "Product" }
  },
  "slotDefs": { "footer": { "allowedTypes": ["Button", "Link"], "max": 2 } },
  "nodes": { "...": "..." }
}
```

Внутри документа компонента входы доступны как `$props.<name>`, слоты размещаются узлами `{"type": "Slot", "props": {"name": "footer"}}`.

### 8.2. Экземпляр

```json
{
  "id": "n_hero01",
  "type": "Composed",
  "ref": { "component": "0192f1c5-...", "version": "live" },
  "props": { "variant": "dark" },
  "bindings": { "title": "$content.title", "image": "$content.cover" },
  "slots": { "footer": ["n_cta01"] },
  "design": { "colSpan": { "base": 12, "lg": 7 } }
}
```

| ID | Требование |
|---|---|
| IR-060 | `design` экземпляра применяется только к внешней обёртке компонента и ограничен свойствами размещения: `width`, `maxWidth`, `colSpan`, `rowSpan`, `alignSelf`, `order`, `hidden`, внешние отступы. Переопределение внутренних узлов компонента запрещено; вариативность выражается входами. |
| IR-061 | Обязательные входы ДОЛЖНЫ быть заданы в `props` или `bindings`. |
| IR-062 | Composed-компонент НЕ ДОЛЖЕН прямо или косвенно включать сам себя. |
| IR-063 | Composed-компонент имеет вычисляемое свойство `requiredMode` — максимальный режим, использованный внутри него. Экземпляр допустим только в зоне с эффективным режимом ≥ `requiredMode` либо при явном разрешении типа в `allowedTypes` зоны. |

### 8.3. Привязка экземпляра к версии

- `"version": "live"` (по умолчанию) — при рендеринге используется версия компонента, опубликованная в том же окружении. Публикация компонента обновляет все страницы. Перед публикацией выполняется анализ влияния ([06-changes-publishing.md §6](06-changes-publishing.md#6-анализ-влияния)).
- `"version": <int>` — закреплённая версия; обновление только явной операцией.

## 9. Политика (Policy IR)

### 9.1. Уровни и режимы

Порядок режимов: `STRICT < SYSTEM < FREE < CODE`. Режим задаётся на трёх уровнях:

1. Проект: `defaultMode`, `maxMode` (настройки проекта).
2. Документ: `policy.mode`, `policy.maxMode`.
3. Зона: `zone.mode`, `zone.maxMode`.

```json
"zone": { "id": "header", "mode": "STRICT", "allowedTypes": ["SiteHeader"], "locked": true }
```

**Вычисление эффективного режима узла:** берётся `mode` ближайшего уровня (зона → документ → проект). Для каждого уровня `mode` ДОЛЖЕН быть ≤ `maxMode` объемлющего уровня; `maxMode` по умолчанию равен `mode` того же уровня. Нарушение — ошибка валидации `POLICY_MODE_EXCEEDS_PARENT`.

Пример: проект `defaultMode=SYSTEM, maxMode=FREE`; экспериментальный лендинг `policy.mode=FREE`; зона Checkout `mode=STRICT`.

### 9.2. Поля политики

| Поле | Уровень | Описание |
|---|---|---|
| `mode` | все | Эффективный режим. |
| `maxMode` | все | Верхняя граница для вложенных уровней. |
| `allowedTypes` | документ, зона | Белый список типов узлов (включая Composed по ID). |
| `deniedTypes` | документ, зона | Чёрный список типов. |
| `locked` | зона | Структурные изменения требуют права `design.zones.manage`. |
| `requiredApprovalRole` | зона | Роль, обязательная для согласования изменений зоны. |

## 10. Импорт во вложенной форме

Команда `import-document` принимает вложенную форму (как в архитектуре v0.1 §4): `children` — массив узлов вместо ID. Сервер присваивает ID, нормализует документ и валидирует его. Вложенная форма НЕ ДОЛЖНА храниться.

## 11. Валидация

### 11.1. Уровни

| Уровень | Проверяет | Когда |
|---|---|---|
| L1 Структура | JSON Schema, инварианты IR-010…015 | Каждая операция |
| L2 Ссылки | Существование типов, ID узлов, компонентов, сущностей, ассетов | Каждая операция |
| L3 Manifest | Свойства, типы значений, события, слоты, контейнеры | Каждая операция |
| L4 Привязки | Разрешимость путей, совместимость типов | Каждая операция (предупреждение), публикация (ошибка) |
| L5 Дизайн | Токены, режимы, допустимые свойства | Каждая операция |
| L6 Политика | Режимы зон, `allowedTypes`, права актора | Каждая операция |
| L7 Доступность (статическая) | [03-design-system.md §6](03-design-system.md#6-статические-проверки-доступности) | Публикация; в Studio — подсказки |

Операция, нарушающая L1–L3, L5 или L6, отклоняется. Нарушения L4 и L7 в черновике допустимы как предупреждения и блокируют публикацию, если политика проекта не понижает их уровень.

### 11.2. Формат диагностики

```json
{
  "code": "BINDING_PATH_UNRESOLVED",
  "severity": "error",
  "documentId": "0192f1c5-...",
  "nodeId": "n_k3j9x2ab",
  "pointer": "/nodes/n_k3j9x2ab/bindings/text",
```

## 12. Версионирование формата

| ID | Требование |
|---|---|
| IR-070 | Читатель ДОЛЖЕН отклонять документ с неизвестной MAJOR-версией. |
| IR-071 | Повышение MINOR допускает только добавление необязательных полей, типов узлов и операторов. |
| IR-072 | Переход на новую MAJOR-версию выполняется миграцией (актор `migration`) с публикацией через Change Set. |
| IR-073 | Manifest объявляет поддерживаемые версии IR (`irVersions`); публикация документа версии, не поддерживаемой целевым manifest, запрещена. |
