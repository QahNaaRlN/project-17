# 13. Реестр решений и открытые вопросы

## 1. Принятые решения

| # | Решение | Альтернативы | Обоснование | Раздел |
|---|---|---|---|---|
| D-01 | IR хранится нормализованно (плоская карта узлов со стабильными ID) | Вложенное дерево | Адресация операций, diff, выбор в preview, CRDT без изменения формата | 02 §2 |
| D-02 | Слои IR — поля узла в одном документе; Content IR — отдельно | Шесть отдельных документов | Атомарность операций, простое версионирование; разделение — на уровне операций и прав | 02 §4 |
| D-03 | Текст, введённый на холсте, хранится в `localContent` документа и привязывается через `$local` | Литералы в `props`; автосоздание сущностей | Контентные свойства всегда привязаны → локализация и единая классификация изменений; без засорения схем | 02 §6.5 |
| D-04 | Условный показ — поле `when` любого узла, а не примитив `Show` | Отдельный узел-обёртка | Меньше узлов и вложенности (метрика «сложность IR») | 02 §6.4 |
| D-05 | Экземпляр Composed-компонента может менять только своё размещение; вариативность — через входы | Переопределение внутренних узлов | Предсказуемые обновления компонента, ограничение overrides | 02 §8.2 |
| D-06 | `live`-ссылки на Composed-компоненты по умолчанию + анализ влияния | Закрепление версии по умолчанию | Ожидаемое поведение дизайн-системы; риск контролируется анализом влияния и уровнем риска | 02 §8.3, 06 §6 |
| D-07 | Режимы на трёх уровнях с `mode`/`maxMode` | Только «строже родителя» | Позволяет FREE-лендинг в SYSTEM-проекте под контролем проекта | 02 §9 |
| D-08 | STRICT допускает сертифицированные Composed-компоненты | Только native | Дизайнерские компоненты можно «промышленно» утвердить без переписывания в код | 03 §4 |
| D-09 | Схемы контента — в коде приложения (manifest) | Редактор схем в Studio | Ревью схем вместе с кодом; один путь изменений; выдержано «разработчик управляет схемами» | 04 §2.4 |
| D-10 | Объекты всех видов в `objects`/`object_versions` | Отдельные таблицы на вид | Единые указатели, CS, ссылки, публикации | 07 §1 |
| D-11 | Рабочая версия в CS изменяема; история — операции | Новая версия на каждую операцию | Размер хранения; неизменяемость сохраняется на уровне операций и зафиксированных версий | 07 §1 |
| D-12 | Head + published-указатели по окружениям; публикация сливает CS | Отдельный этап merge без публикации | Меньше состояний для пользователя; продвижение между окружениями — отдельной командой | 06 §1, §7 |
| D-13 | Миграции схем — декларативные чистые функции с upcast при чтении | Только массовая миграция | Мгновенная согласованность без длинной блокирующей миграции | 05 §4 |
| D-14 | GraphQL — после MVP | GraphQL в MVP | Delivery API с разрешением данных по статическому анализу привязок закрывает потребность MVP | 08 §1 |
| D-15 | JSON Schema — единый источник типов IR; `proto/` удалён | Protobuf | IR — JSON-документ; JSON Schema проверяет его напрямую на обеих сторонах | 00 §5 |
| D-16 | River (PostgreSQL) для задач и outbox | Очередь на Redis | Транзакционная постановка задач вместе с изменениями | 12 §1.1 |
| D-17 | MCP встроен в сервер CMS | Отдельный сервис | Один Command Bus, без отдельного развёртывания | 09 §4 |
| D-18 | CMS не исполняет и не генерирует код по Missing Capability; передаёт задачу через webhook | Встроенный кодирующий агент с доступом к репозиторию | Нет секретов репозитория в CMS; код проходит обычный инженерный процесс | 09 §5 |
| D-19 | Индекс кода — без содержимого файлов | Индекс с фрагментами кода | Минимизация утечек; агент читает код сам со своими правами | 09 §6 |
| D-20 | Встроенные трансформации изображений через imgproxy | Делегировать фреймворку приложения | Независимость от фреймворка | 05 §6.2 |
| D-21 | Preview instance использует существующий стабильный ключ runtime с областью Repeat/Composed | Отдельный счётчик `<nodeId>:<n>` для DOM | Выбор сохраняет идентичность после перестановки элементов и различает вложенные экземпляры без второй системы ID | 10 §5.1, preview-bridge |
| D-22 | L1 schema validator генерируется как standalone AJV-код из исходной JSON Schema | Компиляция схемы в браузере через Function | Preview patch проверяет те же правила IR при строгом CSP без unsafe-eval; генерируемый код проверяется CI и conformance | 02 §11, 10 §5.2 |
| D-23 | Темы (светлая/тёмная) в Studio — после MVP; manifest допускает `modes` у цветовых токенов (закрывает Q-01) | Полная поддержка в MVP | Эксперимент не требует тем; формат уже совместим | 03 §1 (DS-003) |
| D-24 | События форм — через native-компонент `Form` из manifest (закрывает Q-02) | Примитив `Form` с полями | Валидация и отправка формы — код приложения; IR не растёт новым видом узлов | 02 §7 |
| D-25 | История агента в CMS — операции и `reason`; чаты не хранятся (закрывает Q-04) | Полный журнал чатов | Аудит изменений покрывают операции; чаты содержат контент и промпты, которые не нужно хранить | 09 §3 |
