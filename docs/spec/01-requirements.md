# 01. Требования

## 1. Продуктовая цель

Дать дизайнеру почти полную свободу вёрстки внутри промышленной дизайн-системы, сохраняя структурированность CMS. Возможности, выходящие за декларативные границы системы, формализуются как инженерные задачи для разработчика или программного агента.

## 2. Роли и права по умолчанию

| Роль | Основные возможности | Права по умолчанию |
|---|---|---|
| Редактор | Контент, ассеты, вставка готовых блоков, публикация в пределах прав | `content.read`, `content.write`, `content.publish`*, `design.read`, `asset.write` |
| Дизайнер | Композиция, сетки, адаптивность, создание Composed-компонентов | `design.read`, `design.compose`, `component.write`, `content.read`, `content.write`, `capability.request` |
| Разработчик | Регистрация manifest, схемы, действия, источники данных | `schema.read`, `schema.propose`, `schema.apply`, `manifest.register`, `behavior.propose`, `code.propose` |
| Администратор проекта | Пользователи, роли, политики, окружения | `project.admin` |
| Агент | Семантические операции в пределах выданных прав | Задаётся политикой; см. [09-agent.md](09-agent.md) |
| Сервис / миграция | Автоматизированные операции через Command Bus | Задаётся токеном |

\* Право на публикацию может быть ограничено политикой: окружением, уровнем риска, путём страницы.

Полный перечень прав — в [09-agent.md §2](09-agent.md#2-модель-прав).

## 3. Функциональные требования

### 3.1. Общие

| ID | Требование |
|---|---|
| FR-001 | Все изменения состояния CMS ДОЛЖНЫ выполняться через Command Bus. Studio, внешний API, агент и миграции используют одни и те же команды. |
| FR-002 | Studio НЕ ДОЛЖНА иметь привилегированных путей записи, недоступных через публичный Command API. |
| FR-003 | Каждое изменение ДОЛЖНО записываться как неизменяемая операция с актором, временем, целью, типом, данными «до» и «после», причиной и источником. |
| FR-004 | Изменения production ДОЛЖНЫ проходить через Change Set, валидацию, политику и (если требует политика) согласование. |
| FR-005 | Произвольный исполняемый код НЕ ДОЛЖЕН создаваться или исполняться из CMS как часть дизайнерского действия. |
| FR-006 | Система ДОЛЖНА поддерживать несколько проектов, изолированных друг от друга. |

### 3.2. Дизайн и композиция

| ID | Требование |
|---|---|
| FR-010 | Дизайнер ДОЛЖЕН создавать новые визуальные блоки из примитивов без программирования. |
| FR-011 | Дизайнер ДОЛЖЕН сохранять фрагмент композиции как Composed-компонент с типизированными входами. |
| FR-012 | Изменения мышью, через структурный редактор и через агента ДОЛЖНЫ изменять один и тот же документ IR. |
| FR-013 | Режим свободы (STRICT / SYSTEM / FREE / CODE) ДОЛЖЕН задаваться на уровне проекта, страницы и зоны. |
| FR-014 | Адаптивные значения ДОЛЖНЫ задаваться для breakpoint'ов, объявленных в manifest. |
| FR-015 | Система ДОЛЖНА поддерживать коллекции (повтор шаблона по списку) и условный показ узлов. |

### 3.3. Контент

| ID | Требование |
|---|---|
| FR-020 | Разработчик ДОЛЖЕН определять схемы контента с типизированными полями. |
| FR-021 | Редактор ДОЛЖЕН создавать и редактировать сущности контента и заполнять Composed-компоненты структурированным контентом. |
| FR-022 | Модель данных ДОЛЖНА поддерживать локализацию полей. Интерфейс многоязычного редактирования в MVP МОЖЕТ отсутствовать. |
| FR-023 | Изменение схемы ДОЛЖНО сопровождаться миграцией существующих сущностей, если изменение несовместимо. |

### 3.4. Версии и публикация

| ID | Требование |
|---|---|
| FR-030 | Работа над изменениями НЕ ДОЛЖНА влиять на опубликованное состояние до публикации. |
| FR-031 | Публикация Change Set ДОЛЖНА быть атомарной по всем затронутым объектам в пределах окружения. |
| FR-032 | Rollback ДОЛЖЕН возвращать предыдущее опубликованное состояние переключением указателей, без пересборки контента. |
| FR-033 | История ДОЛЖНА давать diff, причину, автора, цепочку согласования для каждого изменения. |

### 3.5. Preview

| ID | Требование |
|---|---|
| FR-040 | Preview ДОЛЖЕН отображать настоящее приложение, получающее черновое состояние через SDK. |
| FR-041 | Studio ДОЛЖНА поддерживать выбор узла, hover, изменение свойств и viewport через протокол сообщений с приложением. |

### 3.6. Агент

| ID | Требование |
|---|---|
| FR-050 | Агент ДОЛЖЕН получать структуру страницы, схемы, компоненты и capabilities через семантические инструменты. |
| FR-051 | Агент ДОЛЖЕН изменять CMS только через семантические операции в Change Set. |
| FR-052 | При отсутствии нужного поведения система ДОЛЖНА сформировать Missing Capability со структурированным контекстом. |
| FR-053 | Агент ДОЛЖЕН получать минимально необходимый контекст репозитория, а не весь репозиторий. |

## 6. Границы MVP

### 6.1. Входит в MVP

1. Регистрация manifest и дизайн-системы приложения.
2. Создание блока из примитивов в режимах SYSTEM и FREE.
3. Сохранение композиции как Composed-компонента.
4. Наполнение компонента структурированным контентом.
5. Изменение того же блока агентом через MCP.
6. Preview настоящего React-приложения в Studio.
7. Валидация и согласование Change Set.
8. Публикация в React-приложение.
9. Rollback публикации.
10. Missing Capability: создание запроса, передача контекста, автоматическое закрытие после регистрации capability в manifest.

### 6.2. Не входит в MVP

Marketplace плагинов; конструктор workflow; A/B-тестирование; аналитика; полноценный интерфейс многоязычного редактирования; GraphQL; адаптеры Vue и Svelte; совместное редактирование (Yjs); семантический поиск; отдельная векторная БД; Kafka; Kubernetes; микросервисная декомпозиция; запланированная публикация; вебхуки для сторонних систем (кроме собственного CI).
