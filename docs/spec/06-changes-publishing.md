# 06. Операции, Change Set, публикация и rollback

## 1. Модель версий

Каждый версионируемый объект (сущность, документ IR, ассет) имеет:

- **версии** — неизменяемые снимки тела с монотонным номером;
- **head** — указатель на последнюю принятую (слитую) версию;
- **published[env]** — указатель на опубликованную версию в каждом окружении.

```
Article 0192…
  versions: v16 v17 v18 v19 [v20 — рабочая версия в CS-42]
  head            -> v19
  published[stg]  -> v19
  published[prod] -> v16
```

Draft из архитектуры v0.1 — это рабочие версии внутри открытого Change Set поверх head. Публикация и откат — перемещение указателей.

| ID | Требование |
|---|---|
| CHG-001 | Версии НЕ ДОЛЖНЫ изменяться после фиксации. |
| CHG-002 | Рабочие версии видимы только в контексте своего Change Set (preview, Query API с `changesetId`). |
| CHG-003 | Изменение head возможно только при слиянии Change Set или откате. |

## 2. Операции

### 2.1. Запись операции

```json
{
  "id": "0192f1d0-…",
  "changesetId": "0192f1cf-…",
  "seq": 17,
  "actor": { "id": "0192…", "kind": "agent", "onBehalfOf": "0192…" },
  "source": "agent",
  "timestamp": "2026-10-09T12:31:07.412Z",
  "target": { "kind": "document", "objectId": "0192f1c5-…" },
  "type": "node.setDesign",
  "payload": { "nodeId": "n_grid01", "set": { "gap": { "base": "md", "lg": "xl" } } },
  "before": { "gap": "md" },
  "after": { "gap": { "base": "md", "lg": "xl" } },
  "reason": "Увеличить воздух между колонками на десктопе",
  "clientOpId": "c-7f2a",
  "undoOf": null
}
```

| Поле | Описание |
|---|---|
| `actor.kind` | `human`, `agent`, `service`, `migration` |
| `actor.onBehalfOf` | Для агента — пользователь, от имени которого он действует ([09-agent.md §3](09-agent.md#3-идентичность-и-делегирование-агента)) |
| `source` | `studio`, `api`, `agent`, `migration`, `import` |
| `before` / `after` | Минимальные фрагменты, достаточные для обратной операции и diff |
| `clientOpId` | Идемпотентность на стороне клиента |
| `undoOf` | ID операции, которую отменяет эта |

### 2.2.1. Реализация (этап M2, первая итерация)

- Реализованы операции над документами: `document.create`, `document.setRoute`, `node.insert`, `node.remove`, `node.move`, `node.setProps`, `node.setDesign`, `node.setBinding`, `node.setCondition`, `node.setBehavior`, `node.rename`; остальные типы каталога появятся вместе с их функциями (контент — со схемами, `component.*` — с Composed-компонентами).
- Маршрут страницы (`path` в `document.create`, `document.setRoute {path | null}`) хранится в версии документа, а не в IR. Формат: `/` или сегменты из строчных латинских букв, цифр и `-._~` либо параметры `:имя`, до 512 символов (`PATH_INVALID`). Маршрут бывает только у страниц (`PATH_NOT_ALLOWED`). Маршруты сравниваются по форме — с параметрами, заменёнными на `:`: `/a/:x` и `/a/:y` совпадают. Форма маршрута, занятая head другой страницы, даёт `PATH_TAKEN` при операции (как и `PATH_INVALID`, `PATH_NOT_ALLOWED` — это `operationCode` ошибки `OPERATION_INVALID`); публикация, `promote` и откат проверяют занятость в head и в окружении (`409 PATH_TAKEN`). Маршрут входит в хэш содержимого (PUB-004), а `document.setRoute` переигрывается при rebase по правилам операций над полями. Ограничение: две страницы не могут обменяться маршрутами в одной публикации — это делается в два шага.
- Индекс в `node.insert` и `node.move` необязателен (по умолчанию — конец списка); для `node.move` это позиция в целевом списке после изъятия узла.
- Пустые коллекции, оставшиеся после операции (`children`, слот, `slots`, `props`, `design`, `bindings`, `on`), удаляются. Благодаря этому операция и обратная ей возвращают документ к исходному виду в точности; это свойство проверяется тестами на случайных документах.
- Обратная операция вычисляется при применении и хранится в `operations.inverse`; `document.create` не отменяется (`UNDO_NOT_SUPPORTED`) — создание отменяется закрытием Change Set.
- Валидация после операции пока ограничена уровнем L1 (структура); L2–L6 добавятся вместе с manifest и политиками.
- Изменять Change Set может только владелец; соавторы (`changeset_collaborators`) и слияние частых операций (§2.3) — следующие итерации.

### 2.3. Слияние частых операций

Чтобы ввод текста и перетаскивание ползунка не создавали тысячи операций, клиент передаёт `coalesceKey` (например, `setDesign:n_grid01:gap`).

| ID | Требование |
|---|---|
| CHG-020 | Операция с тем же `coalesceKey`, от того же актора, следующая сразу за предыдущей в том же CS не позднее чем через 3 с, ДОЛЖНА сливаться с ней: `before` сохраняется от первой, `after` и `payload` — от последней. |
| CHG-021 | Операция «запечатывается» (становится неизменяемой) при добавлении любой другой операции в CS, через 3 с или при `submit`. |

### 2.4. Undo / redo

Команда `undo {changesetId}` добавляет обратную операцию с `undoOf`; `redo` — повторную. История не переписывается. Undo доступен только для операций в открытом Change Set.

## 3. Change Set

### 3.1. Атрибуты

| Атрибут | Описание |
|---|---|
| `kind` | `standard`, `schema`, `migration`, `rollback` |
| `title`, `description` | Заполняются автором; для агента — обязательны |
| `owner` | Актор-создатель; `collaborators` — дополнительные авторы-люди |
| `targets` | Окружения, в которые планируется публикация (влияет на набор требуемых согласований) |
| `bases` | Для каждого затронутого объекта — версия head на момент первого изменения |
| `risk` | Вычисляемый уровень риска (§5.2) |
| `state` | Состояние (§3.2) |

### 3.2. Состояния

```
          ┌──────────── reopen ────────────┐
          ▼                                │
 open ─submit─▶ checking ─ok─▶ in_review ─approve(все)─▶ approved ─publish─▶ merged
  │                │                │                       │
  │             failed ─reopen──────┤                    rebase при смене head
  │                          changes_requested ─reopen─▶ open
  └─abandon─▶ abandoned
```

| Переход | Условие |
|---|---|
| `submit` | Есть хотя бы одна операция; нет неразрешённых конфликтов |
| `checking → in_review` | Все блокирующие проверки §5 пройдены |
| `checking → failed` | Хотя бы одна блокирующая проверка не пройдена |
| `in_review → approved` | Получены все требуемые согласования (§5.3); при нулевом требовании — сразу |
| `approved → merged` | `publish` в первое окружение: head сдвигается, создаётся публикация |
| `* → open` (`reopen`) | Автор вносит правки; полученные согласования сбрасываются |

| ID | Требование |
|---|---|
| CHG-030 | Операции принимаются только в состоянии `open`. |
| CHG-031 | Команды над CS используют оптимистичную блокировку: клиент передаёт `expectedSeq`; несовпадение — `409 CHANGESET_SEQ_CONFLICT`. |
| CHG-032 | Studio создаёт персональный CS автоматически при первом изменении, если у пользователя нет открытого CS для текущего документа. |
| CHG-033 | Пустой открытый CS удаляется через 24 ч; непустой без активности 30 дней — переводится в `abandoned` с уведомлением владельцу. |

## 4. Конфликты и rebase

Когда head объекта сдвинулся после того, как CS зафиксировал базу, CS ДОЛЖЕН быть перебазирован перед `submit` и перед `publish`.

### 4.1. Алгоритм

1. Для каждого объекта, где `bases[obj] ≠ head(obj)`, берётся тело head.
2. Операции CS по этому объекту проигрываются по порядку `seq`.
3. Предусловия операции:
   - `set`/`unset`: текущее значение по пути равно `before` операции **или** уже равно `after` (операция становится пустой);
   - узловые операции: целевой узел, родитель и слот существуют; вставка по `index` ограничивается длиной списка;
   - `node.remove`: узел существует (иначе операция пустая).
4. Невыполненное предусловие — конфликт; операция помечается `conflict`.
5. При отсутствии конфликтов `bases` обновляются, рабочие версии пересоздаются.

### 4.2. Разрешение

Для каждого конфликта автор выбирает: **«оставить моё»** (операция переигрывается с текущим значением как новым `before`) или **«принять их»** (операция исключается из CS операцией-отменой). Пока конфликты не разрешены, CS находится в `open` с флагом `hasConflicts`.

| ID | Требование |
|---|---|
| CHG-040 | Автоматический rebase без конфликтов сохраняет согласования для CS с риском `low` и `medium`; для `high` — сбрасывает. |
| CHG-041 | Rebase с конфликтами всегда сбрасывает согласования. |
| CHG-042 | Studio ДОЛЖНА показывать присутствие других пользователей и открытые CS других авторов по текущему документу, чтобы снизить число конфликтов. |

### 4.4. Реализация (этап M2, третья итерация)

- Команда `rebase-changeset {changesetId, expectedSeq, resolutions?}` доступна владельцу CS в состояниях `open`, `failed`, `changes_requested`, `in_review`, `approved`. Переносятся только объекты, у которых head отличается от базы; seq Change Set не меняется. Ответ: `rebased` (перенесённые объекты), `removed` (объекты, все операции над которыми исключены), `conflicts`, `changeset` и, для поданного CS, повторённые `checks`.
- Операции объекта проигрываются по `seq` поверх тела нового head; для каждой пересчитываются «до», «после» и обратная операция. Операции изменения полей (`node.setProps`, `node.setDesign`, `node.setBinding`, `node.setBehavior`, `node.setCondition`, `node.rename`) конфликтуют (`BEFORE_MISMATCH`), если их «до» не совпадает с текущим значением; если текущее значение уже равно результату операции, операция становится пустой. Для `node.insert`, `node.move`, `node.remove` предусловие — применимость: `node.remove` уже удалённого узла исключается (`dropped`), индекс за концом списка заменяется вставкой в конец, прочие ошибки — конфликт `OPERATION_INAPPLICABLE`. Если первая публикация объекта откачена и head больше нет, каждая операция над ним — конфликт `OBJECT_GONE`.
- Решение `mine` переигрывает операцию поверх текущего значения и доступно только для `BEFORE_MISMATCH`; `theirs` исключает операцию (`status = dropped`), а вместе с ней — её отмену (`undoOf`). Объект, все операции над которым исключены, выходит из CS вместе с рабочей версией.
- При неразрешённых конфликтах рабочие версии и базы не меняются: операции помечаются `conflict`, у CS ставится `hasConflicts`, поданный CS возвращается в `open` со сбросом согласований (CHG-041). `submit-changeset` с конфликтами отклоняется `409 CHANGESET_HAS_CONFLICTS`; операции можно продолжать добавлять.
- Без конфликтов поданный CS остаётся на проверке: проверки повторяются для нового содержимого, согласования переносятся на новый хэш содержимого (CHG-040; для риска `high` — сбрасываются), состояние пересчитывается (`failed`, `in_review` или `approved`; `changes_requested` сохраняется). Если после rebase в CS не осталось объектов, он возвращается в `open`; подача пустого CS отклоняется `CHANGESET_EMPTY`.
- Чтобы повторное применение `node.insert` давало те же узлы, в журнал записывается payload с назначенными ID поддерева. Статус операции (`applied`, `conflict`, `dropped`) возвращается в `GET /changesets/{id}/operations`.

### 4.3. Совместное редактирование (после MVP)

Совместное редактирование через Yjs будет реализовано как транспорт и presence для **одного** Change Set с несколькими авторами. Серверный мост преобразует обновления Y-документа в операции каталога §2.2 и проводит их через Command Bus; отклонённые политикой изменения возвращаются клиентам как корректирующее обновление. Нормализованный IR со стабильными ID узлов напрямую отображается на `Y.Map` и не требует изменения формата.

### 5.2. Уровень риска

Риск CS — максимум по правилам:

| Риск | Правило |
|---|---|
| `low` | Только `entity.setFields`, `localContent.*`, `asset.updateMeta` в существующих объектах |
| `medium` | Структурные и дизайн-изменения документов; новые страницы и сущности; изменения поведения с существующими действиями; изменения компонента, затрагивающие ≤ 10 опубликованных страниц |
| `high` | Изменения в зонах STRICT; изменения компонента, затрагивающие > 10 опубликованных страниц; схемы; удаление опубликованных объектов; изменения политик и маршрутов опубликованных страниц |

Политика проекта МОЖЕТ повышать риск (например, `source = agent` → минимум `medium`) и добавлять правила по путям и схемам.

### 5.3. Согласование

| ID | Требование |
|---|---|
| PUB-001 | Число и роли согласующих определяются политикой по риску, окружению и зонам. По умолчанию: `low` — 0 (если у автора есть `content.publish` для окружения), `medium` — 1, `high` — 2, из них один с ролью `requiredApprovalRole` затронутых зон. |
| PUB-002 | Согласующий НЕ ДОЛЖЕН быть автором ни одной операции CS, в том числе как `onBehalfOf` агента. |
| PUB-003 | Агенты и сервисные акторы НЕ ДОЛЖНЫ согласовывать Change Set. |
| PUB-004 | Согласование привязано к хэшу содержимого CS (множество пар «объект → хэш рабочей версии»). Изменение содержимого сбрасывает согласование, кроме случая CHG-040. |
| PUB-005 | Согласующий видит diff по объектам, результаты проверок, скриншоты, причину и источник каждой операции. |

## 7. Публикация, продвижение, откат

### 7.1. Публикация

`publish {changesetId, environment}` в одной транзакции БД:

1. Блокирует строки затронутых объектов (`SELECT … FOR UPDATE` в порядке ID).
2. Проверяет, что `bases` совпадают с head (иначе `409 REBASE_REQUIRED`).
3. Фиксирует рабочие версии, сдвигает head (если CS ещё не `merged`).
4. Для окружения сдвигает `published` указатели всех объектов CS.
5. Создаёт запись `publication` с прежними указателями (`previous`) и новыми (`current`).
6. Ставит в outbox задачи инвалидации кэшей и уведомлений.

| ID | Требование |
|---|---|
| PUB-020 | Публикация ДОЛЖНА быть атомарной по всем объектам CS в окружении (FR-031). |
| PUB-021 | Delivery API ДОЛЖЕН отражать публикацию не позднее чем через 10 с (p95) после фиксации транзакции. |
| PUB-022 | Публикация в окружение требует права `content.publish` для этого окружения и согласований, требуемых политикой для этого окружения. |

### 7.2. Продвижение между окружениями

`promote {publicationId, toEnvironment}` переносит указатели `current` публикации в целевое окружение, создавая новую публикацию. Перед этим повторяются этапы 1–7 pipeline против manifest и схем целевого окружения, а также собираются согласования, если политика целевого окружения требует больше, чем исходного.

### 7.2.1. Реализация (этап M2, четвёртая итерация)

- `promote {publicationId, toEnvironment}` (право `content.publish`) переносит версии `current` публикации вида `publish` или `promote` в другое окружение вида `standard`. Создаётся публикация вида `promote` со ссылкой на исходную (`sourcePublicationId`) и тем же `changesetId`. Новых версий не создаётся, head не меняется; объекты блокируются в порядке ID.
- Объекты, у которых в целевом окружении уже эта версия, пропускаются. Если пропущены все — `409 PROMOTE_NOTHING`.
- Если в целевом окружении опубликована более новая версия объекта (по номеру фиксации), перенос отклоняется `409 PROMOTE_OUTDATED` со списком объектов: вернуть окружение к старой версии можно только откатом. Другие ошибки: `PROMOTE_SAME_ENVIRONMENT`, `PROMOTE_NOT_SUPPORTED` (публикация вида `rollback`), `ENVIRONMENT_NOT_PUBLISHABLE`.
- Повторение этапов 1–7 pipeline против manifest и схем целевого окружения и согласования по политике окружения появятся вместе с manifest и политиками окружений: пока проверки не зависят от окружения и уже пройдены при подаче.

### 7.3. Откат

`rollback {publicationId, resetHead = true}`:

1. Проверяет, что для всех объектов публикации текущие `published[env]` равны `current` публикации. Если позднее объекты менялись другой публикацией — `409 ROLLBACK_SUPERSEDED` со списком публикаций; пользователь может откатить цепочку от последней.
2. Устанавливает `published[env] = previous` (для объектов, впервые опубликованных этой публикацией, — снимает публикацию).
3. При `resetHead` и `head == current` сдвигает head на `previous`; открытые CS по этим объектам получат rebase.
4. Создаёт CS вида `rollback` (состояние `merged`) и публикацию вида `rollback`.

| ID | Требование |
|---|---|
| PUB-030 | Откат НЕ ДОЛЖЕН создавать новые версии (только перемещение указателей) и ДОЛЖЕН укладываться в NFR-007. |
| PUB-031 | Откат требует `content.publish` в окружении; по умолчанию не требует согласования (аварийный путь). Политика МОЖЕТ потребовать согласование. Откат всегда попадает в журнал аудита. |
| PUB-032 | Откат публикации Composed-компонента с `live`-экземплярами возвращает его прежнюю версию на всех страницах. |

### 7.3.1. Реализация (этап M2, вторая итерация)

- Команды: `submit-changeset {changesetId, expectedSeq}`, `approve-changeset` и `request-changes {changesetId, comment}`, `reopen-changeset`, `publish {changesetId, environment}`, `rollback {publicationId, resetHead}`, `set-approval-policy {low, medium, high}`. Запросы: `GET /changesets/{id}/review`, `GET /publications?environment=`, `GET /publications/{id}`, `GET /documents/{id}?environment=` (опубликованная версия).
- Pipeline на подаче пока состоит из двух блокирующих этапов: `ir` (валидация L1 рабочих версий) и `policy` (права авторов на типы их операций на момент подачи). Проверки и согласования привязаны к хэшу содержимого: SHA-256 пар «ID объекта → хэш рабочей версии» в порядке ID (PUB-004).
- Риск: `low`, если все операции — контентные (§5.2); иначе `medium`. Правила `high` (зоны, схемы, удаление опубликованного) появятся вместе с соответствующими функциями.
- Политика согласований хранится в `projects.settings.approvals` и меняется командой `set-approval-policy` (право `project.admin`; значения 0…5, не убывают с ростом риска). Значения по умолчанию — из PUB-001; условие «`low` — 0, если у автора есть `content.publish`» и роли зон пока не проверяются. Пока в системе нет людей (вход через OIDC — следующий этап), PUB-003 делает согласование невозможным, поэтому проекту нужно снизить требования политики; для этого политика и вынесена в настройки.
- Повторное согласование тем же человеком не увеличивает счётчик; `request-changes` переводит CS в `changes_requested`. `reopen-changeset` возвращает CS в `open` из `failed`, `changes_requested`, `in_review` и `approved` и сбрасывает согласования.
- `publish` принимает только CS в состоянии `approved` и переводит его в `merged`; публикация того же CS в другое окружение будет выполняться через `promote` (§7.2, ещё не реализован). Публиковать можно только в окружения вида `standard` (MF-031). Номер версии присваивается при фиксации (максимум по объекту + 1).
- `rollback` не создаёт CS вида `rollback` (шаг 4): публикация вида `rollback` ссылается на исходную через `source_publication_id`, а причина отката хранится в `publications.reason`. Откат снимает с публикации объекты, впервые опубликованные исходной публикацией, и при `resetHead` возвращает head, если его не сдвигали.
- Команды `unpublish`, outbox инвалидации и таблица маршрутов — следующие итерации. Rebase описан в §4.4, `promote` — в §7.2.1.
- Откат с `resetHead` возвращает head только для публикаций вида `publish`: `promote` и `rollback` head не сдвигали, поэтому и их откат его не трогает.

### 7.4. Снятие с публикации

`unpublish {objectIds, environment}` выполняется через CS (риск `high`). Отклоняется, если на объекты ссылаются другие опубликованные объекты. Страница после снятия отдаёт 404 или настроенный редирект.
