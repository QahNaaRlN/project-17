# Сквозной сценарий §2 в CI

Статус: **черновик на одобрение пользователя; код не начат**.
Дата: 2026-10-21. Требования: STU-440…459 (STU-400…439 заняты пакетами
component.extract и условных политик агента).
Основа: `origin/dev` на `a6a9dc0` (после [PR #78](https://github.com/QahNaaRlN/project-17/pull/78)).
Цель — критерий готовности MVP 1 ([план §3](spec/14-mvp-plan.md#3-критерии-готовности-mvp)):
[сценарий §2](spec/14-mvp-plan.md#2-сквозной-сценарий-приёмки) проходит
автоматически в CI. Уровень тестов — «Сквозные» [testing §2, §3.5](testing.md#2-уровни-тестов).

## 1. Проблема и границы

Сейчас `pnpm --filter @cms/store-example test:e2e` в job `Check` гоняет
Playwright против детерминированной **фикстуры** CMS (`e2e/serve.ts`,
`e2e/studio-fixture.ts`): настоящие SDK, SSR, Studio-BFF и браузер, но сервер,
БД, River, pipeline и MCP — подмена. Шаги §2 проверены по пакетам локальными
приёмками (`docs/*-acceptance.md`) на изолированном стенде
[`studio-review-stand.mjs`](../scripts/studio-review-stand.mjs) — вручную, разными
скриптами, с ручной сборкой. Сквозного прогона всех 10 шагов одной историей
против настоящего CMS в CI нет.

Пакет добавляет **один** Playwright-сценарий из 10 шагов на `examples/react-store`
против настоящих CMS/PostgreSQL/River/Studio/витрины, запускаемый в CI на каждом
PR. Существующие фикстурные E2E остаются (они быстрые и проверяют граничные
случаи UI); новый сценарий их не заменяет.

Вне пакета: нагрузочные NFR-001…007 (k6, отдельный пакет M6), реализация этапов
pipeline 8–9 и `promote` в Studio (свои пакеты), реальные GitHub/LLM/CDN.

## 4. Стенд

```
GitHub Actions (ubuntu-latest)
 ├─ services.postgres: postgres:16 (127.0.0.1:5432)
 ├─ cms (go build ./cmd/cms) — HTTP API, MCP, River, purge → receiver
 ├─ dev-oidc.mjs — Alice, Bob, Erin (editor)
 ├─ studio (apps/studio/dist/server)
 ├─ store-staging, store-production (examples/react-store/dist/server)
 ├─ e2e-purge-receiver.mjs
 └─ [Q-2a] e2e-github-fixture.mjs
```

- PostgreSQL — `services` GitHub Actions; локально — тот же оркестратор с
  `CMS_DATABASE_URL` на любой loopback PostgreSQL (docker). Docker compose не
  вводится: процессы уже запускает `studio-review-stand.mjs`, а compose добавил
  бы второй способ поднимать то же самое.
- Оркестратор: миграции, проект, окружения, роли, ключи доставки, запуск
  процессов, ожидание готовности, файл конфигурации для теста, остановка и сбор
  журналов. Запуск локально: `pnpm e2e:scenario` (сборка + стенд + сценарий).
- Сборки: CMS — `go build`; Studio и витрина — `pnpm build` того же job; для
  шага 10 базовая сборка витрины без `store.quickView`.

## 6. Пороги времени

Один прогон CI — не нагрузочный тест: p95 из выборки на общем runner'е шумный.
Поэтому ограничения §2 проверяются гейтами с допуском, а подтверждение NFR
остаётся за пакетом нагрузочных тестов.

| Ограничение | Как измеряется | Выборка | Гейт CI (рекомендация Q-3) |
|---|---|---|---|
| Шаг 4: правка поля сущности видна в preview < 1 с (IR-044) | от ответа `apply-operations` до текста в iframe | 10 правок | p95 ≤ 1 с, ни одна > 2 с |
| Шаг 6: `document.patch` < 400 мс (NFR-005) | от изменения свойства в Studio до кадра с новым значением в iframe (`requestAnimationFrame` после сообщения) | 20 правок | p95 ≤ 600 мс (1.5×), значения в отчёт |
| Шаги 8–9: видимость в production ≤ 10 с | от ответа `promote`/`rollback` до нового/старого текста на production-витрине (SSR-запрос без кэша браузера) | 1 + 1 | ≤ 10 с строго |
| Шаг 2: preview 375/1024 | вычисленные стили, не время | — | функциональная проверка |

## 7. Незавершённые части

Реестр `e2e/scenario/pending.ts` (STU-455):

| Шаг | Проверка | Временно | Становится строгой |
|---|---|---|---|
| 7 | Этапы pipeline 8 (preview build) и 9 (axe) `passed` | Проверяются этапы 1–7, 13; отсутствие 8–9 фиксируется аннотацией | Когда результаты этапов 8–9 появляются в `checks` — запись удаляется пакетом этапов M6, иначе тест падает «pending выполнен» |
| 8 | `promote` через Studio | `promote` командой API от имени Bob | Когда в Studio есть кнопка переноса — запись удаляется пакетом M4 |

Каждая запись ссылается на строку плана MVP. Иных пропусков (`test.skip`,
`fixme`) в сценарии нет.

## 8. Место в CI

- Новый job рядом с `check`, на тех же триггерах; кэш pnpm и Go как в `check`.
  Существующий шаг «Storefront browser scenarios» остаётся без изменений.
- Ожидаемое время: сборки ~4 мин, стенд ~1 мин, сценарий ~5–7 мин (две сборки
  витрины, pipeline, ожидание задачи выполнения ≤ 10 с цикла STU-339).
- Нестабильность разбирается как дефект: повтор job вручную допустим только для
  диагностики, а не как способ «позеленить».

## 10. Критерии приёмки пакета

- Сценарий проходит в CI на PR пять прогонов подряд без повторов; время job ≤ 15 мин.
- Вмешательство в любую проверку шага (например, отключённая инвалидация,
  литерал вместо токена, согласование автором) делает тест красным — проверяется
  разовым экспериментом с патчами, результат в отчёте.
- Реестр pending содержит только §7; гейты §6 включены; артефакты загружаются.
- Существующие проверки CI, пороги покрытия и фикстурные E2E не ослаблены.
- Локальный запуск одной командой описан и проверен на Windows и Linux.

## 11. Открытые вопросы и рекомендации

1. **Q-1. Обязательность job.** Рекомендация: обязательная проверка для PR в
   `dev` и `main` после пяти зелёных прогонов (критерий приёмки); до этого — не
   обязательная, но видимая. Альтернатива — обязательна сразу.
2. **Q-2. GitHub в шаге 10.** (a) loopback-сервер фактов в бинаре с тегом `e2e`
   (обычная сборка не может указать другой хост); (b) запись фактов PR/CI в БД,
   как в локальных приёмках. Рекомендация: **(a)** — проходит настоящий клиент и
   задача наблюдения, а продуктовый бинарь не меняется; (b) — только если тег
   сборки сочтут лишней сложностью.
3. **Q-3. Гейты времени.** Рекомендация: таблица §6 (NFR-005 с допуском 1.5×,
   IR-044 и ≤ 10 с строго). Альтернатива — только измерять и отчитываться.
4. **Q-4. Production на стенде.** Рекомендация: второе окружение и вторая
   витрина в том же CMS (STU-442). Альтернатива — одна витрина с переключением
   окружения, но тогда шаги 8–9 не проверяют изоляцию окружений.
5. **Q-5. Фикстуры витрины.** Рекомендация: добавить `Collection`, `ProductCard`
   (`variant`) в `examples/react-store` как постоянную часть примера (STU-447),
   а `store.quickView` — только патчем шага 10. Альтернатива — отдельный
   e2e-манифест, но тогда шаг 1 проверяет не настоящий `manifest push` примера.
