Статус: **черновик на одобрение пользователя; решения §11 не приняты**.
Дата: 2026-10-29. Требования: STU-630…649 (STU-610…629 заняты
[сверкой спецификации](spec-reconciliation.md)).
Основа: `origin/dev` на `99704c1` (после [PR #108](https://github.com/QahNaaRlN/project-17/pull/108)).
Строка плана MVP: M6, пакет 8 «Набор для эксперимента и пороги Q-08 на утверждение».

## 1. Проблема и границы

Протокол эксперимента — [14 §4](spec/14-mvp-plan.md#4-протокол-эксперимента): не менее
9 дизайнеров, три условия (A — Webflow-подобный редактор, B — CMS вручную, C — CMS +
агент), латинский квадрат 3×3, три эталонных макета по 15–25 блоков и 3 breakpoint'а,
45 минут обучения на инструмент, 3 часа на задание, инженер на связи. Метрики — §4.2,
предлагаемые пороги — §4.3 (Q-08, срок «до M6»).

Сейчас протокол есть только текстом: нет макетов, стенда для сессий, инструментов
измерения, форм опросников и сводного отчёта. Каждый показатель пришлось бы считать
вручную и по-разному для разных участников.

Пакет делает эксперимент воспроизводимым:

- три эталонных макета сопоставимой сложности и дизайн-система витрины для них;
- стенд и отдельный проект на каждую сессию с нужным условием;
- журнал сессии, автоматические измерения метрик §4.2 и сводный отчёт против порогов;
- формы SUS и NASA-TLX, сценарий ведущего, пилотный прогон;
- измерение NFR-016, STU-030, STU-031 ([ADR-0003](adr/0003-unmeasured-performance.md));
- пороги Q-08 на утверждение до основного прогона.

Вне пакета: набор участников, проведение основных сессий и выводы по их результатам;
недостающие функции Studio ([ADR-0015](adr/0015-m4-editor-gaps.md)) — отдельные пакеты
M4 (решение §11.2 определяет, нужны ли они до эксперимента); production-развёртывание.

## 4. Сессия

1. Ведущий берёт строку `plan.json`, запускает `experiment:session` и журнал.
2. 45 минут обучения на инструменте условия (материалы одинаковой структуры для A, B, C).
3. Участник получает макет и начинает: журнал фиксирует старт; обращения к инженеру —
   отдельными записями.
4. Участник заявляет «готово» → `experiment:check`. Есть дефекты — участник продолжает;
   нет — время фиксируется. Через 3 ч задание завершается принудительно.
5. Опросники SUS и NASA-TLX.
6. После сессии: `experiment:collect` снимает результат (IR, CSS, скриншоты, axe,
   Missing Capability) в каталог сырых данных сессии.

## 8. Критерии приёмки пакета

- Пилот прошёл во всех трёх условиях; отчёт пилота построен `experiment:report` без
  ручных расчётов.
- Эталонная реализация каждого макета проходит `experiment:check` с 0 дефектов и даёт
  визуальное несоответствие ниже порога калибровки.
- Измерения NFR-016, STU-030, STU-031 записаны; при нарушении цели — исправление или ADR.
- Пороги Q-08 утверждены и записаны решением D-xx.
- Проверки CI, пороги покрытия, сценарий §2 и `Load` не ослаблены.

## 10. Риски

- Пробелы Studio (вставка компонентов, буфер) замедляют условие B независимо от гипотезы;
  решение §11.2.
- Девять участников дают низкую статистическую мощность: отчёт показывает медианы и
  разброс, а не проверку значимости; это ограничение протокола, а не набора.
- Расход и доступность LLM в условии C: лимит на сессию и запасной ключ.
- Порядок и обучение влияют на время: латинский квадрат уравновешивает порядок, но не
  перенос навыка между макетами.

## 11. Вопросы на решение

1. **Инструмент условия A.**
   - (а) Webflow (бесплатный план), сайт публикуется на поддомене Webflow; аудит CSS по опубликованному сайту.
   - (б) Открытый конструктор (GrapesJS) на стенде.

   Рекомендация — (а): протокол сравнивает с Webflow, знакомство участников с ним
   фиксируется; открытый конструктор слабее и сдвинет сравнение в пользу CMS.
2. **Пробелы Studio до эксперимента.**
   - (а) До основного прогона реализовать каталог и вставку Composed-компонентов и буфер поддерева (пакеты M4).
   - (б) Проводить с текущей Studio, пробелы — ограничение в отчёте.

   Рекомендация — (а): без вставки готовых компонентов блок из 15–25 элементов собирается
   из примитивов, и условие B измеряет недостающие функции, а не гипотезу. Набор
   реализуется параллельно; пилот можно провести на текущей Studio.
3. **Недостающий элемент в макетах.**
   - (а) В каждом макете ровно один элемент, которого нет в manifest (поведение или компонент), одинаковой сложности.
   - (б) Все элементы макетов есть в manifest.

   Рекомендация — (а): порог «без обращений за кодом вне Missing Capability» проверяется,
   только если такая ситуация возникает; одинаковый элемент на макет сохраняет сопоставимость.
4. **Когда задание считается выполненным.**
   - (а) Участник заявляет «готово», автоматическая проверка STU-637 проходит с 0 дефектов.
   - (б) Решение эксперта.

   Рекомендация — (а): одинаковый для всех условий и не зависит от наблюдателя.
5. **Запись экрана.**
   - (а) Без записи: журнал, автоматические измерения, опросники.
   - (б) Запись экрана с согласия для качественного разбора.

   Рекомендация — (а): метрики протокола записи не требуют; запись — персональные данные
   с хранением и удалением, которые набор тогда должен обеспечить.
6. **LLM в условии C.**
   - (а) Одна модель для всех сессий, выбранная на пилоте; лимит расхода на сессию.
   - (б) Модель на выбор участника.

   Рекомендация — (а): разные модели — дополнительная переменная эксперимента.
7. **Утверждение порогов Q-08.**
   - (а) Утвердить пороги 14 §4.3 как есть до пилота; после пилота они не меняются.
   - (б) Утвердить после пилота с поправками.

   Рекомендация — (а): пороги фиксируются до данных, иначе пилот подгоняет критерии под
   результат. Пилот исправляет набор и измерения, не пороги.
8. **Измерения ADR-0003 в этом пакете.**
   - (а) Да, в пакете (STU-646).
   - (б) Отдельным пакетом.

   Рекомендация — (а): ADR-0003 относит их к набору; нужен тот же документ на 500 узлов.
