# Studio: вход пользователей и доступ к согласованию

Универсальный OIDC Authorization Code + PKCE (S256), server-side exchange и
проверка подписи/issuer/audience/срока/nonce через go-oidc. Провайдер настраивается
оператором; пароли и токены провайдера не попадают в Studio. Идентичность —
`(issuer, sub)`, не email. Новый человек получает ноль прав до явного назначения роли.

| ID | Контракт |
|---|---|
| STU-080 | OIDC discovery/client/callback настраиваются явно; state привязан к браузеру, одноразовый, живёт 10 минут; PKCE и nonce обязательны. HTTPS обязателен, HTTP допускается только для явно включённого loopback development. Ошибки входа не раскрывают код, токены, секреты или ответы провайдера. |
| STU-081 | После входа выдаётся новая случайная серверная сессия на 8 часов, в БД хранится её хэш. Cookie HttpOnly/Secure/SameSite=Lax, host-only/path=/; development исключение Secure только на loopback. Logout отзывает сессию на сервере и очищает cookie. Все команды cookie-сессии требуют правильный Origin и связанный CSRF-токен. Права, disabled actor и принадлежность проекту проверяются на каждом запросе. |
| STU-082 | Studio показывает человека и вход/выход на ru/en. В OIDC-режиме сервисный credential запрещён; запросы используют только cookie текущего пользователя, без fallback. Нет сессии/нет доступа/истёкшая сессия показаны явно. Смена пользователя уничтожает редактор, query cache и CSRF предыдущего пользователя; неподтверждённые команды не переигрываются от нового актора. |
| STU-083 | Пользователь с design.read + content.publish видит страницы CS in_review/approved для окружения, включая чужие рабочие страницы, и открывает их без ID. Владелец продолжает свои failed/changes_requested/in_review/approved CS; чтение не выдаёт право редактировать. Авторство, человеческая природа и роли согласования проверяются прежними server handlers. |
| STU-084 | Права людей назначаются явно публичными admin-командами создания роли и привязки/отвязки человека. Чужая роль/проект, service actor, disabled actor и неизвестные capabilities отклоняются. Саморегистрация/одинаковый email не выдаёт права. Приёмка: два настоящих OIDC-входа → автор сохраняет/подаёт → другой человек согласует → явная публикация; авторское согласование отклонено. |

Сервисный режим сохраняется как явный локальный режим совместимости. Production
deploy, выбор/настройка реального IdP, каталог всех проектов и полноценная админ-панель
ролей, федеративный logout/revocation/back-channel и соавторское редактирование
не входят в пакет. Серверные сессии и логины хранятся в PostgreSQL, не в памяти BFF.

## Явное назначение доступа

Администратор проекта использует существующий публичный Command API с
`X-CMS-Project`, своим Bearer-токеном (или cookie + Origin/CSRF) и уникальным
`Idempotency-Key`. Токен в примеры и репозиторий не помещается.

1. `POST /api/v1/commands/create-role`:
   `{"payload":{"name":"studio-author","capabilities":["design.read","content.read","design.compose","content.write","content.publish"]}}`.
2. Вторую роль `studio-reviewer` создать с
   `design.read`, `content.read`, `content.publish`.
3. `POST /api/v1/commands/bind-human-role`:
   `{"payload":{"actorId":"<ID человека из Studio>","roleId":"<ID созданной роли>"}}`.
   Повторная привязка безопасна. Email и группы IdP не назначают роли.
4. Для отзыва: `POST /api/v1/commands/unbind-human-role` с теми же двумя ID.
   Отзыв прав действует на следующем запросе; `disabled_at` актора также
   прекращает использование всех его сессий.

Чтение собственной работы не зависит от возможности согласовать её. Чужая работа
показывается согласующему только в `in_review`/`approved`, в выбранном проекте и
окружении. Открытие не снимает ограничения владельца; публикация и согласование
проходят через прежний Command Bus с прежней политикой.

## Приёмка и следующий пакет

Go-тесты используют подписывающий RS256 тестовый IdP, реальный verifier/JWKS,
PKCE exchange и PostgreSQL; два OIDC-входа проверяют авторство, согласование,
публикацию и отзыв роли. Chromium проверяет Studio и приложение; IdP/CMS там
моделируются только на публичной HTTP-границе. Это не проверка реального провайдера.

Structure с CodeMirror/JSON diff реализован в [пакете JSON](studio-json-diff.md)
(STU-010/011, STU-090…094): правка преобразуется в операции с историей,
сервер проверяет IR/manifest. Content editor реализован в [пакете контента](studio-content.md).
Пакет [SSE/presence](studio-realtime.md) реализован; следующий пакет — Agent.
