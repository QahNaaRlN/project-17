# Нагрузочные тесты NFR-001…007: отчёт

Спецификация: [docs/load-tests.md](load-tests.md) (STU-540…559), запуск —
[perf/README.md](../perf/README.md). Критерий готовности MVP 2 отмечается выполненным
после трёх зелёных прогонов workflow `Load` подряд на `dev` (решение §11.7).

## Окружение

GitHub-hosted `ubuntu-latest` (параметры каждого прогона — `environment.json` в
артефакте `load-results`). PostgreSQL 16 (`shared_buffers=1GB`), Redis 7, nginx 1.27
и k6 1.0.0 — в контейнерах на той же машине, что и `cms serve`; генератор нагрузки
делит процессор со стендом, поэтому измерения консервативны. Данные — полный профиль
01 §5: 20 проектов × 100 000 сущностей × 10 000 страниц.

### История

Первый прогон, где все этапы дошли до конца, —
[Load 40544082979](https://github.com/QahNaaRlN/project-17/actions/runs/40544082979)
(`98739c4`, загрузка данных 1088 с):

| NFR | p95 / максимум | Итог |
|---|---|---|
| NFR-001 | 0,9 / 624 мс | ✅ |
| NFR-002 | 49,5 / 331 мс | ✅ |
| NFR-003 | 70,8 / 654 мс | ✅ |
| NFR-004 | 283,8 / 1035 мс | ✅ |
| NFR-005 | 3173 мс (медиана ~1000) | ❌ |
| NFR-006 | 1,27 / 1,30 с | ✅ |
| NFR-007 | 1,20 / 1,36 с | ✅ |

NFR-005 измеряется сценарием §2 на втором сервере под той же фоновой нагрузкой; на той
же машине с 4 vCPU работают Studio, витрины, исполнитель проверок и три браузера
Playwright. Все запросы этого сервера в окне сценария в 3–5 раз медленнее, чем в
измеряемом прогоне, включая тривиальные: `GET /auth/session` — p50 27 мс, p95 223 мс;
попадание Delivery — p95 ~150 мс против 49,5 мс; `apply-operations` — p50 263 мс,
p95 628 мс. Это признак нехватки процессора на стенде, а не отдельного медленного пути.

Чтобы проверить это напрямую, стенд во время сценария §2 пишет:
- `cpu.jsonl` — каждые 5 с загрузку машины (busy, iowait, steal, load1) и ядра по именам
  процессов из `/proc`;
- `cpu-summary.json` — сводку: средняя загрузка и p95, доля замеров с загрузкой выше 90 %,
  средние ядра по процессам;
- `profiles/cms-cpu-*.pprof` — CPU-профили CMS сценария по 20 с подряд. pprof открыт только
  в e2e-сборке через `CMS_E2E_PPROF_ADDR` и только на 127.0.0.1.

Посмотреть профиль: `go tool pprof -top perf/results/profiles/<файл>`.

Прогон [Load 40579260532](https://github.com/QahNaaRlN/project-17/actions/runs/40579260532)
(`3d98a7e`) с этими замерами подтвердил нехватку процессора и нашёл причину в коде:

- NFR-005: 20 замеров, медиана ~290 мс, p95 ~430 мс, максимум 599 мс — порог 400 мс
  превышен двумя замерами. Остальные NFR прошли.
- Машина (4 vCPU): средняя загрузка 85 %, p95 99,5 %, в 55 % замеров выше 90 %;
  iowait 1 %, steal 0, load1 до 5,8. Ядра по процессам в среднем: CMS 0,77, PostgreSQL
  0,59, браузеры Playwright 0,55, `docker-proxy` 0,27, Node 0,22, `ffmpeg` (видео
  Playwright) 0,20, k6 0,15.
- Профиль CMS: ~40 % CPU — `deliverycache.Get`, то есть `json.Unmarshal` записи кэша с
  телом в base64 (проверка JSON, разбор строки, base64) на каждом попадании в Redis;
  ~26 % — `apply-operations`, половина из них — проверка документа по JSON Schema.

Исправлено (находка 7) и выключена запись видео Playwright в нагрузочном сценарии
(`E2E_VIDEO=off`: без видео и без скриншотов в трассах; DOM-снимки трасс остаются).

## Найдено и исправлено при подготовке

Отладочные прогоны на уменьшенных данных (Windows, Docker Desktop — не
подтверждение NFR) показали три причины в коде (STU-554):

1. **Чтение сущности через Delivery ждало правок.** `changes.GetContent` загружал
   схемы через `validation.Load`, который берёт `FOR UPDATE` на окружение; при
   одновременных правках в Studio `/entity` ждал их фиксации. Чтение теперь идёт без
   блокировки (`LoadSnapshot`), как Query API.
2. **Правки проекта выполнялись строго по очереди.** `apply-operations` брал
   `FOR UPDATE` на все окружения проекта; 50 редакторов одного проекта упирались в
   один поток (p95 1,24 с при 16 командах/с). Правки теперь берут те же строки в том
   же порядке `FOR SHARE` (`validation.Shared`): правки разных Change Set идут
   параллельно, публикация, manifest и политики (`FOR UPDATE`) по-прежнему ждут их и
   задерживают новые. В отладке p95 снизился до 378 мс.
3. **Каждый запрос с токеном писал в БД.** `TouchToken` обновлял
   `api_tokens.last_used_at` на каждом запросе — отдельная запись и сброс WAL.
   Обновление теперь не чаще раза в минуту на токен; в отладке p95 — 316 мс.

Прогоны полного профиля на Linux нашли ещё четыре причины:

4. **Промах страницы читал все маршруты проекта.** `GetPage` загружал 10 000 маршрутов
   окружения и сопоставлял путь в памяти, а `/routes` (около 1,1 МБ) не помещался в
   кэш с пределом записи 1 МиБ и всегда шёл в БД. Опубликованная страница теперь
   ищется по точному пути, шаблонные маршруты — отдельным запросом по частичному
   индексу (миграция 00030); предел записи кэша — 4 МиБ.
5. **Пул из 4 соединений.** Умолчание pgxpool — max(4, число ядер), на runner с
   4 vCPU это 4 соединения на все запросы и задачи River. Ключ Delivery проверяется
   в БД на каждом запросе, поэтому даже попадания в Redis ждали соединения до таймаута
   (p95 около 60 с), а River терял лидерство. Без `pool_max_conns` в
   `CMS_DATABASE_URL` пул теперь max(16, 4 × число ядер); в локальной отладке на
   многоядерной машине пул был больше, поэтому причина там не проявлялась.

6. **Публикация перепроверяла всё окружение.** Подача и публикация читали все
   ~110 000 опубликованных версий окружения с телами и проверяли каждую; подача CS из
   50 страниц на проекте полного размера заняла 300 с и завершилась 500, поэтому
   прогон не дал ни одной публикации. Проверка теперь инкрементальная
   ([спецификация](incremental-validation.md)): пакет и зависимые объекты по индексу
   ссылок версий (миграция 00031). Попутно стенд получил 1 ГБ `/dev/shm` для
   PostgreSQL: 64 МБ по умолчанию ломали параллельные запросы (SQLSTATE 53100).
7. **Попадание в кэш Delivery разбирало JSON.** Запись Redis хранилась как JSON с телом
   в base64, и каждое попадание декодировало её целиком: ~40 % CPU CMS в сценарии §2 под
   нагрузкой. Запись теперь двоичная — заголовок (ETag, ключи и версии тегов) и сырое
   тело; чтение записи 10 КиБ — 0,5 мкс вместо 100 мкс, 1 МиБ — 0,6 мкс вместо 11,9 мс.
   Прежние JSON-записи читаются как промах и вытесняются по TTL.

Оставшееся ожидание в отладке — строка `project_revisions` (порядок событий Studio,
обновляется в конце каждой команды) и скорость сброса WAL Docker Desktop; итог
определяют прогоны на Linux.

## Ограничения

- Прокси nginx заменяет CDN (решение §11.3): реальный CDN ближе к клиенту, его
  задержка попадания ниже.
- Пользователи Studio в нагрузке — сервисные токены (решение §11.6); путь через
  Studio-BFF и OIDC проверяет NFR-005 в сценарии §2.
- Стенд использует бинарник `cms` с тегом `e2e` (его же запускает стенд сценария §2),
  а не образ `apps/server/Dockerfile`: код сервера тот же, тег добавляет только
  фикстуру фактов GitHub.
