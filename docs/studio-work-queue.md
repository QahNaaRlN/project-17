## 1. Результат и границы

Пользователь находит любую доступную активную работу по всему серверному набору,
открывает её по CS и проходит сравнение, согласование и явную публикацию независимо
от наличия страницы. Один CS всегда представлен одной строкой. Страницы,
компоненты, сущности, ассеты, их смеси и удаления входят в общую очередь.

«Полная» означает все доступные активные CS выбранного стандартного окружения,
а не историю завершённых работ. Свои `open`, `failed`, `changes_requested`,
`in_review`, `approved` видны владельцу. Чужие `in_review`, `approved` видны
человеку с `content.publish`, если доступны все типы объектов CS. `merged` и
`abandoned` в эту очередь не входят; опубликованный результат доступен в разделе
«Публикации». Пустые собственные CS видны с отметкой «Нет изменений» и запретом подачи.

В пакет входят серверные поиск/фильтры/пагинация, независимая от документа карточка,
переходы и сохранение существующих форм контента в открытом собственном CS.
Для component-only CS доступны обзор, сравнение и workflow; отдельный визуальный
редактор компонентов не создаётся. Создание самостоятельных CS/сущностей/ассетов
из нового мастера, архивная очередь, поиск внутри произвольного JSON/RichText,
полнотекстовый движок, новые роли и новые команды публикации не входят.
Существующие сценарии создания работ через «Страницы» сохраняются.
Production, внешний IdP, Figma и завершение полного M4 остаются отдельными задачами.

## 2. Проверенная исходная точка

`ListStudioWork` в `apps/server/db/queries/workspace.sql` выбирает одну живую
страницу с маршрутом на CS через LATERAL LIMIT 1. Поэтому работы без такой страницы
теряются, включая CS только с удалением. Текущий сервер уже возвращает одну строку
на CS; зависимость от representative documentId остаётся в контракте и UI.

`/work-items` требует `design.read`, допускает только environment/after и использует
UUID-пагинацию. Поиск, состояние и принадлежность в `work-items.tsx` фильтруют
лишь загруженные строки. Это ограничение не относится к поиску раздела «Страницы»:
там серверный `q` уже существует.

`Session.record` обязателен, открытие работы вызывает editor.open(documentId, csId).
Формы контента и workflow зависят от этого контекста. Вход в каркас сейчас требует
одновременно `design.read` и `content.read`. Одной замены SQL недостаточно.
Существующий серверный diff всего CS уже поддерживает сущности/ассеты без страницы;
его проекции и guards сохраняются и используются повторно.

## 4. Query API

Новые маршруты под существующим API prefix: `GET /work-queue` и
`GET /work-queue/{changesetId}`. Legacy `/work-items` сохраняет прежний контракт;
Studio переключается на новый. DTO, ограничения и ошибки описаны в
[контракте OpenAPI 3.1](../apps/server/api/work-queue.openapi.json).

### 4.1. Параметры списка

| Параметр    | Контракт                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------- |
| environment | Обязательное существующее стандартное окружение текущего проекта; входит в targets CS. Preview-токен не даёт доступа к очереди. |
| q           | Необязательная строка: trim, валидный UTF-8, максимум 200 Unicode code points, без NUL; пустая равна отсутствующей.             |
| state       | `all` (default), `open`, `failed`, `changes_requested`, `in_review`, `approved`.                                                |
| ownership   | `all` (default), `mine`, `others`; `others` означает только доступные чужие согласования.                                       |
| kind        | `all` (default), `page`, `component`, `entity`, `asset`; CS проходит, если содержит хотя бы один объект выбранного вида.        |
| limit       | Целое 1…100, default 50.                                                                                                        |
| cursor      | Необязательный непрозрачный подписанный курсор, максимум 2048 ASCII-символов.                                                   |

Неизвестные, повторяющиеся, несовместимые или некорректные параметры дают 400;
окружение чужого проекта или отсутствующее — 404. Пустой результат допустимого
фильтра не является ошибкой. Произвольные projectId/actorId/ownerId из клиента не принимаются.

Поиск — регистронезависимое буквальное подстрочное совпадение по названию CS,
отображаемому имени владельца и путям **всех** затронутых страниц. Для переименований
и удалений учитываются оба пути: base и working. Unicode сравнивается средствами
PostgreSQL с зафиксированной коллацией тестовой/рабочей БД; транслитерация,
морфология и fuzzy matching не обещаются. `%`, `_`, кавычки и обратный слеш —
обычные символы, а не шаблоны SQL. Поиск по телам объектов, email, приватным
ключам хранилища и другим служебным metadata отсутствует. Entity/asset-only CS
находится по названию работы и автору; тип выделяется фильтром. UI называет
поля поиска прямо: «Название работы, маршрут или автор».

Условия доступа, поиска и фильтров объединяются AND до LIMIT. При отсутствии
`design.read` CS с документом/компонентом исключается целиком; при отсутствии
`content.read` исключается CS с сущностью/ассетом. Удалённый объект сохраняет
проверяемый тип. Пустой собственный CS требует хотя бы одного из этих read-прав.
Фильтр kind не разрешает частичное раскрытие смешанного CS. Результат не содержит
числа скрытых работ, совпадений или facet counts.

### 4.2. Ответ и порядок

Ответ: `{ items: WorkQueueItem[], nextCursor: string | null }`.
WorkQueueItem: `id`, `title`, `ownerId`, безопасное `ownerName`, `own`, `state`,
`createdAt`, `updatedAt`, `seq`, `objectCount`, `countsByKind` (page/component/entity/asset),
`deletedCount`. Сумма countsByKind равна objectCount; deletedCount — подмножество.
Текстовые поля имеют существующие серверные ограничения; никаких тел JSON,
списков операций или неограниченных массивов объектов в строке списка нет.
Обязательного documentId/path нет. Summary формируется одной согласованной
read-only транзакцией, без N+1 и побочных команд.

Порядок `createdAt DESC, id DESC`: createdAt неизменяемый, updatedAt служит подписью,
а не ключом пагинации. Курсор HMAC связывает version, проект, актора, окружение,
нормализованный q, фильтры, limit и последнюю пару createdAt/id. Клиент не задаёт
границу отдельно. Подмена, другой контекст, неизвестная версия или повреждение —
400 `WORK_QUEUE_CURSOR_INVALID`, без молчаливого перехода к первой странице.
Ключ берётся из существующей конфигурации подписания, не генерируется на запрос.
Права проверяются заново на каждой странице; курсор не сохраняет право доступа.

Выбирается limit+1; nextCursor=null означает конец на момент запроса. Точного
total нет. Один CS появляется один раз независимо от количества страниц/объектов.
Для неизменившегося набора подходящих работ keyset не пропускает и не повторяет
элементы при добавлении новой работы сверху. Между запросами очередь живая:
сменившие состояние работы могут уйти/войти в выборку, новые сверху видны после
обновления. Глобальный неизменяемый snapshot всей очереди не обещается.
Клиент дополнительно объединяет страницы по CS ID и предлагает обновить начало.

Лимит JSON-ответа 4 MiB; превышение даёт явную ограниченную ошибку
`WORK_QUEUE_LIMIT_EXCEEDED`, не усечённый успешный ответ. Малый limit не скрывает
неподходящие строки из-за фильтрации после выборки. При изменении SQL проверяется
план на 10 000 CS, смешанных типах и совпадении за первой сотней; индексы при
необходимости добавляются миграцией. Это проверка разумного плана, не закрытие NFR MVP.

### 4.3. Прямое открытие

`GET /work-queue/{changesetId}?environment=…` возвращает summary и полный индекс
затронутых объектов: id, kind/docKind, base/working version IDs, deleted,
безопасные подпись и base/working path либо null. Неизвестная подпись не заменяется
придуманным именем; UI показывает тип и короткий ID. Для пустого CS индекс пустой.
Максимум 1000 объектов и 4 MiB; превышение — явная ошибка, без разрешения решений
по неполному списку. Большая работа остаётся доступна как summary в очереди.

Доступ к карточке равен доступу к строке списка. CS чужого проекта, нецелевого
окружения или вне допустимого ownership/state/read scope даёт одинаковый 404
`WORK_QUEUE_ITEM_NOT_FOUND`. Авторизация выполняется до выдачи metadata и поиска.
Права существующих review/history/diff/content маршрутов также проверяются
непосредственно: знания CS ID недостаточно. Для служебных ролей сохраняются
действующие ограничения; никакой новый маршрут не разрешает агенту согласовать.

Review/history/diff остаются отдельными Query API. Карточка не изображает несколько
запросов одним атомарным снимком: сверяет CS/seq/окружение и версию diff; при
расхождении очищает доступные решения и перечитывает данные. Базовые read-права
определяют видимость; дополнительные права и pipeline определяют действия.

## 5. Studio и контекст работы

WorkContext содержит конфигурацию проекта/окружения, CS, seq, manifest/hash,
review/history и выбранный объект при его наличии. DocumentSession добавляет
реальный document record и preview только при входе в поддерживаемый редактор
страницы. WorkContext не получает record с dummy UUID и не создаёт скрытую страницу,
версию, операцию или CS для открытия карточки.

В карточке: название, владелец, состояние, дата с часовым поясом, состав по типам,
полный список объектов, «Сравнение», «Проверки», «История» и текущие действия.
У пустой работы объясняется запрет подачи. У удаления есть tombstone и исторический
путь; кнопки открытия удалённой страницы нет. Для component-only — полный diff
и workflow с пояснением доступного режима. Смешанная работа не сводится к первой
странице: выбор объекта меняет детали, но решение всегда относится ко всему CS.

Формы существующего контента используют WorkContext, manifest и права объекта.
Редактирование возможно только в собственном `open` CS с соответствующим write-правом;
проверки привязок/локалей/RichText/ассетов сохраняются. После сохранения seq,
состав, диагностики и diff перечитываются. В остальных состояниях — чтение и явный
возврат в работу существующей командой, если он разрешён. Страница/preview для
этого не требуется. Создание файла и замена используют прежний безопасный поток,
если действие уже доступно в форме; новый upload pipeline не проектируется.

Вход в каркас требует доступа к проекту и хотя бы одного read-права
(`design.read` или `content.read`). Разделы и запросы учитывают конкретные права:
content-only пользователь не получает редактор/каталог страниц через общий gate.
Отказ одного раздела не блокирует доступную очередь. Сервисный режим сохраняет
свои ограничения; локальная приёмка workflow использует двух людей через OIDC.

Deep link: `/editor#work=<CS UUID>` в выбранном настроенном окружении.
Существующие ссылки на документ сохраняются. Hash не задаёт иной проект, API host
или произвольное окружение. Открытие переводит фокус на заголовок карточки;
возврат восстанавливает поиск/фильтры, загруженные страницы, позицию и фокус строки.
При новом окружении начинается отдельный список. При прямом входе без строки
в истории возврат открывает первую страницу текущей очереди.

Смена работы/документа/окружения блокируется при dirty-вводе, сохранении,
выполняющейся команде или неизвестном исходе. Никакое автоматическое обновление
не уничтожает такой ввод. При потере доступа защищённые данные очищаются;
сохранять или повторять команду от отозванной identity нельзя.

## 6. Поиск, актуальность и решения

Строка поиска отправляется с debounce 300 ms; Enter применяет сразу. Смена
q/state/ownership/kind сбрасывает страницы и курсор. Ключ запроса содержит текущую
identity, проект, окружение и все нормализованные параметры. Старый запрос
отменяется; поздний ответ не меняет новый список. Ошибка следующей страницы
оставляет строки, ошибка нового поиска не показывает старые совпадения как новые.
Подпись количества: «Загружено N работ», без ложного общего total.

Выбранная работа независима от фильтров: пока доступна, карточка сохраняется,
даже если перестала соответствовать поиску, с пояснением. При завершении своей
команды публикации показывается подтверждённый результат и переход к публикации,
строка удаляется. Прямой повторный вход в завершённую работу не обходит active scope.
При внешнем завершении/потере доступа карточка закрывается с понятным сообщением
и возвратом к перечитанной очереди; подробности недоступной работы не остаются.

Очередь обновляется после своих команд, при фокусе окна и каждые 30 s в видимой
вкладке независимо от открытого документа. Имеющиеся SSE-события дополнительно
инвалидируют список/карточку, если соединение есть; подписка на presence фиктивного
документа не создаётся. Новый отдельный SSE endpoint в этом пакете не требуется.
Перед каждым решением сервер всё равно повторяет текущие проверки; интервал
обновления не является гарантией актуальности разрешения.

Смена identity/logout очищает кэш очереди и WorkContext, отменяет запросы и
закрывает подтверждение. 401/403/404 при обновлении выбранной работы запрещает
действия и очищает защищённые данные. При временной сетевой ошибке прочитанный
снимок помечен устаревшим, решения запрещены до успешного перечитывания.

Для submit/approve/request-changes/reopen/publish сохраняются existing command
payloads и правила whole-CS review. Studio передаёт expectedSeq и обязательный
expectedDiffSnapshot там, где он требуется предыдущим пакетом. Self-approval,
approval участником-автором или агентом не разрешается; очередью нельзя обойти pipeline.
Подтверждение публикации называет весь состав и окружение. Неизвестный исход
сохраняет точные payload/idempotency key; повтор использует ту же команду, не новый
ключ. Истечение окна безопасного replay не запускает новую команду автоматически.
Изменение формы, CS или опубликованной базы требует нового просмотра сравнения
перед новым решением. Публикационная история и безопасный откат PR #54 не ослабляются.

## 7. Проверки и приёмка

| Уровень   | Обязательное доказательство                                                                                                                                                                                                                                                |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQL/API   | Более 100 доступных работ: совпадение за первой страницей находится одним поиском; маршрут второй/третьей страницы CS тоже находится. q/state/ownership/kind применяются совместно до LIMIT. Unicode, пустой q, литералы `%`/`_`, повторы/неизвестные параметры проверены. |
| Полнота   | Page/component/entity/asset-only, смеси, удаление последней страницы, отсутствие маршрута и пустой собственный CS. Один CS с несколькими страницами даёт одну строку и точные counts. Поиск старого/нового маршрута покрывает rename/delete.                               |
| Права     | Чужие draft/failed/changes_requested не видны; чужие review/approved требуют человека-публикатора. Чужой проект/окружение и смешанный CS без read-права не раскрываются даже через q, kind или прямой ID. Проверены отзыв/назначение роли и служебный актор.               |
| Курсор    | Равные createdAt, разные IDs, границы limit, последний/пустой результат; подмена actor/project/env/q/filter/limit, подписи и версии; новая верхняя строка между страницами без дублей неизменившихся строк.                                                                |
| Контекст  | Карточка и content-only gate работают без DocumentSession. Сохранение entity/asset обновляет seq/diff; сравнение показывает все типы и удаления. Открытие не меняет число CS, документов, версий или операций.                                                             |
| UI        | Debounce/Enter, гонка поздних ответов, повтор следующей страницы, сброс фильтров, deep link/назад/фокус, offline/empty/no-match, 375 px, клавиатура, RU/EN; скрытые разделы не запрашивают недоступные данные.                                                             |
| Workflow  | CS без страницы: submit → независимый review → approve → явный publish. Reopen/request-changes, отказ self-approval, изменение seq/базы после просмотра, отзыв прав и потеря ответа проверяют прежние guards и точный replay.                                              |
| Регрессии | «Страницы», legacy work-items, редактор/preview, формы контента, mixed-CS diff, история публикаций и безопасный откат сохраняют поведение.                                                                                                                                 |

Локальная сквозная приёмка расширяет существующий стенд и scripts двух OIDC-людей.
Фикстуры готовят через Command API: entity-only, asset-only, component-only,
удаление страницы и смешанный CS, плюс более 100 работ для поиска/пагинации.
Alice находит entity/asset-only работу, открывает и сохраняет доступную форму,
смотрит полный diff и подаёт; Bob находит её серверным поиском, проверяет изменения,
согласует и явно публикует. Для ассета используется валидный завершённый тестовый
upload; mocked metadata не выдаётся за проверку загрузки и доставки файла.

Проверяются committed версии и published pointers в PostgreSQL, ожидаемый контент
через Delivery API и доступность файла при asset-приёмке. Ни открытие, ни workflow
не создают фиктивную страницу. Component-only и deletion-only проходят review
без редактора страницы. Отдельный content-only пользователь входит в каркас,
видит свою очередь, сохраняет разрешённый контент и не получает design-доступ.
Доказательства — отчёт с CS/publication IDs и снимки desktop/mobile без секретов.
Внешний IdP/CDN/production по локальному стенду не объявляются проверенными.

## 8. Реализация, зависимости и готовность

1. Серверный query/DTO/проверки доступа и OpenAPI; SQL, keyset, bounded counts,
   индексы по результатам плана. Проверить права связанных прямых read-endpoints.
2. WorkContext и capability-aware shell; адаптация API/BFF, форм контента,
   review/history/diff/publishing с необязательной DocumentSession.
3. Полная очередь, серверные параметры, карточка, deep links, обновление без
   документа и сохранение guards; браузерная и реальная локальная приёмка.

Зависимости уже в dev: workflow, OIDC-стенд, content forms, whole-CS diff и
guarded publication history. Для приёмки нужны работающий PostgreSQL, тестовое
хранилище ассетов и два локальных человеческих аккаунта; внешнего IdP не требуется.
Отдельной блокирующей зависимости от Figma нет.

Реализация ведётся новой веткой от актуального dev, PR обратно в dev. При изменении
SQL — `go tool sqlc generate`, Go build/vet/race, действующие пороги покрытия;
целевые Studio/API tests, `pnpm check`, браузерная приёмка и CI точного финального
SHA без ослабления существующих проверок. Реальные integration tests требуют
запущенной БД; пропуск или прерванный прогон не означает успех.

Пакет готов только после выполнения STU-176…189, положительной локальной приёмки,
наблюдаемого CI и актуализации документации с реализованными/оставшимися частями.

## 9. Реализовано и локальная приёмка

Реализованы STU-176…189: новые list/card API, фильтры до LIMIT, поиск по всем
маршрутам CS, HMAC keyset, проверка свежих прав, whole-CS visibility, bounded
summary/index и индекс миграции 00019. Legacy work-items сохранён. Studio использует
WorkContext без обязательного record; формы контента, history/diff/workflow
работают без страницы. Вход допускает content-only роль. Сохранены seq/snapshot,
идемпотентный повтор и неизвестный исход; закрытая карточка заменяется квитанцией.
Обновление по таймеру/фокусу не создаёт presence-сессию фиктивного документа.
Усилены прямые чтения CS/review/history/content/diff: чужой открытый CS и
частично недоступная работа скрываются целиком.

Стенд 2026-10-15: CMS 18213, Studio 18214, подписанный OIDC 18215, store 18216,
MinIO 18217; отдельная БД `studio_work_queue_20261015`. Alice находит entity-only
работу за 105 более новыми CS, сохраняет форму и подаёт её; Bob проверяет,
согласует и явно публикует. Тот же путь пройден для asset-only работы после
настоящего upload/processing до ready. Delivery API подтвердил оба результата.
Независимая read-only проверка PostgreSQL подтвердила committed/head/published
версии и отсутствие документов в этих CS. Готовый файл прочитан из локального
S3 с проверкой точного hash. Это не проверка внешнего CDN.

Проверены component-only/deletion-only карточки, прямой вход, 375 px и отдельный
content-only доступ с сохранением формы. Каталог команд пока не предоставляет
document.delete: tombstone для локальной проверки импортируется отдельной
ограниченной фикстурой, остальные изменения создаются Command API. Новая команда
удаления документа в этот пакет не входит.

Воспроизведение: свежий стенд по [инструкции](studio-work-approval.md), затем
`scripts/studio-live-work-queue.mjs`. Нужны `STUDIO_REVIEW_ADMIN_FILE`,
`STUDIO_REVIEW_OUTPUT`, `STUDIO_REVIEW_DATABASE_URL`; URL допускает только
loopback-БД с префиксом `studio_work_queue_`. Фикстура удаления и независимая
read-only проверка находятся в `scripts/fixtures/work-queue-*.go`; исполняются
из Go-модуля сервера. Секреты остаются в локальных private-файлах.
Отчёт `work-queue-acceptance.json`, снимки `work-queue-desktop.png` и
`work-queue-mobile.png` и `work-queue-mobile-card.png` хранятся в локальном каталоге доказательств.

SQL-проверка точного generated query на 10 000 CS находит единственное старое
совпадение; измерено около 25 ms на локальной БД, без заявления о закрытии NFR.
255 тестов Studio и действующие пороги покрытия пройдены. Готовность к слиянию
определяется всеми проверками текущего SHA в PR, включая Go race/coverage и
браузерные сценарии. Полный M4, архивная очередь и внешняя эксплуатация не закрыты.
