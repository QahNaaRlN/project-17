Основа: `origin/dev` на `f30b5a6` (после [PR #82](https://github.com/QahNaaRlN/project-17/pull/82)).
Цель — снять записи `studio-promote` и `studio-production-rollback` реестра
[`pending.ts`](../examples/react-store/e2e/scenario/pending.ts): шаги 8–9
[сценария §2](spec/14-mvp-plan.md#2-сквозной-сценарий-приёмки) выполняются в
Studio, а не командами API. Строка плана MVP: M4, «`promote` в Studio».

## 1. Проблема и границы

Команда `promote {publicationId, toEnvironment}` есть в API (06 §7.2.1), но
Studio её не вызывает: [публикация](studio-publishing.md) STU-073 и
[история публикаций](studio-publication-history.md) §1 прямо исключили promote.
Studio-BFF привязан к одному окружению `config.environment`: каждый query и
command с другим окружением получает `403 STUDIO_ENVIRONMENT_FORBIDDEN`.
Поэтому lead-designer не может из Studio ни перенести публикацию staging в
production, ни увидеть историю production, ни отменить публикацию production.
Сценарий §2 делает это командами API от имени Bob.

Пакет добавляет:

- настроенные **целевые окружения переноса** у Studio (обычно `production`);
- read-only **предпросмотр переноса** со снимком и защиту команды `promote` этим снимком — по образцу отката (STU-166, STU-168);
- действие «Перенести в …» в карточке публикации и выбор окружения в разделе «Публикации»: история и откат целевого окружения тем же экраном.

Вне пакета: редактирование и подача работ в production (работа ведётся только в
`config.environment`), подключение этапов pipeline 1–7 и 8–11 к `promote`
(решение §11.3), автоматический перенос цепочки зависимых публикаций
(решение §11.4), manifest/schema-promote, preview-окружения `pr-*` как цель,
unpublish, внешние IdP, production-развёртывание и реальный CDN.

## 2. Проверенная основа

| Основа | Состояние в dev | Чего не хватает |
|---|---|---|
| Команда `promote` | `content.publish` в целевом окружении; переносит current публикации `publish`/`promote` в окружение вида `standard`; пропускает совпадающие версии; `PROMOTE_OUTDATED`, `PROMOTE_NOTHING`, `PROMOTE_SAME_ENVIRONMENT`, `PROMOTE_NOT_SUPPORTED`, `PROMOTE_SCHEMA_NOT_SUPPORTED`; L1/L3 и транзитивные Composed против manifest цели; `RequireZoneApprovals` для цели; purge в outbox | Снимка просмотренных последствий нет: UUID публикации не доказывает, что пользователь видел текущее состояние цели |
| История и откат | `publication-history` (список, карточка, diff, rollback-preview со снимком), guarded `rollback`, Studio-раздел «Публикации» (PR #54) | Только `config.environment`; promote виден в истории как «Перенос», но не запускается |
| Studio-BFF | `config.environment`, `appOrigin`, `previewAppOrigins` | Нет списка разрешённых целевых окружений и адресов их приложений |
| Сценарий §2 | Шаги 8–9 через API, записи `studio-promote`, `studio-production-rollback` | Шаги в Studio |

Перенос, как и в API, выполняется **по одной публикации**. В сценарии §2 это две
публикации staging: сущность `Collection` (CS редактора) и страница (CS
дизайнера); страница ссылается на опубликованную сущность, поэтому порядок важен.

## 4. Снимок и порядок проверки

Снимок защищает от исполнения переноса по устаревшему просмотру. Он меняется,
если после preview:

- в цели опубликована, перенесена или откатана версия любого объекта публикации (pointer или его происхождение);
- изменился маршрут цели, который проверяет перенос;
- в цели активирован другой manifest;
- изменились политика согласований или агентов цели, роли и права актора;
- CS публикации получил или потерял согласование (переоткрыт, отозван).

Как и у отката, все pointers цели входят в снимок консервативно: несвязанная
публикация в цели требует перечитать preview, после чего перенос снова возможен.

Порядок команды: Command Bus проверяет актора и idempotent replay; handler
блокирует окружения проекта и объекты в порядке ID (как сейчас), пересчитывает
снимок и сравнивает, затем выполняет существующие проверки `promote` и пишет
публикацию, pointers и outbox одной транзакцией. Replay успешной команды
возвращает прежнюю публикацию, хотя её выполнение изменило снимок.

Preview вычисляет те же проверки виртуально, без записи pointers, маршрутов,
публикаций и outbox: нельзя выполнить «пробный promote» и откатить его.

## 5. Конфигурация и стенд

```json
{
  "project": "store",
  "environment": "staging",
  "appOrigin": "http://127.0.0.1:18136",
  "promotionTargets": [{ "environment": "production", "appOrigin": "http://127.0.0.1:18137" }]
}
```

`appOrigin` цели используется только для ссылок после переноса; во фрейм
предпросмотра Studio приложение цели не загружается, CSP `frame-src` не
расширяется. `scripts/e2e-stand.mjs` и `scripts/studio-review-stand.mjs`
получают необязательную вторую витрину и передают её как цель.

## 6. Экран

Раздел «Публикации»: сегментированный выбор окружения над списком
(`staging` · `production`); метка окружения видна в заголовке карточки.

Карточка публикации staging вида `publish`/`promote`:
«Перенести в production…» → загрузка preview → сводка «Будет перенесено: N,
уже в production: M», блокеры с действиями (ссылка на публикацию-зависимость,
«Открыть историю production» для `PROMOTE_OUTDATED`) → диалог с причиной →
«Подтвердить перенос». После успеха — карточка новой публикации production с
подписью «Перенос» и ссылкой на исходную.

Карточка публикации production: прежний «Посмотреть последствия отката»; действия
переноса нет, если других целей нет (STU-474).

## 7. Отступления от спецификации

- 06 §7.2: «перед переносом повторяются этапы 1–7 pipeline против manifest цели».
  Сервер повторяет L1/L3, Composed, маршруты и ссылки, но не все этапы 1–7;
  пакет этого не меняет (решение §11.3), preview честно показывает выполненные
  проверки. Подключение этапов к `promote` — пакет этапов pipeline M6.
- STU-073 и §1 истории публикаций исключали promote из Studio — снимается этим
  пакетом, ограничение «работа в одном окружении» сохраняется.

## 9. Критерии приёмки пакета

- Сценарий §2 в CI проходит шаги 8–9 через Studio; в `pending.ts` осталась только запись `pipeline-8-9`.
- Перенос с устаревшим снимком (публикация в цели, смена manifest/политики/прав, переоткрытый CS) не выполняется и не оставляет следов; проверено тестами на каждое условие §4.
- Неизвестный исход и повтор создают одну публикацию `promote` и один набор outbox.
- BFF не пропускает работу, подачу или `publish` в цель и перенос в окружение вне `promotionTargets`.
- Локальная приёмка: Alice публикует в staging, Bob переносит две публикации в production через Studio, видит страницу на production-витрине, отменяет перенос и видит прежнее состояние; head и открытые CS не изменились.
- Существующие проверки CI, пороги покрытия и E2E не ослаблены.

## 11. Принятые решения — 2026-10-26

1. **Как Studio работает с production.** Одна Studio с `promotionTargets`: работа,
   подача и `publish` — только в `config.environment`; история, перенос и откат —
   также в целевых окружениях. Отдельный экземпляр Studio для production не
   вводится (STU-460, 461).
2. **Снимок для переноса.** Promote-preview со снимком; команда `promote` из Studio
   передаёт `expectedPromoteSnapshot`, расхождение — `409 PROMOTE_SNAPSHOT_STALE`,
   как у отката (STU-462, 465, 466).
3. **Этапы pipeline при переносе.** В пакете — существующие проверки команды
   `promote`; полное подключение этапов 1–7 к `publish` и `promote` одним
   механизмом — пакет этапов pipeline M6. Отступление зафиксировано в §7.
4. **Зависимые публикации.** Перенос по одной публикации; диагностика
   `CONTENT_REFERENCE_UNPUBLISHED` ведёт к публикации, которую нужно перенести
   раньше. Автоматический перенос цепочки не входит в пакет (STU-468).
5. **Причина переноса.** Обязательна: после trim 1…2000 символов, envelope
   `reason`, сохраняется в publication и аудите (STU-467).
