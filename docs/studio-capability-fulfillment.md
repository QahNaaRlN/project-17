## 1. Результат и границы

Когда в стандартное окружение запроса зарегистрирован и **активирован** manifest,
содержащий запрошенный ключ с совместимым контрактом, а версия этого manifest
происходит из проверенного слитого PR запроса, CMS сама переводит запрос в
`fulfilled` и заменяет `pending:<requestId>` настоящим действием во всех
привязках запроса (группа `requiredBy`) от имени системного актора
`service: cms-system`. Владелец каждого Change Set видит замену в карточке
запроса, в работе и в истории CS; обычные проверка, согласование другим
человеком и публикация остаются обязательными.

Один зелёный CI или открытый PR не выполняет запрос. Регистрация manifest
сама по себе тоже не выполняет запрос, если версия не связана с проверенным
слиянием. Ручной путь STU-268 (явное «Применить доступное действие») сохраняется
и остаётся единственным путём для запросов без проверенной GitHub-связи.

В границах: таблица привязок запроса (группа `requiredBy`) и команда
присоединения к существующему запросу; оценка выполнения после активации
standard-manifest; происхождение версии; атомарная замена по каждому CS;
аргументы выполнения; состояния привязок, повтор и undo; системный актор;
уведомления в продукте; Query API, Studio, RU/EN; миграция 00024; локальная
приёмка шага 10 целиком.

Вне границ: component/dataSource/token-запросы (пакет №3), условные политики
агента (№4), почта/внешние уведомления, автоматические подача, согласование или
публикация CS, генерация кода, автоматическое открытие/слияние PR, GitHub
Enterprise, входящие webhook, восстановление `pending` при откате manifest,
изменение уже опубликованных версий.

## 3. Требования

| ID | Требование |
|---|---|
| STU-335 | Привязки запроса хранятся отдельно: `{anchorId, changesetId, documentId, nodeId, event, ownerId, state, revision}`; существующая привязка мигрирует как первая. На запрос ≤ 50 активных привязок, на CS ≤ 20 запросов. Ключ/контракт запроса после submit не меняются |
| STU-336 | `attach-capability-request` присоединяет к **открытому отправленному** запросу, в том числе созданному другим владельцем (решение §11.7), новую привязку в собственном открытом standard CS того же окружения с правами STU-260 (capability.request, design.read, behavior.use, владение CS, эффективная CODE-зона). В одной транзакции проверяются seq/manifest, записывается `node.setBehavior` с `pending:<id>`; замена непустой цепочки требует явного подтверждения. Повтор идемпотентен |
| STU-337 | Владелец видит только свои привязки и их число в группе; разработчик (code.propose) — число привязок и их состояния без IR, страниц и владельцев. Отсоединение — явная операция владельца, удаляющая `pending` из своего узла обычной операцией; последняя привязка отсоединяется только отменой запроса |
| STU-338 | Выполнение оценивается только после **активации** manifest в стандартном окружении запроса (сразу или после публикации схемного CS, MF-021/025). Регистрация в preview, pending-кандидат и чужое окружение не выполняют запрос. Активация ставит задачу оценки в outbox той же транзакции; повторная регистрация того же manifest не создаёт повторной работы |
| STU-339 | Условие выполнения: (1) ключ есть в активном manifest окружения; (2) контракт совместим с proposedContract по правилу STU-268; (3) у запроса активная GitHub-связь; (4) **текущее** (не last-known) наблюдение PR: `state=merged`, `integrationType=merged_commit`; (5) commit code index активного manifest равен `integrationSha` (без сети) либо является его потомком в базовой ветке по проверенному сравнению GitHub compare (§5, решение §11.1); (6) только если политика конфигурации содержит правила `target=integration`, их агрегат `success` на `integrationSha` (решение §11.4). Запрос без GitHub-связи автоматически не выполняется, остаётся ручной resolve (решение §11.5). Любое невыполненное условие — состояние ожидания с причиной, без изменений |
| STU-340 | Перед решением задача запрашивает свежие факты существующей синхронизацией GitHub (бюджеты STU-305 сохраняются) и при необходимости одним GET сравнения commit. Сеть вне транзакций; решение принимается в короткой транзакции после повторной проверки generation/ревизий. Ошибка сети не превращается в выполнение или отказ: запрос ждёт с причиной и ограниченным повтором. Периодического опроса нет: повторная оценка — только по событиям (решение §11.8) |
| STU-341 | Решение атомарно для запроса: `status=fulfilled`, `fulfilled_manifest_id`, `fulfillment_commit`, наблюдение-основание и аудит в одной транзакции; привязки переходят в `queued`. Ручной resolve и автоматическое выполнение взаимоисключающие по revision запроса; выполненный запрос не выполняется повторно |
| STU-342 | Замена выполняется **по CS**: все готовые привязки одного CS (в том числе разных запросов этой активации — группа) заменяются одной группой операций `node.setBehavior` через общий конвейер (inverse, history, rebase, quota) с актором `service: cms-system` и `onBehalfOf` = владелец CS. Ошибка одной привязки откатывает группу этого CS и не затрагивает другие CS |
| STU-343 | Перед заменой под блокировкой CS повторяются: CS открыт (`open` или `changes_requested`), standard, цель — окружение запроса; узел/событие содержат ровно `pending:<id>`; документ не удалён; manifest активен; аргументы валидны L1–L4. Иначе привязка получает состояние `anchor_changed`, `changeset_closed`, `changeset_in_review`, `awaiting_args` или `invalid_args` без записи |
| STU-344 | Аргументы: действие без обязательных аргументов заменяется вызовом без args; при обязательных — используются заранее подтверждённые владельцем **аргументы выполнения** привязки (`set-capability-fulfillment-args`, проверка по standard-manifest на момент выполнения). Preview-аргументы — только префилл формы. Нет подтверждённых — `awaiting_args`, владелец завершает формой (решение §11.2) |
| STU-345 | Системный актор `service: cms-system` создаётся на проект миграцией/bootstrap, без токенов и входа, с единственным правом исполнять замену `pending:<id>` → вызов того же ключа. Любая иная операция от него отклоняется; в истории, diff и аудите он показан как «CMS (система)» с указанием запроса и manifest |
| STU-346 | Undo владельцем группы замены восстанавливает `pending` в его CS (разрешённое восстановление журнала), привязка становится `reverted`; запрос остаётся `fulfilled`. Повторная замена — явной кнопкой владельца. Rebase переносит замену как обычную операцию; конфликт оставляет привязку `anchor_changed` |
| STU-347 | CS в `in_review`/`approved` не меняются системой (это сбросило бы проверку/согласование): привязка `changeset_in_review`; после перевода CS в `open`/`changes_requested` задача повторяет замену (решение §11.3). Слитый, отменённый или удалённый CS — `changeset_closed`, привязка закрыта без изменений |
| STU-348 | Уведомление владельца — в продукте: состояние в карточке запроса, отметка в «Работах» и очереди («Действие доступно» / «Нужны аргументы» / «Требует внимания»), событие realtime проекта. Тексты не раскрывают чужие CS/страницы. Внешние каналы, включая почту, — отдельный пакет (решение §11.6) |
| STU-349 | Последующие регистрации: тот же manifest повторно — no-op; новый manifest без ключа после выполнения не возвращает `pending` и не меняет статус (MF-022 защищает опубликованное; черновики получают обычную диагностику); новый совместимый manifest не перевыполняет запрос. | STU-350 | Публикация по-прежнему отклоняет `pending` (IR-053, STU-269) независимо от статуса запроса; после замены CS проходит обычные проверки, согласование другим человеком и публикацию. Система никогда не подаёт, не согласует и не публикует |
| STU-351 | Query: `GET /capability-requests/{id}/fulfillment` — условия STU-339 по пунктам с причинами, основание (manifest, commit, наблюдение, сравнение), привязки по правам STU-337; `get_capability_request` агента получает краткую сводку без IR. Чтение не вызывает сеть. Чужой scope — 404 |
| STU-352 | Studio: раздел «Выполнение» в карточке (чек-лист условий, основание, привязки владельца с состояниями, «Повторить замену», форма аргументов выполнения с префиллом из preview, «Присоединить к запросу» из панели события), отметка системной группы в истории CS и в Structure. | STU-353 | Миграция/SQL/задачи/команды/Query/Studio и отрицательные сценарии покрыты тестами с ID требований; сбой каждой новой таблицы и шага проверяется инъекцией. Покрытие Go сохраняется ≥ 95% с запасом (цель пакета — ≥ 95.3% по итоговому CI); пороги не снижаются, исключения не добавляются |
| STU-354 | Локальная приёмка шага 10 целиком (§9): две привязки в двух CS, PR слит (факты GitHub — фикстура изолированной БД), CLI регистрирует собранный manifest, запрос выполняется автоматически, заглушки заменены, публикация до замены отклонялась, после — проходит с независимым согласованием, действие выполняется в новом публичном браузере |

## 4. Модель данных и команды

Миграция 00024:

- `capability_request_anchors`: id, project, request, changeset, document, node, event,
  owner, state (`active`, `queued`, `replaced`, `awaiting_args`, `invalid_args`,
  `anchor_changed`, `changeset_in_review`, `changeset_closed`, `reverted`, `detached`,
  `failed`), revision, fulfillment_args jsonb, args_manifest_id, last_error,
  replaced_change_id, timestamps. Частичный уникальный индекс активной привязки на
  (request, changeset, document, node, event). Перенос существующих привязок 1:1.
- `capability_requests`: `fulfillment_commit`, `fulfillment_observation_id`,
  `fulfillment_state` (`waiting`, `verifying`, `fulfilled`) и `fulfillment_reason`.
  Колонки привязки в запросе остаются как исходная привязка (провенанс pack).
- `capability_fulfillment_jobs`: outbox на (project, environment, manifest),
  уникальный по тройке; попытки, lease, причина.
- Системный актор `cms-system` на проект; FK истории допускают его как обычного актора.

| Команда | Payload сверх project/reason/idempotency key | Кто |
|---|---|---|
| attach-capability-request | requestId, expectedRequestRevision, changesetId, expectedSeq, documentId, nodeId, event, expectedManifestHash, confirmReplaceExisting | Владелец CS: capability.request, design.read, behavior.use |
| detach-capability-request | requestId, anchorId, expectedAnchorRevision, expectedSeq | Владелец привязки |
| set-capability-fulfillment-args | requestId, anchorId, expectedAnchorRevision, handlers | Владелец привязки + behavior.use |
| retry-capability-fulfillment | requestId, anchorId, expectedAnchorRevision | Владелец привязки (замена после `reverted`/`anchor_changed`/`changeset_in_review`) |

Создание, отправка и ручной resolve STU-255…268 остаются; resolve теперь
выполняет замену во **всех** привязках владельца в этом CS и помечает
остальные привязки как `queued` для их владельцев (тот же механизм, что §6).

## 5. Происхождение версии

Активный manifest стандартного окружения связан с commit через code index
(STU-263/264): `repo.commit` — полный SHA. Manifest без индекса никогда не
выполняет запрос автоматически (ручной путь доступен).

Сравнение: если commit индекса ≠ `integrationSha`, задача выполняет один
фиксированный GET `repos/{owner}/{name}/compare/{integrationSha}...{commit}` в base
repository теми же учётными данными и сетевыми ограничениями STU-309.
Принимаются только ответы `status ∈ {ahead, identical}` и
`merge_base_commit.sha = integrationSha`; дополнительно проверяется, что commit
достижим из настроенной базовой ветки (поле `base_commit` совпадает с
`integrationSha`, ветка не читается по имени). `behind`/`diverged`, 404, лимиты и
неполные ответы — `commit_unrelated`/`unavailable`, не выполнение. Результат
сравнения хранится нормализованно рядом с наблюдением.

Основание выполнения неизменяемо: manifest id/hash, commit, observation id,
integrationSha, результат сравнения и время. UI называет его «Собрано из
слияния PR #N (commit abc1234), подтверждено GitHub в …», а не «проверено
развёртывание»: CMS по-прежнему доверяет сервисному токену CI в том, что
зарегистрированный manifest собран из указанного commit.

## 6. Выполнение и замена

1. Активация standard-manifest записывает задачу `(project, environment, manifest)`.
2. Задача выбирает отправленные нетерминальные запросы окружения, ключи которых
   есть в manifest, по 100 за проход.
3. Для каждого запроса — STU-339/340: свежая синхронизация GitHub, при
   необходимости сравнение, затем короткая транзакция решения (STU-341).
4. Привязки `queued` группируются по CS; каждый CS обрабатывается своей
   транзакцией в порядке блокировок окружения → CS → объекты (STU-342/343).
5. Итоги привязок, аудит и событие realtime фиксируются в той же транзакции CS.

Lease/CAS и generation защищают от параллельных workers и поздних ответов;
рестарт возобновляет просроченные задачи. Повтор при временных ошибках — до 3
попыток с интервалами 1 и 5 минут; затем `failed` с причиной и кнопкой повтора
у владельца. Состояние «ожидает слияния» не опрашивает GitHub бесконечно:
повторная оценка происходит при следующей активации manifest, явной проверке
владельцем или разработчиком («Проверить выполнение»), и при новом
наблюдении `merged` по связи (уже существующая синхронизация).

## 8. Studio

Карточка запроса, раздел «Выполнение»: статус (`ожидает`, `проверяется`,
`выполнен`), чек-лист STU-339 с текущими значениями (ключ, контракт, PR,
слияние, commit сборки, CI слияния), основание выполнения и время. Список
привязок владельца: страница, узел, событие, состояние, действия «Задать
аргументы выполнения» (форма STU-240 с префиллом из preview-аргументов),
«Повторить замену», «Отсоединить». Разработчик видит число привязок и состояния.

Панель события: если для ключа есть открытый запрос, вместо создания дубля —
«Присоединить к запросу …» с предпросмотром diff. История CS: группа «CMS
(система) · выполнение store.favorite из PR #N» с undo. Работы/очередь: отметки
STU-348. RU/EN, клавиатура, focus/Escape, 375 px, dirty guards и exact retry —
как в предыдущих пакетах.

## 9. Проверки и локальная приёмка

| Область | Обязательные сценарии |
|---|---|
| Миграция | Перенос привязок 1:1, up/down/up, системный актор на существующих и новых проектах |

## 11. Принятые решения — 2026-10-20

Пользователь одобрил спецификацию и принял рекомендации по всем вопросам.

1. **Связь commit сборки со слиянием.** Равенство `integrationSha` проверяется без
   сети; иначе commit сборки должен быть потомком слияния по GitHub compare (STU-339, §5).
2. **Обязательные аргументы.** Применяются заранее подтверждённые владельцем
   аргументы выполнения (префилл из preview); иначе `awaiting_args` (STU-344).
3. **CS на проверке.** `in_review`/`approved` не меняются и ждут возврата в работу (STU-347).
4. **CI слияния.** Успешные проверки на merge commit требуются только при
   правилах `target=integration` в конфигурации (STU-339).
5. **Запросы без GitHub-связи.** Только ручной resolve (STU-339, §1).
6. **Уведомления.** Только в продукте: карточка, работы, realtime; почта —
   отдельный пакет (STU-348).
7. **Группы.** Присоединение к запросу из CS других владельцев разрешено, каждый
   видит только свои привязки (STU-336, STU-337).
8. **Повторная проверка.** Только по событиям — активация, слияние, кнопка — без
   периодического опроса, в пределах бюджетов STU-305 (STU-340, §6).
