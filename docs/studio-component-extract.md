## 1. Результат и границы

Дизайнер выбирает собранный блок на странице и запускает «Сохранить как
компонент». Мастер предлагает имя, входы и слоты. После подтверждения в том же
открытом standard CS появляется новый документ `kind=component`, а исходное
поддерево на странице заменяется одним экземпляром `Composed`
с `ref.version = "live"`. Значения, которые раньше задавались на узлах
поддерева, переходят на экземпляр как `props`/`bindings` входов. Preview
страницы до и после извлечения выглядит одинаково. Компонент проходит
согласование и публикацию вместе со страницей одной публикацией CS.

Приёмочный путь (шаг 3 MVP): блок «ProductShowcase» из шага 2 (`Grid` →
`Stack` с `Heading`, `Text`, `Button` + `Image`) → мастер → входы `title`
(из `Heading.text`), `description` (из `Text.text`), `image` (из `Image.src`),
`products` (новый вход-список по контракту источника) и слот `footer`
(с `Button`) → документ `kind=component` и экземпляр `Composed` на странице
→ undo/redo → reload → согласование другим человеком → публикация →
новый публичный браузер видит тот же блок без preview-атрибутов.

Входят:

- серверная операция `component.extract` с inverse, rebase, проверками L1–L7,
  зон и прав; серверный read-only план извлечения;
- мастер STU-024 в Visual/Structure, инспектор экземпляра (входы и слоты)
  и открытие документа компонента в Structure того же CS;
- `$props`-привязки и Repeat по входу-списку внутри документа компонента
  (минимум, нужный для перехода к шагу 4);
- публикация, откат и `promote` нового компонента вместе с CS;
- MCP-инструменты `plan_component_extract` (чтение) и `create_component`.

Не входят: вставка существующих компонентов из палитры и каталог компонентов
проекта; `component.setInputs`/`component.setSlots` для уже созданных
компонентов; извлечение из документа-компонента (вложенное извлечение);
закреплённые версии `ref.version: <int>` и `node.setComponentVersion`;
`design` экземпляра (IR-060, см. §2); detach/inline экземпляра обратно
в поддерево как пользовательская операция; переименование и удаление
компонента; сертификация в мастере (существующий `component.certify`
остаётся отдельным действием); буфер обмена между документами и `node.wrap`;
Missing Capability для компонентов; Figma и production-развёртывание.

| Сертификация | [`component.certify`](../apps/server/internal/changes/certification.go): сертификация у версии, сброс при изменении тела | Новый компонент создаётся несертифицированным |

| Проверка Composed | [validation.go](../apps/server/internal/composition/validation/validation.go) разрешает ссылки и транзитивные компоненты (`COMPONENT_CYCLE`); [manifestdoc](../apps/server/internal/composition/manifestdoc/validate.go) — `COMPONENT_NOT_FOUND`; [policydoc](../apps/server/internal/composition/policydoc/policy.go) — requiredMode и сертификация; [bindingdoc](../apps/server/internal/composition/bindingdoc/validate.go) — `$props` по `inputs` и входы экземпляра | Повторно использовать на обоих документах одной группы; фикстуры извлечения |
| Runtime | [plan.ts](../packages/runtime/src/plan.ts): только `live`, входы с default/required, слоты с min/max/allowedTypes, защита от цикла; любой `design` экземпляра даёт `CMS_COMPONENT_DESIGN_UNSUPPORTED`. [server.ts](../packages/react/src/server.ts) догружает компоненты через `getDocument` (≤ 64) | Доказать визуальную эквивалентность до/после; черновой компонент в preview своего CS |
| Delivery | `Page.components` в [content.go](../apps/server/internal/delivery/content.go) всегда пуст | Сохраняется: клиент догружает `/document/{id}`; заполнение `components` — вне пакета |
| Studio | [structure.ts](../apps/studio/src/structure.ts) исключает Repeat/Slot/Composed из палитры и не предлагает копировать/перемещать неразрешённый Composed | Мастер, инспектор экземпляра, Structure документа компонента |
| MCP | Каталог [tools.go](../apps/server/internal/agents/tools.go) без компонентных инструментов | Два инструмента, общий серверный код с Studio |

Обнаруженные расхождения, которые пакет фиксирует, а не исправляет молча:

1. IR-060 разрешает на экземпляре `design` размещения, а runtime отвергает
   любой `design`. В этом пакете экземпляр создаётся без `design`; оформление
   выбранного корня, включая `colSpan` и отступы, остаётся на корне документа
   компонента и поэтому одинаково для всех экземпляров. Поддержка IR-060
   в runtime — открытый вопрос Q-2.
2. Каталог кодов 02 §11.2 называет `COMPONENT_RECURSION`, сервер выдаёт
   `COMPONENT_CYCLE`. Пакет использует действующий `COMPONENT_CYCLE` и не
   вводит синоним.
3. Runtime передаёт в область компонента всю область страницы (`$content`,
   `$data`, `$item`), а статическая проверка компонента её не разрешает.
   Контракт пакета: извлечённый компонент зависит от страницы только через
   входы. Фикстура runtime проверяет, что извлечённый компонент не использует
   унаследованную область.

## 4. Операция `component.extract`

### 4.1. Payload

```json
{
  "type": "component.extract",
  "target": { "kind": "document", "objectId": "<pageObjectId>" },
  "payload": {
    "nodeId": "n_showcase",
    "name": "ProductShowcase",
    "description": "Витрина с изображением и списком товаров",
    "inputs": {
      "title":       { "from": [{ "nodeId": "n_h1", "prop": "text" }], "required": true },
      "description": { "from": [{ "nodeId": "n_txt", "prop": "text" }] },
      "image":       { "from": [{ "nodeId": "n_img", "prop": "src" }] },
      "products":    { "def": { "type": "list", "of": { "type": "object", "fields": { "id": { "type": "string" }, "title": { "type": "text" }, "image": { "type": "asset", "assetKind": "image" } } } } }
    },
    "slots": {
      "footer": { "nodeIds": ["n_btn"], "allowedTypes": ["Button", "Link"], "max": 2 }
    },
    "localContent": { "t_cta_label": "move" }
  }
}
```

Цель задаётся конвертом операции. Поле `documentId` из строки каталога 06 §2.2
совпадает с `target.objectId` и в payload не дублируется. Строка каталога
уточняется при реализации. Payload строгий: неизвестные поля отклоняются.

- `name` — 1…80 символов, записывается в `meta.title` компонента.
  `description` — до 500 символов, в `meta.description`.
- Вход задаётся либо `from` (одно или несколько свойств поддерева
  с одинаковым текущим значением), либо `def` (новый вход без источника).
  `def` допустим и вместе с `from`, если сужает выведенный тип: required,
  default, description, enum-подмножество. Расширение типа запрещено.
- Типы нового входа (`def` без `from`): string, text, number, boolean, enum,
  url, link, asset(image), а также list/object, скопированные из result-контракта
  источника активного manifest. Произвольный конструктор схем не вводится.
- `localContent` — решения для ключей `$local`, на которые ссылается поддерево
  и которые не стали входами: `move` (перенести, если на странице больше
  не используется) или `copy` (скопировать, если ключ нужен странице).
  Ключ без решения — `COMPONENT_EXTRACT_LOCAL_UNRESOLVED`. По умолчанию
  Studio предлагает делать контентные свойства входами.
- `componentId`, `instanceNodeId` и ID Slot-узлов клиент не передаёт.
  Сервер назначает их и сохраняет в каноническом payload журнала, как
  `node.insert` сохраняет назначенные ID. Поэтому redo и rebase
  детерминированы.

### 4.2. Результат

Документ компонента:

- `irVersion`, `kind: "component"`, `root` — ID выбранного узла;
- `nodes` — узлы поддерева с прежними ID, кроме диапазонов слотов: на их месте
  стоит `Slot {props: {name}}`;
- у узлов-источников входов literal удаляется из `props`, привязка
  заменяется на `bindings.<prop> = "$props.<input>"`;
- `inputs` по 4.1, `slotDefs` по слотам, `localContent` перенесённых
  и скопированных ключей;
- `policy.mode` равен эффективному режиму места извлечения на странице;
  `maxMode` не выше `maxMode` страницы;
- `dataSources` не переносятся: данные приходят только через входы.

На странице выбранный узел заменяется на
`{type: "Composed", ref: {component, version: "live"}, props, bindings, slots}`
в том же родителе, слоте и позиции. Узлы диапазонов слотов остаются
в документе страницы и переходят в `slots` экземпляра. Узлы поддерева
и ключи localContent со статусом `move` из страницы удаляются.
Пустые коллекции удаляются по правилу 06 §2.2.1.

Before — фрагмент страницы: поддерево в плоской форме, позиция и перенесённые
ключи localContent. After — `{componentId, instanceNodeId, inputs, slotDefs}`.
Оба вычисляет сервер (CHG-010).

### 4.3. Проверки и отказы

Порядок проверок: payload → права и CS → план (4.4) → применение к копиям
обоих документов → L1–L3, L5, L6 на конечном состоянии группы → policydoc.CheckEdit
и validatePending. Любой отказ откатывает всю группу, включая объект, версии,
журнал и seq.

| Код (`operationCode` при `OPERATION_INVALID`) | Когда |
|---|---|
| `PAYLOAD_INVALID` | Неизвестные поля, неверные типы, лимиты имени/описания/числа входов и слотов |
| `NODE_NOT_FOUND` | `nodeId`, `from.nodeId` или `slots.nodeIds` нет в поддереве |
| `COMPONENT_EXTRACT_ROOT_DENIED` | Выбран корень страницы |
| `COMPONENT_EXTRACT_TARGET_KIND` | Цель — не документ `page` |
| `COMPONENT_EXTRACT_PROTECTED` | Зона/locked внутри поддерева, locked-предок без `design.zones.manage`, pending-действие |
| `COMPONENT_EXTRACT_EXTERNAL_SCOPE` | Внешняя область в свойстве без входа или в `when`/`on`/аргументах действия |
| `COMPONENT_EXTRACT_NODE_REF` | nodeRef, anchor-link или scrollTo через границу поддерева в любую сторону |
| `COMPONENT_EXTRACT_LOCAL_UNRESOLVED` | Ключ `$local` без решения или `move` ключа, который нужен странице |
| `COMPONENT_EXTRACT_INPUT_INVALID` | Имя не identifier, зарезервировано (`constructor`, `prototype`, `__proto__`) или повторяется; тип не из списка 4.1; расширение типа |
| `COMPONENT_EXTRACT_INPUT_INCOMPATIBLE` | Источники одного входа различаются значением или типом; тип несовместим с потребителем |
| `COMPONENT_EXTRACT_SLOT_INVALID` | Диапазон не непрерывен, не из одних соседей, включает корень, пересекается с другим слотом или с узлом-источником входа; min/max противоречат числу узлов |
| `COMPONENT_NAME_TAKEN` | Имя совпадает с `meta.title` другого компонента в head проекта или в этом CS (без учёта регистра) |
| `POLICY_TYPE_DENIED`, `POLICY_COMPONENT_MODE_REQUIRED` | Экземпляр не допускается зоной места (allowedTypes/deniedTypes, IR-063, STRICT без сертификации) |
| `LIMIT_EXCEEDED` | IR-014 любого документа; > 64 экземпляров Composed на странице |
| `CHANGESET_SEQ_CONFLICT`, `FORBIDDEN` | Общие отказы Command Bus |

Диагностики не содержат значений контента, недоступного без `content.read`,
и тел чужих черновиков.

### 4.4. План извлечения

`GET /api/v1/documents/{id}/component-extract-plan?changesetId=&nodeId=`
требует `design.read`, а для `$content` — `content.read`. Без этого права
кандидаты из `$content` показываются как «недоступная зависимость» без
выражения. Ответ:

- `blockers[]` — коды и pointers из 4.3, которые не зависят от выбора
  пользователя;
- `candidates[]` — свойства поддерева `{nodeId, prop, type, current: literal|binding-kind,
  content, external, suggestedName}`; `external: true` означает, что вход обязателен;
- `localKeys[]` — ключи `$local` поддерева и признак использования вне его;
- `slotRanges[]` — допустимые диапазоны соседей с типами узлов;
- `sourceListTypes[]` — list/object-контракты источников активного manifest
  для новых входов;
- `effectiveMode`, признаки сертификации и `allowedTypes` места.

План — подсказка. Операция заново выполняет те же проверки в транзакции.
Расчёт плана и проверки операции — одна функция Go, без дублирования в TS.

### 4.5. Undo, redo и история

Inverse — внутренняя операция `component.revertExtract
{componentId, instanceNodeId, before}`. Она не принимается от клиентов
в `apply-operations` (`OPERATION_UNKNOWN`) и порождается только как inverse.
Она восстанавливает фрагмент страницы и localContent в точности и исключает
объект компонента из CS. Рекомендуемая реализация: у объекта ещё нет head,
поэтому строка `changeset_objects` и рабочая версия удаляются, а объект
помечается неиспользуемым без повторного использования ID другими объектами.
Альтернатива — флаг исключения; выбор оформляется при реализации без изменения
контракта. Redo применяет канонический payload и воссоздаёт тот же componentId.

Undo доступен только как отмена всей группы. Если после извлечения в CS есть
операции над компонентом или экземпляром, стек undo по STU-054 сначала отменяет
их. Inverse проверяет, что компонент не изменён и экземпляр не изменён
со времени извлечения, иначе даёт `UNDO_STATE_MISMATCH`, а не частичное
восстановление. Сертификация, выданная позже, снимается вместе с компонентом.

### 4.6. Rebase

Компонент без head не участвует в сравнении баз. Извлечение переигрывается
как операция над страницей:

- поддерево, его позиция и использованные ключи localContent на новой базе
  совпадают с `before` — операция переигрывается с тем же каноническим payload;
- иначе — конфликт `COMPONENT_EXTRACT_BASE_CHANGED` (для узла,
  удалённого на базе, — `OPERATION_INAPPLICABLE`). Доступно только решение
  `theirs`; `mine` молча потерял бы изменения базы внутри поддерева.

Решение `theirs` исключает извлечение вместе с созданным компонентом
и каскадно исключает зависимые операции CS: правки документа компонента,
правки экземпляра и его слотов, а также undo/redo этих записей. Ответ rebase
перечисляет исключённые операции и pointers. Studio предлагает повторить
мастер на новой базе с сохранёнными ответами пользователя.

## 5. Версии, проверки и публикация

Новый компонент получает рабочую версию в CS и первую зафиксированную версию
при слиянии CS. Экземпляр ссылается на `live`. Это значит, что в окружении
рендерится опубликованная там версия компонента. Отдельная публикация
компонента вне CS не вводится.

- Валидация черновика и submit разрешают компонент рабочей версией того же CS.
  Чужой CS его не видит: `COMPONENT_NOT_FOUND`.
- Pipeline проверяет этапы 1–7 для обоих документов; анализ влияния
  PUB-010…012 строит граф с новым компонентом. Риск CS не понижается из-за
  того, что компонент новый.
- Publish атомарно сдвигает указатели страницы и компонента. Если в CS
  страницы с экземпляром нет компонента и в целевом окружении он
  не опубликован, публикация блокируется `COMPONENT_NOT_FOUND`.
- `promote` переносит обе версии. Целевое окружение повторно проверяет
  manifest и политику, в том числе requiredMode.
- Откат первой публикации снимает указатели обоих объектов одной публикацией
  отката. Версии не создаются.
- Согласование и защита решения по снимку (STU-149…161) охватывают оба
  документа. Diff показывает новый документ целиком и замену поддерева
  экземпляром на странице.

## 6. Studio

### 6.1. Мастер STU-024

Запуск: кнопка в панели выбранного узла, контекстное меню дерева
и сочетание клавиш (предложение: Ctrl/Cmd+Alt+K, конфликт проверяется
с STU-023). Мастер — модальный диалог с шагами, которые можно пройти
с клавиатуры, и кнопкой «Назад».

1. **Имя.** Имя и описание. Свободное имя проверяется планом и повторно
   сервером (`COMPONENT_NAME_TAKEN`).
2. **Входы.** Таблица кандидатов из плана: узел, свойство, тип, текущее
   значение (literal/`$local`/`$content`/`$data`/`$item`), имя входа,
   обязательность, default. Внешние зависимости отмечены и не снимаются.
   Контентные свойства предлагаются входами по умолчанию. Если отказаться
   от входа для `$local`, мастер предупреждает: «текст станет общим для всех
   экземпляров», и предлагает move/copy по плану. Кнопка «Добавить вход»
   создаёт новый вход по типу из 4.1; для list/object тип выбирается
   из контрактов источников. Неиспользуемый вход допустим
   с предупреждением `COMPONENT_INPUT_UNUSED`.
3. **Слоты.** Выбор диапазона соседних узлов в мини-дереве поддерева, имя
   слота, allowedTypes (по умолчанию типы выбранных узлов), min/max.
4. **Итог.** Будущее дерево компонента и экземпляра, список входов
   и слотов, предупреждения плана. «Сохранить» отправляет одну группу
   `apply-operations {group: true}` с текущим expectedSeq.

Отказ сервера возвращает к шагу с ошибкой с подсветкой поля; ввод
сохраняется. `CHANGESET_SEQ_CONFLICT` предлагает перечитать план, не повторяя
запись вслепую. Неопределённый исход повторяется только тем же телом и ключом
(STU-053). Пока запрос выполняется, другие записи блокируются (STU-064).

### 6.2. Экземпляр, слоты и документ компонента

- Дерево страницы показывает экземпляр с именем компонента, значком
  и слотами как обычными дочерними группами. Узлы слотов редактируются
  и перемещаются по правилам STU-061 с allowedTypes/min/max слота.
- Инспектор экземпляра строит поля по `inputs` компонента с существующими
  формами привязок (STU-203…218, STU-219…236). Входу `products` можно
  назначить `$data.<key>.items` по совместимому типу.
  Новое поле `design` экземпляра не предлагается (см. §2, пункт 1).
- Клик по узлу внутри экземпляра на холсте выделяет экземпляр. Панель
  предлагает «Открыть компонент». Структура компонента не копируется
  в дерево страницы.
- «Открыть компонент» открывает документ в Structure того же CS: дерево,
  свойства и JSON узла с операциями `node.*` (право `design.compose`)
  по `target` компонента. Для документа компонента отключены
  `document.setContent` и `document.setDataSource`. Picker предлагает
  `$props.<input>` по типам входов, а действие Repeat принимает вход-список
  (`$props.products`) по правилам STU-225…227. Preview остаётся preview
  страницы с экземпляром. Изменения компонента применяются после
  авторитетного перечитывания.
- Изменение тела компонента сбрасывает его сертификацию по действующему
  правилу. Studio предупреждает об этом до записи, если компонент
  сертифицирован.

### 6.3. Preview и история

Preview перечитывает авторитетную страницу и рабочую версию компонента
своего CS после извлечения и после каждой правки компонента. Поздний ответ
отменённого запроса не применяется. История показывает одно действие;
undo возвращает поддерево, выбор переходит на восстановленный исходный узел.
JSON diff страницы не порождает `component.extract` и не создаёт `Composed`.
Ручное добавление `Composed` через JSON на неразрешённый компонент
диагностируется как сейчас.

## 8. Проверки и критерии готовности

Каждое STU-400…419 получает тест или фикстуру с ID по [правилам](testing.md).
Общие Go/TS фикстуры: `packages/ir/fixtures/component-extract.json`
(вход-документ, payload, ожидаемые оба документа, inverse, коды отказов).

| Уровень | Обязательные сценарии |
|---|---|
| Go ops (чистые функции) | Извлечение literal/`$local`/`$content`/`$data`/`$item`-входов; новый вход; слоты; move/copy localContent; все коды 4.3; extract + inverse = исходный документ на случайных документах (как для существующих операций); детерминированный канонический payload |
| Go / PostgreSQL | Создание объекта и версии в группе, откат группы при отказе, seq/idempotency, undo/redo с тем же componentId, `UNDO_STATE_MISMATCH`; права `component.write`/`design.compose`/`content.read`, чужой/закрытый/не standard CS; locked/зоны/STRICT/allowedTypes; rebase: совпадение, `COMPONENT_EXTRACT_BASE_CHANGED`, каскадное исключение; submit/publish/promote/rollback обоих объектов, `COMPONENT_NOT_FOUND` в чужом CS |
| Go/TS conformance | `$props` по inputs, IR-061 на экземпляре, requiredMode, слоты min/max/allowedTypes; одинаковые диагностики Go и TS |
| Runtime / React | Эквивалентность плана рендера до/после на фикстурах (scoped ID нормализуются); компонент не использует унаследованную область; черновой компонент своего CS; отсутствие preview-атрибутов в published |
| Studio | Доступность/причины отключения, шаги мастера, внешние зависимости, move/copy, слоты, итог, отказ/конфликт/потерянный ответ, история одной записью, инспектор входов, выбор внутри экземпляра, Structure компонента с `$props` и Repeat; RU/EN, клавиатура, фокус, 375 px |
| MCP | Оба инструмента, AGT-030…032, actor/onBehalfOf, отказ без `component.write` |
| Реальный браузер (STU-419) | Сценарий §9 |

Критерии приёмки шага 3 MVP:

1. В CS появляется объект `kind=component` с `inputs` `title`, `description`,
   `image`, `products` и `slotDefs.footer`. На странице на месте блока —
   один `Composed` с `ref.version = "live"`, `bindings` входов и `slots.footer`
   с `Button`.
2. В IR компонента и страницы только токены дизайна. Предупреждений L5
   и ошибок L1–L3/L6 нет.
3. Preview на 375 и 1024 px до и после извлечения совпадает (DOM и вычисленные
   стили блока с точностью до scoped ID, скриншоты без отличий выше порога
   сравнения пакетных E2E).
4. Undo возвращает исходное поддерево байт-в-байт, redo — тот же componentId.
   После reload состояние то же.
5. Автор не может согласовать CS. Другой человек согласует, публикация
   атомарно выпускает оба документа. Новый публичный браузер видит блок,
   Delivery до публикации отдаёт 404 для компонента.
6. Связка с шагом 4: в Structure компонента создаётся Repeat по `$props.products`,
   на экземпляре `products` привязывается к `$data.featured.items`, preview
   показывает карточки. Достаточно для перехода к шагу 4; IR-044 и порог
   < 1 с этим пакетом не подтверждаются.

5. Отчёт фиксирует SHA, manifest hash, ID CS/страницы/компонента, версии,
   скриншоты до/после и ограничения среды без секретов. Отчёты
   не коммитятся. Локальная приёмка на рабочем дереве не заменяет CI
   конечного SHA. Пороги не снижаются.

Порядок реализации после одобрения: чистая операция и inverse с фикстурами →
план и Command Bus/rebase/публикация → runtime-эквивалентность → мастер
и инспектор → Structure компонента с `$props`/Repeat → MCP → сквозная приёмка.

## 10. Открытые продуктовые вопросы

- **Q-1. Повторное использование.** Без вставки компонента из палитры
  компонент используется один раз. Рекомендация: отдельный следующий пакет
  «каталог и вставка компонентов» (STU-060 сейчас исключает Composed),
  до `component.setInputs/setSlots`.
- **Q-2. Размещение экземпляра (IR-060).** Оставить оформление корня внутри
  компонента (текущий выбор) или в этом пакете научить runtime `design`
  размещения на экземпляре и переносить `colSpan`/`order`/внешние отступы
  корня на экземпляр? Второй вариант точнее соответствует IR-060,
  но расширяет runtime.
- **Q-3. Входы-списки.** Тип `products` копируется из контракта источника
  (`store.products`). Нужен ли конструктор object/list-типов или ссылка на
  `reference Product`? Рекомендация: только копия контракта в MVP.
- **Q-4. `$local` без входа.** Предлагать `copy` или `move` по умолчанию,
  и разрешать ли вообще общий текст компонента без входа в SYSTEM-зонах?
- **Q-5. Извлечение в STRICT-зоне.** Разрешить ли пакет «извлечь
  и сертифицировать» одной группой для пользователя с
  `design.components.certify` или оставить два явных шага?
- **Q-6. Уникальность имени.** Имя уникально в проекте (текущий выбор)
  или допускаются дубли с разными ID? Нужен ли отдельный машинный ключ
  компонента помимо `meta.title`?
- **Q-7. Слот без узлов.** Разрешать ли объявить пустой слот
  (`footer` без выбранных узлов, `min: 0`) или слот всегда создаётся
  из существующих узлов?
- **Q-8. Агент.** Достаточно ли текущего риска агентского CS ≥ medium или
  создание компонента агентом должно повышать риск до high?
- **Q-9. Каскад при rebase.** Исключать зависимые операции автоматически
  (текущий выбор, со списком в ответе) или требовать явного решения
  по каждой?
